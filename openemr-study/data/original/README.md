# Reproducibility artifact: Who Writes the Bug, Who Finds the Bug?

Companion data for the ISC2 Security Congress 2026 talk *"Who Writes the Bug,
Who Finds the Bug? Human-AI Security Lessons from Open Source"* (Eric St-Pierre,
Medoya Consulting LLC).

This is a **measured case study, not a benchmark leaderboard**. It traces
confirmed CVEs in a large open-source healthcare platform (OpenEMR) back to the
commit that introduced each one, then asks a counterfactual: reviewing the
selected introducing-file diff without the target advisory, would a
general-purpose AI model have flagged it? This is a retrospective replay, not
an observed historical merge decision or a full-PR detection benchmark.

## The question

Which known flaws do the recorded AI review configurations flag, and how do
review instructions and supplied context affect targeted follow-up results?
There is no matched human-versus-AI review experiment. The results motivate
routing hypotheses and a reusable evaluation rubric, not a validated division
of defect classes between people and AI.

## Headline results (blind review, 24 validated CVEs + 10 benign controls)

Two recorded model identities (`claude-sonnet-5` and `claude-haiku-4-5-20251001`)
were evaluated across all 24 validated CVEs (144 review runs) and 10 comparison diffs
(20 runs). Numbers are reported **split by cohort** (Group A = 16 CVEs disclosed
Feb-Mar 2026, after both models' training cutoffs; Group B = 8 older CVEs disclosed
2018-2025):

The original reviews ran through Claude Code. Sonnet was selected through a
harness alias, so the records do not establish one immutable snapshot across
the August runs and October repairs. The frozen user prompt already mentions
security alongside correctness, reliability and maintainability. It does not
identify the target flaw or use a security-specialist checklist.

| Model | Cutoff | Post-cutoff Caught (Group A) | Post-cutoff Partial | Post-cutoff Missed | Older Caught (Group B) | All Valid Caught |
|-------|--------|------------------------------|---------------------|--------------------|------------------------|------------------|
| Sonnet 5 | Jan 2026 | 13 / 16 | 3 / 16 | 0 / 16 | 7 / 8 | 20 / 24 |
| Haiku 4.5 | Jul 2025 | 5 / 16 | 6 / 16 | 5 / 16 | 3 / 8 | 8 / 24 |

- **Single-file vs Cross-file visibility:** Across the **20 CVEs where the vulnerable
  sink and security contract were visible inside the diff**, Sonnet 5 caught **20 of
  20 (100%)**. Across the **4 CVEs where confirming exploitability required a second
  file outside the diff** (`CVE-2025-31121`, `CVE-2026-24487`, `CVE-2026-25146`,
  `CVE-2026-33321`), Sonnet 5 caught **0 of 4 (3 Partial, 1 Missed)**. This is a
  post hoc grouping, not proof that missing context caused each incomplete result.
- **Benign controls (`benign_controls/`, 10 diffs):** On 6 security-fix patches and 4
  routine commits, Sonnet 5 raised **0 of 10 false security alerts** (Haiku 4.5 raised
  1 Medium false security alert on `BENIGN-03`), while raising **4 of 10 High
  missing-context correctness warnings** asking to verify callers, helper functions,
  or PHP version support outside the single-file diff.
- **Post-cutoff fix dates:** On the 8 Group A cases whose security fix became public
  in OpenEMR's repository **after** Sonnet 5's January 31, 2026 training cutoff,
  Sonnet 5 caught **7 of 8 (88%)**. Every case caught by Haiku 4.5 (8 of 24) was also
  caught by Sonnet 5 (0 Haiku-only catches).

Signal findings:

- **Longest commit-to-disclosure interval:** a SQL injection left behind by a
  2010 security hardening commit and disclosed 15.7 years later (5,720 days) was
  scored Caught on all 3 runs by Sonnet 5 (`CVE-2026-29187`). Prior training
  exposure to the code is not ruled out.
- **Verified cross-file miss (both models, 0 of 6 runs):** `CVE-2025-31121`
  (stored XSS via `C_Document::retrieve_action()` returning raw file bytes when
  `$disable_exit=true`, which `Controller::act()` in `Controller.class.php`
  splats from `$_GET` and echoes as `text/html`). In reviews supplied with the diff
  of `C_Document.class.php` but not `Controller.class.php`, both models flagged
  file-handle leaks and encryption order, but missed the XSS across all 6 runs.
- **Severity/actionability gap (`Partial`):** on `CVE-2026-25146` (payment
  `gateway_api_key` secret rendered into client-side JS), Sonnet 5 Run 1 spotted
  the exact line but downplayed it as Low/Medium ("worth confirming"), scoring
  `Partial` rather than a merge-blocking `Caught`.
- **Evaluation hygiene lessons:**
  1. **Verify ground truth on the vulnerable mechanism, not just advisory links:**
     2 of 24 initial cases (`CVE-2026-24487`, `CVE-2026-24849`) were linked to
     commits that patched different mechanisms (`FhirLocationService.php` and TLS
     verification in `CDADocumentService.php`); both were caught in audit and
     quarantined in `validity.csv`.
  2. **Separate execution errors from misses:** 1 of 144 runs (`CVE-2026-25146`
     Sonnet Run 2) returned empty output, was reclassified as an execution
     error (`run_status.csv`), and was re-run under the same recorded model identity on
     2026-10-15 (scored Partial).
  3. **Self-reported recognition is noisy:** both models recognized OpenEMR on
     at least 22 of 24 valid cases and occasionally claimed awareness of
     advisories disclosed after their own training cutoff. Scoring credits only
     technical detection, and human adjudication verified all 48
     case-model scores (48 of 48 majority scores; 142 of 144 individual runs).

## Targeted follow-ups: context, instructions and false alarms

The four original Sonnet 5 gaps were retested through the direct API, with three
reviews per case and condition. The researcher selected one historical context
file per case using the known vulnerability trace. General review plus context
scored two recovered cases, patient access and payment-secret exposure. Security
plus touched-code instructions with the same context scored three, adding
stored XSS. PDF-rendering SSRF remained Partial.

Thus 20 original catches plus two or three distinct recovered cases yields
**22, then 23 of the original 24 with a scored catch across experiments**. The
original 20 were not rerun under the improved conditions. These are accumulated
case coverage, not detection rates for one fixed 24-case workflow. The
follow-up used model judging and model-applied Rule B rulings and awaits
independent human verification. It did not measure false alarms with added
context. See `followup_expanded_context/README.md` and `final_detection.csv`
in that folder.

Separate prompt controls found false security alarms in **0/10** Sonnet 5
general-prompt reviews and **5/10** security-plus-touched-code reviews, with
**2/10** of the latter Medium or higher. These are individual reviews of ten
comparison changes, not majority-of-three vulnerability scores. See
`followup_security_prompt/README.md` and `benign_summary.csv` in that folder.
Jev routing and ZZ-Trace did not select the prompts or context in these scored
follow-ups and receive no credit for the recovered cases.

## Reproducing the method

The tooling is the `quadrant` CLI (Python stdlib + lazy pandas), included with
the talk materials. In brief (full steps in `METHODS.md`):

1. Clone the target repo and enrich the CVE list from GitHub Security Advisories,
   NVD 2.0, and OSV.dev.
2. Trace each CVE to its introducing commit (SZZ-style, via `git blame` on the
   fix), record survival and who caught it.
3. Extract the introducing diff and **blind** it (strip the commit message,
   neutralize filenames).
4. Run the frozen prompt (`prompt.md`), 3 runs per CVE per model.
5. Score against the CVE with a separate model (`rubric.md`), majority of 3.
6. Regenerate `compare.txt` to see the cross-model grid and drift.

Future runs should record the resolved model configuration, complete request,
actual tool/file access, input revisions, execution errors and judging rules.
The archived review text can be rescored, but exact original request bytes and
repository reads were not retained for the inspected D05 baseline. The historical
Claude Code environment is not fully reproducible from the user prompt alone;
new API runs are new configurations, not reconstructed historical executions.

## Honesty caveats

- This is **one codebase and two models**. Treat it as a method demonstration
  with real numbers, not a universal ranking.
- The post-cutoff versus older gap is *consistent with* contamination but not cleanly
  separable from difficulty (the two sets differ in vulnerability
  mix and diff size). See `rubric.md`.
- Of 32 CVE candidates, 28 traced (22 with high confidence); some introducing
  commits predate the GitHub PR workflow or arrived as bulk imports, so tracing
  is a lower bound for those. Details and per-CVE flags are in `cves.csv` and
  `METHODS.md`.
- An earlier-cutoff frontier reviewer (Sonnet 4.6 / Opus 4.6, Aug 2025 cutoff) was
  planned but not executed in the original 24-case comparison;
  Haiku 4.5 is the earlier-cutoff anchor in this round (its cutoff predates
  all 16 Group A fixes; neither cohort is contamination-free).
- The inputs were selected retrospectively: 25 of 26 staged diffs were scoped to
  the known vulnerable file. The inventory has seven CVEs without scored runs;
  their exclusion reasons are not recorded. A future held-out full-PR study is
  needed to test generalization and automatic context selection.

## Responsible disclosure

All CVEs here are already publicly disclosed and fixed. No new or undisclosed
vulnerability is described in this artifact.
