## Security review: `FhirCareTeamService.php`

I found no high- or medium-severity vulnerabilities in this diff. The notes below are low severity or items to verify.

### Findings

**1. `xlt()` used on database values in a JSON API response**
- **Location:** `parseOpenEMRRecord`, `$description = xlt($dataRecordProvider['role_title']);`
- **OWASP:** A03 Injection (output encoding), A04 Insecure Design
- **Problem:** `xlt()` is meant for translating constant UI strings and HTML-escaping them. Here it is applied to a stored value (`role_title`) and the result goes into a FHIR JSON payload. This HTML-entity-encodes data in a non-HTML context, which corrupts values (for example `&amp;`). It is also the wrong control. FHIR clients that render the JSON as HTML need to do their own encoding, and consumers that assume the data is not pre-encoded may double-encode or mishandle it. It is not directly exploitable, because `json_encode` prevents breaking out of the JSON.
- **Severity:** Low
- **Fix:** Return the raw value. Let `json_encode` and the client handle output encoding.

**2. Loose comparison in `array_search` for status validation**
- **Location:** `array_search($dataRecord['status'], self::CARE_TEAM_STATII) !== false`
- **OWASP:** A04 Insecure Design (input validation)
- **Problem:** `array_search` is non-strict by default. On PHP 7, a value such as `0` or `true` loosely equals `"active"`, so it passes validation and is passed to `setStatus()`. A missing `status` key also raises an undefined-index notice. The practical impact is a malformed resource, not a compromise.
- **Severity:** Low
- **Fix:** Use `in_array($status, self::CARE_TEAM_STATII, true)` and check with `isset`.

**3. Unvalidated codes passed to `lookup_code_descriptions`**
- **Location:** `lookup_code_descriptions($dataRecordProvider['role_code'])` and `lookup_code_descriptions($dataRecordFacility['facility_taxonomy'])`
- **OWASP:** A03 Injection (second-order)
- **Problem:** These values come from the database (user and facility settings) and go into a helper outside this diff. Confirm that the helper uses bound parameters. The helper is not shown, so I cannot confirm it is safe. The TODO about the `facility_taxonomy` column size also suggests the stored data may be truncated or malformed.
- **Severity:** Low (verify)

**4. Removal of the `getOne` override: access-control dependency**
- **Location:** deleted `getOne($fhirResourceId, $puuidBind)`
- **OWASP:** A01 Broken Access Control
- **Problem:** The old override passed `$puuidBind` directly to `CareTeamService::getOne`. The service now falls back to `FhirServiceBase::getOne`, which should go through `searchForOpenEMRRecords` with `_id` and `$puuidBind`. That is probably fine. Verify with a test that a patient-scoped token cannot read another patient's CareTeam by `_id`, and that `$puuidBind` is always applied in `CareTeamService::getAll`.
- **Severity:** Low (verify)

### Positive changes
- `getAll(..., false, ...)` became `getAll(..., true, ...)`. If `false` meant OR semantics, the old code could combine the patient filter with other filters using OR and return records outside the patient's scope. Switching to AND is a fix. Confirm that `$puuidBind` is enforced as a mandatory AND condition in `CareTeamService`.
- References are now built through `UtilsService::createRelativeReference`, and the meta object is typed properly.
- `createProvenanceResource` validates the type of its input.

### Summary
There are no injection, authentication, or SSRF issues in this change. Before merging, confirm the patient-binding behavior of the inherited `getOne` and `getAll`, and fix the `xlt()` misuse and the loose status comparison.
