# Security Review: `interface/forms/eye_mag/report.php`

## Summary
This is a large, newly-added report-rendering script with several significant issues. The most serious is a lack of any access-control/authorization check on patient data (IDOR), combined with several stored/reflected XSS sinks, unsafe use of PHP's `extract()`/variable-variables, and a few raw string-concatenated SQL queries. Individually some of these are low risk, but combined on a page that renders full PHI (chief complaint, HPI, exam findings, photos) they are serious.

---

### 1. Broken Access Control — Missing authorization / IDOR
**Location:** Top of file, request handling block:
```php
if ($_REQUEST['ptid']) $pid = $_REQUEST['ptid'];
if ($_REQUEST['encid']) $encounter=$_REQUEST['encid'];
if ($_REQUEST['formid']) $form_id = $_REQUEST['formid'];
```
and throughout `narrative()`, `eye_mag_report()`, `display_draw_image()`.

**Problem:** `pid`, `encid`, and `formid` are taken directly from the request and used to pull patient demographics, clinical notes, images, and prescriptions, with no call to `acl_check()`, `aclCheckCondition`, or any verification that the logged-in user is permitted to access this particular patient/encounter. There is no "patient in current user's care" check seen anywhere in this file (unlike most other OpenEMR form report scripts). Any authenticated user can likely enumerate `ptid`/`encid` values to view other patients' exam data, photos, and clinical notes.

**Severity:** High (sensitive health data exposure / IDOR).

---

### 2. Cross-Site Scripting (XSS) — unescaped output of DB-sourced free text
**Location:** 
- `&nbsp;<?php echo $HPI1; ?>` (HPI1 is echoed raw, unlike every other field in the same block which goes through `text()`).
- `echo $item['codetext']."<br />";`, `echo $item['code']."<br />";`, `echo $item['plan']."</div><br />";` in the Impression/Plan rendering loop (`$query = "select * from form_".$form_folder."_impplan ..."`).
- `echo $item."<br />";` and `echo $PLAN2."<br />";` for `$PLAN_items`.
- `report_ACT()` uses `htmlspecialchars($term, ENT_NOQUOTES)` — quotes are *not* encoded, which is weaker than the `text()` helper used everywhere else.

**Problem:** These fields (`HPI1`, `plan`, `codetext`, `PLAN`/`PLAN2`) originate from user-entered clinical text stored in the database. They are rendered without HTML-encoding (`text()`/`htmlspecialchars` with full entity encoding), allowing stored XSS if a user (or compromised account) previously stored `<script>` or event-handler payloads in these fields. This is inconsistent with the rest of the file, which correctly wraps nearly every other field in `text()`.

**Severity:** High (stored XSS in a clinical record viewed by multiple staff members).

---

### 3. Reflected/Stored XSS via unescaped attribute interpolation
**Location:**
```php
$filetoshow = $GLOBALS['webroot']."/controller.php?document&retrieve&patient_id=$pid&document_id=".$doc['document_id']."&as_file=false&blahblah=".rand();
echo "<img src='".$filetoshow."' style='width:220px;'>";
```
(appears twice — patient photo block and `display_draw_image()`).

**Problem:** `$pid` comes straight from `$_REQUEST['ptid']` and is placed into an HTML attribute without `attr()` encoding. If it contains a `'`, `>`, or other HTML metacharacters, it can break out of the `src` attribute and inject markup/script. Relying on `$sanitize_all_escapes` (which targets SQL-safety, not HTML-safety) is not a substitute for output encoding.

**Severity:** Medium–High.

---

### 4. SQL Injection — string-concatenated queries instead of parameterized statements
**Location:**
```php
if ($_SESSION['pc_facility']) {
  $sql = "select * from facility where id=" . $_SESSION['pc_facility'];
}
```
```php
$sql = "SELECT * from documents where documents.url like '%".$filename."'";
```
(`display_draw_image()`, where `$filename` is built from `$pid`/`$encounter`, both request-derived)

Also, dead/commented-out code retained in the diff:
```php
$sql = "SELECT * from documents where url='file://".$file_location."'";
```

**Problem:** Unlike the majority of the file, which correctly uses parameterized `sqlQuery()/sqlStatement()` calls, these build SQL via string concatenation with request-influenced values (`$pid`, `$encounter`) or session values. Even though global "sanitize_all_escapes" may mitigate some injection vectors, this is fragile defense-in-depth and inconsistent with secure coding guidance; it should use bound parameters like the rest of the file.

**Severity:** Medium (likely mitigated in part by global escaping, but still a code-quality/defense-in-depth failure and a true injection vector if that escaping has any gap).

---

### 5. Insecure Design — unsafe use of `extract()` and dynamic variable-variables on DB data
**Location:**
```php
@extract($objQuery);
```
(`eye_mag_report()`, `narrative()`), plus:
```php
$LOCATION = $prefs['LOCATION'];
$$LOCATION = text($prefs['GOVALUE']);
```
and the `${"ODSPH_$count_rx"} = ...` pattern repeated throughout.

**Problem:** This recreates register_globals-style behavior (ironically, the file explicitly sets `$fake_register_globals=false;` at the top) by exporting arbitrary DB column names as live PHP variables. Any column added to `form_eye_mag`, `form_eye_mag_prefs`, or `form_eye_mag_wearing` can silently overwrite program-control variables like `$choice`, `$pid`, `$PDF_OUTPUT`, `$cols`, etc. This is a classic "variable variables / extract injection" pattern (CWE-621 / CWE-915) that makes the security behavior of the script dependent on database schema and content, and is very hard to audit. The `@` error-suppression operator also hides any resulting notices that might reveal the problem.

**Severity:** Medium (design flaw with unpredictable impact, hard to rule out exploitation paths).

---

### 6. Security Logging and Monitoring Failures
**Location:** Use of `@extract($objQuery);`, `@sqlQuery()` style suppressed errors in several spots.

**Problem:** No logging of access to patient reports, and warnings/errors are deliberately suppressed with `@`. This reduces the ability to detect anomalous access patterns (e.g., repeated requests with mismatched `ptid`/`encid` that may indicate IDOR probing).

**Severity:** Low–Medium.

---

### 7. Minor / Informational
- `if ($_REQUEST['CHOICE']) $choice = $_REQUEST['choice'];` — case mismatch (`CHOICE` vs `choice`) looks like a bug, not a vulnerability, but indicates insufficient testing of this input-handling code.
- File paths are built using `$GLOBALS["fileroot"]`, `$GLOBALS['OE_SITE_DIR']`, etc., combined with filenames derived from the `Document` class — this pre-existing pattern (not introduced here) should be checked elsewhere for path traversal, since it is reused in this new file (`display_draw_image()`, patient photo block).
- No CSRF token is used, but since this endpoint appears read-only (GET, no state change), this is low risk — still worth confirming no side effects occur on load.
- Inline PDF/image paths reference `$GLOBALS["webserver_root"]` and construct `sign_$providerID.jpg` paths; `$providerID` comes from `getProviderIdOfEncounter($encounter)` (DB-derived, lower risk) but is worth confirming it can't be influenced by request data indirectly.

---

## Recommendations
1. Add explicit authorization checks (`acl_check()`/patient-encounter ownership validation) before any data is fetched or rendered, based on `$pid`/`$encounter`/`$form_id`.
2. Wrap **every** field originating from the database in `text()` (or `xlt()`/`attr()` as appropriate) before output — audit `$HPI1`, `plan`, `codetext`, `code`, `PLAN`, `PLAN2`, and the `report_ACT()` helper (use `ENT_QUOTES`).
3. Use `attr()` for all values interpolated into HTML attributes (e.g., `$filetoshow`, `$pid` in img src URLs).
4. Replace concatenated SQL (`facility where id=...`, `documents.url like '%...'`) with parameterized `sqlQuery()`/`sqlStatement()` calls consistent with the rest of the file.
5. Remove/avoid `extract()` and variable-variable patterns on data pulled from the database; use explicit, named array access instead.
6. Remove `@` error suppression and add logging around patient-data access for audit purposes.
