Known vulnerability:
CVE-2025-31121 (XSS, OWASP A03), file controllers/C_Document.class.php.
This change adds a fifth positional parameter, $disable_exit = false, to
C_Document::retrieve_action() and, when it is set, returns the raw document file contents

## Summary

This diff adds a `$disable_exit` parameter to `C_Document::retrieve_action()` so the function can **return** file bytes instead of streaming them to the browser and calling `exit`/`die`. Because this controller method is invoked through the generic, reflection-style dispatcher in `Controller::act()`, the new parameter is effectively attacker-controllable from the query string, and the new code paths bypass several protections that the original code relied on (headers, encryption, logging). Below are the issues found.

---

### 1. Broken Access Control / Insecure Design — new parameter is reachable and controls security-relevant behavior
**Location:** `controllers/C_Document.class.php`, `retrieve_action($patient_id, $document_id, $as_file, $original_file, $disable_exit)`; dispatch logic in `library/classes/Controller.class.php::act()`

`act()` builds `$args_array` purely from the names/values present in the request query string (`$qarray`) and calls the target `*_action` method with `call_user_func_array`. There is no allow-list of parameters that may be set this way. This means a request such as
`...&action=retrieve&patient_id=..&document_id=..&as_file=1&original_file=1&disable_exit=1`
can set `$disable_exit` directly. A parameter that was presumably meant to be used only for **internal/programmatic** calls (e.g., from another controller method that needs the raw bytes) is now exposed to any external caller who can reach this action, letting them flip an internal behavioral switch that was never designed to be part of the public API.

**Severity:** High — turns an internal implementation detail into an externally-controllable security-relevant flag.

---

### 2. Cryptographic Failure — encryption is bypassed when `disable_exit` is set
**Location:** lines around:
```php
$f = fopen($url,"r");
$filetext = fread( $f, filesize($url) );
if($disable_exit == true) {
    return $filetext;
}
...
if ( $doEncryption ) {
    $ciphertext = $this->encrypt( $filetext, $passphrase );
    ...
}
```
and the CouchDB branch:
```php
if($disable_exit == true) {
    return base64_decode($content);
}
```
In the normal flow, `$doEncryption` decides whether the file content is encrypted before being sent out (`$this->encrypt($filetext, $passphrase)`). The new `$disable_exit` branch returns `$filetext` (or the base64-decoded CouchDB blob) **before** the `$doEncryption` check is ever evaluated, unconditionally returning raw/plaintext content regardless of whether the caller/document required encryption. If any caller relies on `original_file`/`disable_exit` to retrieve data that is supposed to be encrypted (e.g., for secure transmission, portal download, API response), the encryption step is silently skipped.

**Severity:** High — defeats an existing confidentiality control for what is likely PHI (patient documents).

---

### 3. Security Misconfiguration / Potential XSS — security headers are skipped in the new return path
**Location:** same blocks as above; compare to the surrounding (unmodified) code that sets:
```php
header('Content-Description: File Transfer');
header('Content-Transfer-Encoding: binary');
...
```
These headers (and, elsewhere in the untouched code, `Content-Disposition`/`Content-Type`) force the browser to treat the document as a download/binary stream rather than rendering it. The new `disable_exit` paths return raw file bytes to the caller with **no headers at all**. If the returned value is later echoed/rendered by whatever code calls `retrieve_action($disable_exit=true)` (e.g., inlined into a page, used in a preview, or passed to another handler that doesn't itself set a safe `Content-Type`), an attacker-uploaded document (HTML/SVG/JS masquerading as an allowed file type) could be rendered in the browser context, leading to stored XSS. Since the PR diff does not show the caller, this is a latent risk introduced by removing the header-based protections for this specific response path.

**Severity:** Medium–High, depending on how the returned value is consumed by the (unseen) caller.

---

### 4. Security Logging and Monitoring Failure — audit trail bypass
**Location:** CouchDB branch already present (`$this->document_upload_download_log(...)`) is only called on the **error** path; the new `return base64_decode($content)` success path (and the local-file `return $filetext;` / `return;` paths) do not call `document_upload_download_log()` before returning.

Document retrieval in a medical records system (OpenEMR) should be audited for compliance (HIPAA access logging). The new early-return paths skip whatever download/access logging the normal flow would have performed after the headers/output block, meaning accesses made via `disable_exit=true` are not recorded in the audit log.

**Severity:** Medium — compliance / forensics impact rather than direct compromise.

---

### 5. Weak input validation — loose comparison on a security-relevant flag
**Location:** `if($disable_exit == true)` (used three times)

`$disable_exit` is compared with loose `==` against `true`. If this value ever arrives as a string from user input (as it would via the `Controller::act()` dispatch mechanism), PHP's loose comparison means almost any non-empty, non-"0" string (`"false"`, `"no"`, `"1"`, etc.) evaluates as `true`. Combined with issue #1, this makes it trivial to toggle this branch unintentionally or maliciously. Should use strict comparison (`=== true` or `== '1'` cast appropriately) and, more importantly, should not be influenced by request input at all.

**Severity:** Low–Medium (amplifies issue #1).

---

### 6. No error handling around new `fopen`/`fread` calls
**Location:**
```php
$f = fopen($url,"r");
$filetext = fread( $f, filesize($url) );
```
`$url` is not validated here, and `fopen`/`filesize` failures (file missing, permissions, race condition) are not checked. This can produce PHP warnings/notices (information disclosure of file paths in error output if `display_errors` is on) and/or pass `false` into `fread`, returning empty or corrupted data silently. This is a minor robustness/misconfiguration issue, but worth fixing alongside the refactor since the diff moved this code and had a chance to add checks.

**Severity:** Low.

---

### 7. Pre-existing issues touched by this change (not introduced, but now more reachable)

- **Broken Access Control (IDOR):** `retrieve_action()` takes `$patient_id` and `$document_id` directly and (in the visible code) does not show an authorization check that the currently authenticated user/session is permitted to access the specified patient's document before reading/returning its content. Since this PR adds a new way to retrieve content programmatically (`disable_exit`), any caller reusing this function should be reminded that the underlying access-control check (if it exists elsewhere in the untouched code) must still be enforced for the new return-value code path. If no such check exists, this is a High severity IDOR allowing cross-patient document disclosure.
- **Unvalidated `$url` / path handling:** `fopen($url, "r")` uses a path apparently derived from stored document metadata; if any part of that path is influenced by user input (document naming, `from_pathname`, etc.) without normalization, this is a path traversal risk — pre-existing but relevant since this code block was modified.
- **Passphrase/encryption source:** `$passphrase = $_POST['passphrase'];` is taken directly from POST without validation — pre-existing, but the new `disable_exit` paths make it easy to retrieve content *without* ever supplying/validating a passphrase, which somewhat defeats the purpose of having passphrase-based encryption gating at all.

---

## Recommendations

1. Do not allow `$disable_exit` (or any internal/trusted-only flag) to be settable via the generic `Controller::act()` request-driven dispatch. Either rename/guard it so it can only be set by internal PHP calls (e.g., call the underlying logic through a private/protected helper method not reachable via `act()`), or explicitly strip it from any request-derived argument array.
2. Ensure the encryption (`$doEncryption`) check happens *before* any return of file content, in all three return points (local file, converted file, CouchDB).
3. Preserve/verify access-control checks for `patient_id`/`document_id` on every return path, including the new ones.
4. Ensure `document_upload_download_log()` (or equivalent audit logging) is called on every successful retrieval path, including the new early returns.
5. Use strict comparisons for boolean flags derived from request data, or better, type-cast/validate explicitly.
6. Add error handling around `fopen`/`fread`.
