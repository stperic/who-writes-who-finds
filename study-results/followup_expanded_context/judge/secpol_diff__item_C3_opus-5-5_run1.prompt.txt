# Security Review: `portal/portal_payment.php`

**Verdict: Do not merge.** The change adds a new unauthenticated path to decrypted cardholder data (`recid`) and exposes a gateway key to the browser. It also builds on, and keeps, several pre-existing critical flaws in how patient identity and payment posting are authorized.

---

## Critical

### 1. IDOR via new `recid` parameter discloses any patient's card data
- **Location:** `$recid = isset($_REQUEST['recid']) ? (int) $_REQUEST['recid'] : 0;` → `$edata = $appsql->getPortalAuditRec($recid);` → `$ccdata = json_decode(decryptStandard($edata['checksum']), true);`
- **Category:** A01 Broken Access Control
- **Problem:**
  - Any portal-logged-in patient can supply an arbitrary `recid`. The code does not check that the audit record belongs to `$_SESSION['pid']`, and does not restrict this parameter to staff.
  - The record is decrypted and rendered: cardholder name, zip, card number, expiry, CVV, transaction ID and auth code.
  - Sequential integer IDs make enumeration trivial.
  - The new display branch `if (isset($_SESSION['authUserID']) || isset($ccdata["transId"]))` prints the **full unmasked card number** to *anyone*, including patients, whenever a `transId` exists.
- **Fix:**
  - Accept `recid` only for authenticated staff.
  - For any record lookup, verify `$edata['patient_id'] == $_SESSION['pid']` when `$isPortal`.
  - Never print the full PAN based on `transId`.

### 2. Patient ID taken from request, overriding the portal session (pre-existing, relied upon)
- **Location:**
  - `$pid = isset($_REQUEST['pid']) ? $_REQUEST['pid'] : $pid;`
  - `$pid = $_REQUEST['hidden_patient_code'] > 0 ? $_REQUEST['hidden_patient_code'] : $pid;`
  - `$form_pid = $_POST['form_pid'];`
- **Category:** A01 Broken Access Control
- **Problem:**
  - A portal user's `$_SESSION['pid']` is replaced by attacker-controlled input.
  - The page then shows the other patient's name, insurance, encounter reasons, balances and pending card data (via `getPortalAudit($pid, ...)`).
  - Write operations then run against `$form_pid`.
  - The new `$isPortal` flag exists but is never used to block this.
- **Fix:** When `$isPortal` is true, force `$pid = $form_pid = $_SESSION['pid']` and ignore all request-supplied patient identifiers.

### 3. Portal patients can post payments and close encounters without paying (pre-existing, modified in this diff)
- **Location:** The whole `if ($_POST['form_save'])` block.
- **Category:** A01 Broken Access Control / A04 Insecure Design
- **Problem:**
  - Nothing requires `$_SESSION['authUserID']` before writing to `ar_session`, `ar_activity` and `payments`.
  - With `radio_type_of_payment=cash`, the code also runs `UPDATE form_encounter SET last_level_closed=4` and `UPDATE billing SET billed=1`.
  - The UI hides the "Post Payment" button from patients, but a patient can POST `form_save` directly. That lets them:
    - record arbitrary "payments" that were never charged,
    - mark encounters as closed or billed, for themselves or for any `form_pid`.
  - Amounts are server-unvalidated. Negative values pass `if ($amount = 0 + $payment)`, and `form_prepayment` is inserted raw. The "no negative payments" rule is client-side JS only.
- **Fix:**
  - Require an authenticated staff user with the appropriate ACL (e.g. `acct`) for `form_save`.
  - Validate that amounts are positive numerics on the server.
  - Tie posted payments to a verified gateway transaction.

### 4. Storage and display of full PAN and CVV (pre-existing, retained)
- **Location:**
  - `echo $ccdata["cardNumber"]`
  - `<span id="cvvpin"><?php echo text($ccdata["cardCode"]) ?>`
  - The InHouse flow posting raw card fields to `paylib.php`
- **Category:** A02 Cryptographic Failures / A04 Insecure Design
- **Problem:**
  - In the InHouse path, card number, expiry and CVV are stored (reversibly encrypted with the application key) in the portal audit table and shown to staff.
  - Storing the CVV after authorization is prohibited by PCI DSS under any circumstances.
  - Any database plus key compromise, or any IDOR (#1, #2), exposes full card data.
  - The AuthorizeNet and Stripe tokenization paths are an improvement, but the InHouse path remains the default (`paySubmit`).
- **Fix:**
  - Remove the InHouse raw-card flow, or at minimum never persist CVV.
  - Store only a token and the last 4 digits.
  - Never render the full PAN.

## High

### 5. Gateway API key exposed to every page viewer
- **Location:** `var apiKey = <?php echo json_encode($GLOBALS['gateway_api_key']); ?>;`
- **Category:** A02 Cryptographic Failures / A05 Security Misconfiguration
- **Problem:**
  - The key is emitted unconditionally to every portal and staff session, whichever gateway is configured.
  - For Stripe, the client only needs the publishable key (`publicKey`). If `gateway_api_key` holds the Stripe **secret** key, or an Authorize.Net transaction key rather than the login ID, attackers get full gateway API access: charges, refunds, customer data.
- **Fix:**
  - Emit only the values the client library actually requires: Stripe publishable key; Authorize.Net `apiLoginID` and public `clientKey`.
  - Emit them only for the active gateway.
  - Keep secret keys server-side.

### 6. Stored XSS through the card number field
- **Location:** `echo $ccdata["cardNumber"] . "</span><br>";`
- **Category:** A03 Injection (XSS)
- **Problem:**
  - `cardNumber` is patient-supplied, and the HTML `pattern` attribute is not enforced server-side.
  - It is echoed without escaping. A patient can submit `<script>…</script>` as a "card number", and it executes in a staff (billing) user's session when they review the payment.
  - That enables session riding and access to all patient records.
  - Other fields were switched to `text()` in this diff, but this one was missed.
- **Fix:** `echo text($ccdata["cardNumber"])`, and validate digits-only on the server.

### 7. No CSRF protection on state-changing requests
- **Location:**
  - `invoiceForm` POST to `portal_payment.php` (`form_save`)
  - All POSTs to `lib/paylib.php` (`portal-save`, `review-save`, AuthorizeNet, Stripe)
- **Category:** A01 Broken Access Control (CSRF)
- **Problem:** No CSRF token is generated or verified. A malicious page can make a logged-in staff member post payments, close encounters or mark billing as billed.
- **Fix:** Add and verify CSRF tokens (OpenEMR's `CsrfUtils`) on all of these requests.

## Medium

### 8. No accountable user recorded for portal-originated writes
- **Location:**
  - `user_id = $_SESSION['authUserID']` and `post_user = $_SESSION['authUserID']` in `ar_session`/`ar_activity` inserts
  - Copay path uses `$_SESSION['authId']`
  - `sqlQueryNoLog`
- **Category:** A09 Security Logging and Monitoring Failures
- **Problem:**
  - When a portal patient triggers these writes, the user fields are empty or NULL. Financial records then have no attributable actor.
  - The change also replaced a hard-coded `post_user` of `3` with session values that are empty for portal users.
  - The inconsistent use of `authId` vs `authUserID` makes the audit trail unreliable.
- **Fix:**
  - Once #3 is fixed, consistently record the staff user.
  - Log portal-originated payment events explicitly, including the patient pid.

### 9. Request body built by unencoded string concatenation
- **Location:** `let extra = "&inv_values=" + inv_values + "&extra_values=" + extra_values;` (used with `.serialize() + extra`)
- **Category:** A03 Injection (parameter injection) / A08 Data Integrity
- **Problem:** The JSON is not URL-encoded. Values containing `&` or `=` inject or override POST parameters such as `pid` or `mode` seen by `paylib.php`. This compounds #2.
- **Fix:** Wrap the values in `encodeURIComponent(...)`, or send a `FormData` or JSON body.

### 10. Race condition in `sequence_no` allocation
- **Location:** `SELECT IFNULL(MAX(sequence_no),0) + 1 ...` inside `sqlBeginTrans()`, followed by an insert.
- **Category:** A04 Insecure Design (integrity)
- **Problem:**
  - Under InnoDB's default isolation, a plain `SELECT MAX` takes no lock. Concurrent postings can compute the same sequence number, causing duplicate-key failures or lost or misattributed ledger rows.
  - Writes to `ar_session` and `payments` sit outside the transaction, so partial failures leave inconsistent financial records.
- **Fix:**
  - Use `SELECT ... FOR UPDATE` or an atomic counter.
  - Wrap the whole payment posting in one transaction.

## Low

### 11. Wrong escaping context in JavaScript strings
- **Location:**
  - `prompt("<?php echo xlt('Please enter card comfirmation authorization') ?>", ...)`
  - Various `alert("<?php echo addslashes(xl(...)) ?>")`
- **Category:** A03 Injection (XSS)
- **Problem:** HTML escaping and `addslashes` are not correct for a JS string context. Exploitable only through malicious translation strings.
- **Fix:** Use `json_encode()` (or `xlj()`), as the diff already does for `chargeMsg`.

### 12. Unescaped configuration values in HTML and JS
- **Location:** `$GLOBALS['assets_static_relative']`, `$GLOBALS['webroot']`, `$v_js_includes` echoed raw into `src`/`action` attributes and JS strings.
- **Category:** A03 Injection / A05 Security Misconfiguration
- **Problem:** These are admin-controlled values, so this is defense in depth only.
- **Fix:** Wrap them with `attr()` or `js_escape()`.

### 13. Third-party payment scripts not shown or controlled
- **Location:** `Accept.dispatchData(...)` and `Stripe(publicKey)` are called, but no script includes appear in this diff.
- **Category:** A08 Software and Data Integrity Failures / A06 Vulnerable and Outdated Components
- **Problem:** The gateway libraries' load location and integrity are not visible in this change.
- **Fix:**
  - Confirm they load only from the official gateway origins (`js.stripe.com`, `js.authorize.net`) over HTTPS.
  - Do not self-host or proxy them (Stripe requires direct loading).
  - Add a CSP restricting script sources.
