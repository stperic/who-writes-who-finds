## Review: FhirCareTeamService changes

### 1. Patient-context binding is not enforced (High)

`FhirCareTeamService` now defines `getPatientContextSearchField()` and exposes a `patient` search parameter, but it does not implement `IPatientCompartmentResourceService`. The base class only applies the patient restriction when that interface is present:

- `FhirServiceBase::createOpenEMRSearchParameters()` adds the `puuidBind` constraint only if `$this instanceof IPatientCompartmentResourceService`.
- `FhirServiceBase::getOne()` adds the patient field only under the same check.
- `FhirServiceBase::getAll()` calls `searchForOpenEMRRecords($oeSearchParameters)` without passing `$puuidBind`, so the subclass's `$puuidBind` parameter is always null.

The removal of the custom `getOne()` makes this worse. The old override called `careTeamService->getOne($id, $puuidBind)` directly, so the bind was applied. Now a patient-scoped request (e.g., a patient-facing SMART/API token) can read any patient's CareTeam by ID or by search. This is a data-exposure regression. Fix: add `IPatientCompartmentResourceService` to the implements list, or otherwise ensure the bind is applied.

### 2. Dependency on an unchanged CareTeamService return shape (High)

The changed `searchForOpenEMRRecords` now passes `true` instead of `false` to `getAll`. The new `createParseOpenEMRRecord` code assumes a substantially different shape:

- `$dataRecord['providers']` is a list of lists, with `end()` taken on each inner list.
- `$dataRecord['facilities']` entries are arrays with `uuid` and `facility_taxonomy` keys.
- Each provider record has `role_code`, `role_title`, `facility_uuid`, and `provider_uuid`.
- `$dataRecord['status']` and `puuid` must be present.

None of this is in the diff, and the flag's meaning is not shown. If `CareTeamService` does not produce this shape, you will get undefined-index notices, null UUIDs, or invalid references. The PR should include or reference the matching service change and tests.

### 3. Fragile handling of empty provider groups (Medium)

`$dataRecordProvider = end($dataRecordProviderList);` returns `false` for an empty array. The following accesses then read from `false`, producing null values and possibly a participant with `Practitioner/` and an empty member. Add a guard that skips empty groups.

### 4. Possible undefined index on `status` and `role_title` (Medium)

- `$dataRecord['status']` is read without `isset`. If the query does not select `status`, this raises a notice and the default path is never clearly exercised.
- `xlt($dataRecordProvider['role_title'])` is used as a fallback. If `role_title` is null or missing, this passes null to a translation function.

### 5. Loose comparison in status validation (Low)

`array_search(...) !== false` uses loose comparison. Use `in_array($status, self::CARE_TEAM_STATII, true)` for clarity and strictness.

### 6. Facility description handling (Low)

When `lookup_code_descriptions` returns empty, the code explicitly sets `$description = null`. This is inconsistent with the provider branch, which falls back to a translated title. The TODO about column size is also unresolved in a merged change.

### 7. Maintainability (Low)

- `USCGI_PROFILE_URI` is a public, non-typed constant, unlike the `private const` style used just above it. The name also looks like a typo for US Core (`USCGI` vs `USCORE`/`USCG`). Confirm against the actual profile constant convention used elsewhere.
- The participant role-building code is duplicated across the provider and facility branches. A helper would reduce the risk of divergence.
- Stray blank lines and the odd `, self::...` line break in `CARE_TEAM_STATII` should be cleaned up.
- The `getOne()` removal is a behavioral change that is not called out in the PR description.
- `createProvenanceResource` now throws `BadMethodCallException` on wrong input, while the base class's `getAll` calls it with a parsed resource. This works, but the contract should be documented.

### Summary

The most important problem is #1: the CareTeam resource lacks the patient-compartment interface, so patient-bound requests are not restricted. #2 is a cross-file dependency that cannot be verified from this diff. The rest are robustness and style issues. I would not merge until #1 and #2 are resolved.
