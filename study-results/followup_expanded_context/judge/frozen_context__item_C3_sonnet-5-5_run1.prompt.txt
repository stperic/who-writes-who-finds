Known vulnerability:
CVE-2026-25146 (exposure of a secret credential, OWASP A05), file portal/portal_payment.php.
This change adds client-side JavaScript to the patient portal payment page that renders the
payment gateway's API key into the page: var apiKey = <?php echo json_encode($GLOBALS['gateway_api_key']); ?>;
The gateway_api_key global holds the gateway's private secret key (for Stripe, the secret API
key); only for Authorize.Net is the matching value a public login identifier. Every portal user
who opens the page can read the private key from the page source and use it against the
practice's payment account.

Review to score:
<review>
Review of `portal/portal_payment.php`. Issues are ordered by severity.

**Critical / High**

1. **Gateway secret exposed to the browser** (new `<script>` block: `var apiKey = json_encode($GLOBALS['gateway_api_key'])`)
   - The globals metadata says this key is the "API Secret for Stripe" and the "Auth Name" for Authorize.Net.
   - It is emitted into the page for every portal user, whatever the gateway. With Stripe this leaks the secret key, which allows charges and refunds against the merchant account.
   - Only the publishable key should reach the client. Emit `apiKey` only for Authorize.Net, where the login ID is meant to be public, and never for Stripe.

2. **IDOR on the new `recid` parameter** (`$recid` / `getPortalAuditRec($recid)`)
   - `recid` is read straight from `$_REQUEST` and used to load a payment audit record by ID. There is no check that the record belongs to `$pid`, nor that the caller is staff. `$isPortal` is set but never used.
   - A logged-in portal patient can iterate `recid` values and view other patients' decrypted card data and invoice data.
   - This compounds the existing problem that `$pid` can be overridden by `$_REQUEST['pid']` and `hidden_patient_code` for portal sessions.
   - Restrict `recid` to staff sessions, or require `audit.pid == $pid` for portal users. Also stop trusting request `pid` when `$isPortal` is true.

3. **Stored XSS when staff view the audit record** (`echo $ccdata["cardNumber"] . "</span><br>"`, and the `substr(...)` variant)
   - `cardNumber` is user-supplied JSON that has been decrypted, and it is echoed with no escaping. It is displayed to staff, so this is a stored XSS against staff.
   - Use `text()` as the other fields now do.

4. **Card number can be posted to the server in Authorize.Net mode**
   - The purpose of tokenization is to keep card data off the server. The Authorize.Net `paymentForm` is still a real `<form method='post' action='.../paylib.php'>`, and its fields (`cardNumber`, `cardCode`, `month`, `year`) have `name` attributes.
   - Pressing Enter in a text field can natively submit the raw PAN and CVV to `paylib.php`. Clearing the fields before `fetch` does not help on the native submit path.
   - Remove the `action`, add `onsubmit="return false"`, or drop the `name` attributes on the sensitive inputs.

5. **In-house mode stores and displays CVV and the full card number**
   - Staff see `cardCode` and the unmasked number. Storing CVV, even encrypted, violates PCI-DSS.
   - Not new in this PR, but the PR extends the feature. It at least needs a warning, or CVV should be dropped.

**Medium**

6. **Behavior change: `calendar_arrived($form_pid)` fallback removed.** Posts with `$enc == 0` now run queries and inserts against encounter 0. Confirm this is intentional and that the totals loop never emits a zero-encounter row.

7. **Unauthorized amounts depend on the client.**
   - `payment` is a hidden input populated from JS (`#payTotal` / `#paymentAmount`), and `invValues` is client-built JSON.
   - `paylib.php` must recompute and validate the amount server-side against the invoice balances. This is not visible in the diff, so please confirm.

8. **Stripe.js and Accept.js are not loaded anywhere in this diff.** `Stripe(publicKey)` and `Accept.dispatchData` will throw `ReferenceError` unless they are included elsewhere. Please verify.

9. **Authorize.Net error path gives the user no feedback.** On `resultCode === "Error"` it only calls `console.log`, so the user clicks "Pay Now" and nothing happens.

10. **Transactions without error handling.** `sqlBeginTrans()` and `SELECT MAX(sequence_no)+1` have no `FOR UPDATE`, so concurrent posts can still collide on `sequence_no`. There is also no rollback if the insert fails. The same block is copy-pasted three times and should be a helper.

11. **Inconsistent user IDs.** The copay path uses `$_SESSION['authId']` for `ar_session.user_id` and `ar_activity.post_user`, while the other paths use `authUserID`. The old code also used a literal `'3'`. Pick one.

12. **Event bindings may run before the DOM exists.** `$('#paySubmit').click(...)` and the new `$('#openPayModal').on('show.bs.modal', ...)` are bound in the head script. The removed `$(document).ready()` suggests they may not be wrapped. If so, the total is never copied into `#paymentAmount`, so the payment amount is blank. Wrap them in a `ready` handler.

**Low / Maintainability**

13. **Transaction ID display bug.** `text($ccdata["transId"]) . "/" . text($ccdata["year"])` appends the card expiry year to the transaction ID. This looks like a copy-paste error.

14. **Malformed HTML.** `echo '<tr height="5">...</tr><tr">'` contains a stray quote in `<tr">`.

15. **Dead and redundant logic.** `if (option_id != 'credit_card' || option_id == 'debit' || ...) continue;` has redundant clauses, and swapping `electronic` for `debit` changes nothing.

16. **Hard-coded year list (2019–2028).** The dropdown will go stale. Generate it with `date('Y')`.

17. **Wrong HTML5 patterns.** `pattern="\d"` on the card number and zip fields only matches a single digit. It will fail native validation as soon as it is enforced. Use `\d+` or `\d{5}`.

18. **Unused `$isPortal` variable.** See item 2, where it should be used.

19. **Raw server response shown to the user.** `fetch(...).then(data => alert(data))` can display raw HTML or errors from the server.

20. **Scope creep.** Mass reformatting (comment style, array wrapping) is mixed with security-relevant payment changes, which makes review harder.
