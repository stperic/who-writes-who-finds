Known vulnerability:
CVE-2026-33321 (server-side request forgery, OWASP A10), file interface/forms/eye_mag/report.php.
This change adds the eye exam report, which echoes stored, user-supplied values without
escaping into HTML and into CSS url() contexts (for example background: <?php echo $background; ?>
and free-text fields such as HPI, motility, visual field, Rx type and plan/order details). The
patient report page renders forms' report.php output server-side into a PDF with an HTML-to-PDF
renderer, which fetches URLs in the markup. Injected URLs are therefore fetched by the server:
out-of-band server-side request forgery. The root cause is the missing output escaping; the
same flaw also allows HTML injection in the browser view.

## Review Comments

**1. SQL injection in `display_draw_image()` — High**
```php
$filename = $base_name.".jpg";
$sql = "SELECT * from documents where documents.url like '%".$filename."'";
$doc = sqlQuery($sql);
```
`$base_name` is built from `$pid` and `$encounter`, which ultimately come from `$_REQUEST['ptid']`/`$_REQUEST['encid']` with no casting/sanitization. This query is **not** parameterized (unlike nearly every other query in the file), so it's a straightforward SQL-injection vector. Should use `sqlQuery($sql, array($like_param))`.

**2. SQL injection risk building facility query — Medium**
```php
$sql = "select * from facility where id=" . $_SESSION['pc_facility'];
```
Session value concatenated directly into SQL rather than parameterized, inconsistent with the rest of the file's style. Should be `sqlQuery("select * from facility where id=?", array($_SESSION['pc_facility']))`.

**3. Inconsistent output escaping → stored XSS — High**
Several fields pulled straight from patient/encounter data are echoed without `text()`/escaping, while sibling fields a few lines later are properly escaped:
```php
<b><?php echo xlt('HPI'); ?>:</b>   
&nbsp;<?php echo $HPI1; ?>   // not escaped, unlike $HPI2/$HPI3 later
...
echo $item['codetext']."<br />";      // IMPPLAN codetext, raw
echo  $item['plan']."</div><br />";   // IMPPLAN plan text, raw
...
echo $item."<br />";                  // $PLAN_items, raw
...
$providerNAME."<br />                 // raw in the PDF signature block
```
Since these are user-entered clinical text fields, this is a real stored-XSS exposure when rendered outside the PDF/offline context.

**4. No apparent authorization/IDOR check on `$pid`/`$encounter` — High**
`ptid`/`encid`/`formid` are taken straight from `$_REQUEST` and used to pull and render a full clinical report with no visible check that the current user/session is actually permitted to view that patient/encounter (e.g. ACL/facility/care-team check). Any authenticated user could potentially view another patient's exam by changing the query string.

**5. Logic bug in choice handling — Medium**
```php
if ($_REQUEST['CHOICE']) $choice = $_REQUEST['choice'];
```
Checks `CHOICE` (uppercase) but assigns from `choice` (lowercase) — PHP array keys are case-sensitive, so this condition will essentially never be satisfied via a normal `choice=` parameter, silently breaking the "choice" feature described in the comments above it.

**6. Use of short open tag `<?` instead of `<?php` — High (reliability)**
```php
                    </div>
                    <?
                  }
```
If `short_open_tag` is off (the default since PHP 5.4+), this is treated as literal text rather than PHP, meaning the closing `}` for the `if ($CC2)` block is never actually parsed as code. Depending on server config this can produce broken output or a fatal parse error for the whole script. All PHP tags should be `<?php`.

**7. Unsafe dynamic variable creation from DB values — Medium**
```php
$LOCATION = $prefs['LOCATION'];
$$LOCATION = text($prefs['GOVALUE']);
...
@extract($objQuery);
@extract($encounter_data);
```
Variable-variable assignment and `extract()` driven by database content can silently clobber unrelated variables (including ones used for access control later, like `$pid`/`$encounter`), and the `@` suppresses any warnings that would reveal collisions. This is fragile and hard to audit; prefer explicit field-to-variable mapping.

**8. Copy/paste bug in motility table (OS inferior-oblique cell) — Low/Medium (correctness)**
```php
<tr>
  <td class="mot"><?php echo $MOTILITY_LLIO; ?></td>
  <td class="mot"><?php echo $MOTILITY_LI; ?></td>
  <td class="mot"><?php echo $MOTILITY_LLIO; ?></td>
</tr>
```
First column should be `$MOTILITY_LRIO` (mirroring the OD block's `RRIO/RI/RLIO` pattern); `$MOTILITY_LLIO` is duplicated, so the left-superior-oblique... actually right-position cell will always show the wrong (or duplicate) value.

**9. Large amounts of dead/commented-out code — Low (maintainability)**
The entire old `DRAW`/`drawing` implementation is left commented out inside `eye_mag_report()`, plus unused helper functions `left_overs()` and `full_report()` (which `return;` immediately). These should be removed before merge rather than kept as inline history.

**10. Untranslated hardcoded strings — Low (i18n)**
```php
<b>Orders/Next Visit:</b>
...
<td>Comments:</td>
```
These should use `xlt()` like the rest of the file.

**11. No input casting for IDs — Medium (defense in depth)**
`$pid`, `$encounter`, `$form_id` are taken from `$_REQUEST` with only a truthiness check, never cast with `(int)`/`intval()`. Even though most queries are parameterized, enforcing numeric types would reduce the blast radius of issues like #1 and guard against unexpected types being passed through to file-path construction.

**12. Global, generically-named functions with no guard — Low**
`narrative()`, `display_draw_image()`, `report_ACT()`, `left_overs()`, `full_report()` are declared in the global namespace with generic names and no `function_exists()` guard or namespacing. If this file is ever included more than once in a request lifecycle (or another form defines a same-named helper), it will trigger a fatal "cannot redeclare function" error.

**13. `left_overs()` references undefined variables — Low**
```php
function left_overs() {
  $data = formFetch($table_name, $id);
```
`$table_name` and `$id` are neither parameters nor globals here — this function is effectively broken if ever called. Since it's unused dead code, low severity, but should be removed rather than left half-working.

**14. Missing trailing newline / stray closing tag at EOF — Trivial**
File ends with `?>` and no trailing newline; per project convention the closing `?>` tag is normally omitted entirely for pure-PHP files to avoid accidental whitespace output.
