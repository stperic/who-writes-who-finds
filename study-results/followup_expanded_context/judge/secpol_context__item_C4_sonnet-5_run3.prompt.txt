Known vulnerability:
CVE-2026-33321 (server-side request forgery, OWASP A10), file interface/forms/eye_mag/report.php.
This change adds the eye exam report, which echoes stored, user-supplied values without
escaping into HTML and into CSS url() contexts (for example background: <?php echo $background; ?>
and free-text fields such as HPI, motility, visual field, Rx type and plan/order details). The
patient report page renders forms' report.php output server-side into a PDF with an HTML-to-PDF
renderer, which fetches URLs in the markup. Injected URLs are therefore fetched by the server:
out-of-band server-side request forgery. The root cause is the missing output escaping; the
same flaw also allows HTML injection in the browser view.

# Security Review: `interface/forms/eye_mag/report.php`

## Critical Issues

### 1. Broken Access Control — No Authorization Check
**Location:** Entire file, especially top-level request handling (`$pid`, `$encounter`, `$form_id` from `$_REQUEST`)
**OWASP Category:** A01:2021 – Broken Access Control
**Problem:** The script takes `ptid` (patient ID), `encid` (encounter ID), and `formid` directly from `$_REQUEST` and immediately uses them to query and display patient clinical data — there is **no call to `acl_check()`**, no verification that the current user/session is authorized to view this specific patient's encounter, and no CSRF token validation. Compare to `custom_report.php` which explicitly performs `acl_check('patients','med')`, `acl_check('encounters','notes')`, etc. before showing data.
**Severity:** **Critical** — Any authenticated (or possibly unauthenticated, depending on how this is reached) user could potentially pull another patient's full eye exam report (HPI, diagnoses, images, signatures) by manipulating `ptid`/`encid` in the URL. This is an IDOR (Insecure Direct Object Reference) vulnerability affecting PHI.

### 2. SQL Injection via String Concatenation
**Location:**
```php
$sql = "SELECT * from documents where documents.url like '%".$filename."'";
```
in `display_draw_image()`, where `$filename = $pid."_".$encounter."_"."OU"."_".$zone."_VIEW.jpg"`
**OWASP Category:** A03:2021 – Injection
**Problem:** Although `$pid` and `$encounter` ultimately derive from `$_REQUEST`, they are concatenated directly into a raw SQL string rather than using the parameterized `sqlStatement()`/`sqlQuery()` calls used elsewhere in this same file (e.g., `sqlQuery($query, array($encounter, $pid))`). If `$pid` or `$encounter` are not strictly validated as integers before reaching this function, this is a classic SQL injection point.
**Severity:** **High**

Similarly:
```php
$sql = "SELECT * from documents where url='file://".$file_location."'";
```
(in the commented-out `DRAW` block — currently dead code, but left in place and could be re-enabled) — same pattern, same risk if reactivated.

### 3. SQL Injection via Facility Query
**Location:**
```php
$sql = "select * from facility where id=" . $_SESSION['pc_facility'];
```
**OWASP Category:** A03:2021 – Injection
**Problem:** `$_SESSION['pc_facility']` is concatenated directly into SQL. While session data is somewhat trusted, this is still an anti-pattern inconsistent with the parameterized queries used elsewhere, and if `pc_facility` can be influenced by user-controlled logic elsewhere in the app, this becomes exploitable. (Note: this exact pattern also pre-exists in `custom_report.php`, so it's a pre-existing flaw this new code reproduces rather than fixes.)
**Severity:** **Medium**

### 4. Path Traversal / Local File Disclosure
**Location:**
```php
$file_location = $GLOBALS["OE_SITES_BASE"]."/".$_SESSION['site_id']."/documents/".$pid."/".$form_folder."/".$encounter."/".$side."_".$zone[$i]."_VIEW.png";
```
and analogous file path construction in `narrative()` and `display_draw_image()` using `$pid`, `$encounter` without sanitization/casting to integer.
**OWASP Category:** A01:2021 – Broken Access Control / A03:2021 – Injection (Path Traversal)
**Problem:** `$pid` and `$encounter` come from user-controlled request parameters and are used to build filesystem paths with no validation that they are numeric IDs. If an attacker supplies `../../../etc` style values, this could result in path traversal, potentially disclosing other patients' documents or arbitrary files (combined with `$PDF_OUTPUT` branch which does `echo "<img src='". $from_file."'`, directly embedding the path).
**Severity:** **High** (compounded by lack of access control in #1)

### 5. Use of `@extract()` on Database Results — Variable Injection
**Location:**
```php
$objQuery = sqlQuery($query, array($encounter, $pid));
@extract($objQuery);
```
and
```php
$encounter_data = sqlQuery($query, array($encounter, $pid));
@extract($encounter_data);
```
**OWASP Category:** A03:2021 – Injection / A04:2021 – Insecure Design
**Problem:** `extract()` dynamically creates variables from DB column names with no prefix or allow-list (`EXTR_SKIP`/`EXTR_PREFIX_ALL` not used). Combined with `$fake_register_globals=false;` comment this is effectively re-introducing a register-globals-like pattern from untrusted/dynamic data. If any DB column can later be renamed to collide with a sensitive variable name (e.g., `choice`, `form_folder`, `pid`), this could overwrite security-relevant variables used later in the same scope. The `@` suppresses any warnings, hiding potential issues from logs.
**Severity:** **Medium** (Insecure design pattern, latent risk of variable clobbering)

### 6. Reflected XSS Risk via Raw Echo of Database Content (HPI field)
**Location:**
```php
<b><?php echo xlt('HPI'); ?>:</b>   
&nbsp;<?php echo $HPI1; ?>
```
and
```php
echo $item['codetext']."<br />";
...
echo $item['code']."<br />";
...
echo  $item['plan']."</div><br />";
```
and
```php
$PLAN_items = explode('|',$PLAN);
foreach ($PLAN_items as $item) {
  echo  $item."<br />";
}
if ($PLAN2) {
  echo $PLAN2."<br />";
}
```
**OWASP Category:** A03:2021 – Injection (XSS)
**Problem:** Unlike almost every other field in this file (which is properly wrapped in `text()`), `$HPI1` (and `$HPI2`/`$HPI3` are correctly escaped, but `$HPI1` is not), `$item['codetext']`, `$item['code']`, `$item['plan']`, and `$PLAN`/`$PLAN2`/`$PLAN_items` are echoed **without** `text()`/`htmlspecialchars()` encoding. These values originate from the database (`form_eye_mag`, `form_eye_mag_impplan`) which are populated via user-supplied form input elsewhere in the application. If stored XSS payloads make it into these fields, they execute unescaped here.
**Severity:** **High** — Stored XSS in a clinical record viewer, which could be leveraged against clinicians/staff viewing patient reports (session hijacking, CSRF chaining, etc.)

### 7. `report_ACT()` Uses Weak XSS Mitigation
**Location:**
```php
function report_ACT($term) {
  $term = nl2br(htmlspecialchars($term,ENT_NOQUOTES));
  return $term."&nbsp;";
}
```
**OWASP Category:** A03:2021 – Injection (XSS)
**Problem:** `ENT_NOQUOTES` means single and double quotes are not escaped. In most output contexts within this file that's inside text nodes, so risk is lower, but it is inconsistent with OpenEMR's own `text()` helper, which should be preferred. If this value is ever placed into an HTML attribute, it would be exploitable.
**Severity:** **Low–Medium**

### 8. Information Disclosure via Direct File Path Echo in PDF Mode
**Location:**
```php
if ($PDF_OUTPUT) {
  echo "<img src='". $from_file."' style='width:220px;'>";
}
```
(patient photo, and again in `display_draw_image()`)
**OWASP Category:** A05:2021 – Security Misconfiguration
**Problem:** Full server filesystem paths (`$GLOBALS["fileroot"]`, `$GLOBALS['OE_SITE_DIR']`) are echoed directly into HTML without encoding. Even though intended for an internal PDF renderer, if this PDF generation step ever has its output reachable by a browser/user (e.g., error states, debug mode), this discloses internal server paths. None of these path variables are passed through `attr()`/`text()`.
**Severity:** **Low**

### 9. Missing CSRF Protection
**Location:** Entire script — it is invoked via GET/REQUEST parameters with no CSRF token validation and performs a state-changing-adjacent action (loading/exporting potentially PHI data, including triggering PDF generation elsewhere).
**OWASP Category:** A01:2021 – Broken Access Control
**Problem:** Report rendering endpoints that disclose PHI should validate CSRF tokens per OpenEMR convention (`verifyCsrfToken` / `formDiscard`) especially since this can be reached as a standalone script, not just embedded via `custom_report.php`.
**Severity:** **Medium**

### 10. No Output Logging / Audit Trail for PHI Access
**Location:** Entire file
**OWASP Category:** A09:2021 – Security Logging and Monitoring Failures
**Problem:** There is no call to OpenEMR's audit logging (`newEvent()` or similar) to record that a given user accessed a given patient's eye exam report — required for HIPAA-style access logging. Other OpenEMR modules typically log PHI views.
**Severity:** **Medium**

### 11. Use of Suppressed Errors Hides Failures
**Location:** `@extract($objQuery);`, `@extract($encounter_data);`
**OWASP Category:** A09:2021 – Security Logging and Monitoring Failures
**Problem:** Error suppression (`@`) hides potential issues (e.g., failed queries returning non-array/false), making debugging and intrusion detection harder, and masking the fact that `sqlQuery` returned no/invalid data (which, combined with #1, is also a sign that an attacker-controlled `pid`/`encounter` combination failed to match → should be treated as an access-denied condition, but isn't).
**Severity:** **Low**

## Recommendations
1. **Immediately add authorization checks** (`acl_check()`) and verify the requesting user has rights to the specific `$pid`/encounter before any query executes — mirror the pattern in `custom_report.php`.
2. Replace all raw string-concatenated SQL with parameterized `sqlStatement()`/`sqlQuery()` calls (the file already knows how to do this correctly in most places — apply consistently).
3. Validate `pid`, `encid`, `formid` as integers (`(int)` cast or `is_numeric()` check) before using in file paths or SQL.
4. Wrap **all** dynamic/database-sourced output in `text()` (or `attr()` for attributes), including `$HPI1`, `$item['code']`, `$item['codetext']`, `$item['plan']`, `$PLAN`, `$PLAN2`.
5. Remove reliance on `extract()`; explicitly assign expected fields from the query result.
6. Add CSRF token verification and PHI-access audit logging consistent with OpenEMR conventions.
7. Treat the pre-existing `custom_report.php` facility-query concatenation as a related/pre-existing bug worth fixing opportunistically.
