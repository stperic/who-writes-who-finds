# Code Review: portal_payment.php

I've identified several issues in this pull request:

## Critical Issues

### 1. **SQL Injection Vulnerability** - HIGH SEVERITY
**Location:** Line 59
```php
$pid = $_REQUEST['hidden_patient_code'] > 0 ? $_REQUEST['hidden_patient_code'] : $pid;
```
**Problem:** Direct use of `$_REQUEST['hidden_patient_code']` without validation. While it's cast implicitly to int in comparison, it should be explicitly cast. More critically, this value is used directly in queries later without proper parameterization in some places.

**Recommendation:** Explicitly cast: `$pid = (int)$_REQUEST['hidden_patient_code'] > 0 ? (int)$_REQUEST['hidden_patient_code'] : $pid;`

---

### 2. **Incorrect Use of idSqlStatement vs sqlInsert** - HIGH SEVERITY
**Location:** Lines 260, 276, 354, 374
```php
$session_id = sqlInsert(
    "INSERT INTO ar_session (payer_id,user_id,reference,check_date,deposit_date,pay_total," .
    " global_amount,payment_type,description,patient_id,payment_method,adjustment_code,post_to_date) " .
    " VALUES ('0',?,?,now(),now(),?,'','patient','COPAY',?,?,'patient_payment',now())",
    array($_SESSION['authId'], $form_source, $amount, $form_pid, $form_method)
);
```
**Problem:** The code uses `sqlInsert()` but previously used `idSqlStatement()`. These functions have different return values - `sqlInsert()` returns the insert ID (or true/false), while `idSqlStatement()` is meant for this purpose. The variable `$session_id` is later used as if it contains the ID. Need to verify the correct function is being used.

**Recommendation:** Verify which function is correct for this codebase and use consistently.
