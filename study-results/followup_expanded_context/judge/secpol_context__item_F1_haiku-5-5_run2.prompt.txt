## Security Review: Controller dispatch refactor

The change removes the old regex sanitization of controller and action names and replaces it with a whitelist plus a generic dispatcher. The whitelist blocks arbitrary class and file loading, which is a real improvement. However, I found several issues, the most important being an ACL coverage gap and the removal of input sanitization on the action name.

---

### 1. Broken access control: sub-controllers reachable without their parent's ACL
- **Location:** `Controller::VALID_CONTROLLERS`, `CONTROLLER_ACL_MAP`, `Controller::dispatch()` (ACL call at `checkControllerAcl($controllerParam)`)
- **Category:** A01:2021 Broken Access Control
- **Problem:** `pharmacy`, `insurance_company`, `insurance_numbers`, `document_category`, `x12_partner`, and `hl7` are all whitelisted as top-level controllers. `CONTROLLER_ACL_MAP` covers only `practice_settings` and `prescription`. The `admin/practice` check for these sub-controllers lives only in `C_PracticeSettings::__construct()`. Because `dispatch()` accepts `controller=pharmacy` directly from `$_GET`, a user without `admin/practice` can call these controllers directly and skip the parent check. The same applies to `document` and `hl7`, which depend entirely on each controller's own ACL code. This refactor rewrote the ACL logic and kept the gap. The diff does not show `C_Pharmacy`, `C_InsuranceCompany`, `C_Document`, and the others, so their internal checks cannot be verified here.
- **Severity:** High (confirm each target controller enforces its own ACL; if not, Critical for patient documents and admin data)

### 2. Reflected XSS risk via unsanitized action name in exception message
- **Location:** `Controller::dispatch()`: `throw new NotFoundHttpException("Action '$action' does not exist on controller: $className");`
- **Category:** A03:2021 Injection (XSS)
- **Problem:** The old code stripped non-alphanumeric characters from the action name (`preg_replace("/[^A-Za-z0-9_]/", "", ...)`). The new code uses `$params['action']` raw, so the value is attacker-controlled and unfiltered when it appears in the exception message. If the global exception handler renders this message as HTML without escaping, an attacker can inject markup via `controller.php?controller=document&action=<script>...`. The handler is not in the diff, so exploitability depends on it. Escaping at the throw site or restoring the character filter closes the gap.
- **Severity:** Medium (High if the error page renders messages unescaped)

### 3. Missing `method_exists` check and unconditional action call in process mode
- **Location:** `Controller::dispatch()`:
  ```php
  if ($isProcessing && is_callable([$controllerObj, $processMethod])) { ... }
  if ($isProcessing || is_callable([$controllerObj, $actionMethod])) {
      $output .= $callMethod($actionMethod);
  ```
- **Category:** A05:2021 Security Misconfiguration / A04:2021 Insecure Design
- **Problem:** The original code required both `is_callable()` and `method_exists()`. The source comment says `is_callable()` alone is unreliable because Smarty's `__call` makes it always true. The new code drops `method_exists()`. Also, when `$isProcessing` is true, the action method is called without any existence check. Consequences: an attacker can trigger undefined-method errors or fatal errors that may leak internals, and if any class in the hierarchy implements `__call`, `is_callable()` returns true for any `<name>_action` string and routes it there.
- **Severity:** Medium

### 4. GET-triggered state-changing processing (CSRF-style exposure)
- **Location:** `Controller::dispatch()`: `if (isset($params['process'])) { ... $_POST['process'] = "true"; }`
- **Category:** A01:2021 Broken Access Control (CSRF)
- **Problem:** Any GET request with `process` in the query string is converted to POST processing, which runs `*_action_process` handlers. A cross-site link or image can therefore trigger state-changing operations without a POST or a CSRF token, unless each `_process` handler validates a CSRF token itself. The logic is inherited, but the refactor makes it more central and also has `dispatch()` write to `$_POST` based on `$params` (not `$_GET`), so nested dispatch calls have side effects on global request state.
- **Severity:** Medium (depends on per-controller CSRF checks)

### 5. Attacker-controlled positional argument injection, including arrays
- **Location:** `Controller::dispatch()`: `$args[$key] = ...;` then `$controllerObj->$method(...array_values($args));`
- **Category:** A03:2021 Injection / A04:2021 Insecure Design
- **Problem:** Every query parameter not in the reserved list is passed positionally in URL order, so the attacker chooses which value lands in which action parameter. Values are not normalized, so `?...&x[]=1` passes an array. Typed parameters then throw `TypeError`, which can leak paths or cause errors in handlers that do not validate input. The old code had the same URL-order coupling, but the regex filter on argument names is gone.
- **Severity:** Low

### 6. Behavior regression in `act()` when the second key is `action`
- **Location:** `Controller::act()`: `$positionalAction = (string) ($keys[1] ?? 'default');`
- **Category:** Functional correctness (not a direct vulnerability)
- **Problem:** For `controller.php?practice_settings&action=list`, the positional action becomes `action`, so the explicit `action` value is dropped and dispatch calls `action_action`. This is not a security flaw but can break routing and is worth a test.
- **Severity:** Informational

---

### Items reviewed without finding issues
- `C_PracticeSettings.class.php`: `attr($_SERVER['QUERY_STRING'])` escapes the value before it is placed in `FORM_ACTION`, so there is no XSS there. The constructor ACL check still runs for `practice_settings`. The sub-action wrappers pass user input only as dispatch parameters, not into SQL or shell calls.
- Controller file loading: the whitelist prevents path traversal and arbitrary `include`, and this is a clear improvement over the previous `preg_replace` approach.

### Recommended actions before merge
1. Verify that every whitelisted controller enforces its own ACL, or add `CONTROLLER_ACL_MAP` entries for all sub-controllers of `practice_settings`.
2. Escape or filter the action name in the exception message, or restore the `[A-Za-z0-9_]` filter.
3. Restore `method_exists()` and check callability for the action method in process mode.
4. Require a POST and a CSRF token for `_process` handling, and do not accept `process` from the query string.
5. Reject non-scalar parameter values before spreading them into action calls.
