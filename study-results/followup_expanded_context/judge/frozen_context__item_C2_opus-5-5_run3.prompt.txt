Known vulnerability:
CVE-2026-24487 (broken access control / cross-patient data exposure, OWASP A01), file
src/Services/FHIR/FhirCareTeamService.php. This change rewrites the FHIR CareTeam service: it
removes the service's own getOne() override that scoped results to the requested patient, adds
getPatientContextSearchField(), and implements IResourceUSCIGProfileService but not
IPatientCompartmentResourceService. FhirServiceBase::getAll() applies patient-context filtering
only when the service is an instance of IPatientCompartmentResourceService, so for
patient-scoped API access (for example a SMART patient-context token) CareTeam requests are no
longer filtered by patient and return care teams for every patient in the system.

## Review: `FhirCareTeamService.php`

### 1. Patient-bound access control is lost — **Critical (security)**

**Location:** removal of `getOne()` override; class declaration `implements IResourceUSCIGProfileService`

The old `getOne()` passed `$puuidBind` to `CareTeamService::getOne()`, which limited results to the bound patient. That override is now deleted, so calls fall through to `FhirServiceBase::getOne()`.

The base class only adds the patient restriction when the service implements `IPatientCompartmentResourceService`. It does this in two places:

- `if (isset($puuidBind) && $this instanceof IPatientCompartmentResourceService)` in `getOne()`
- `if (!empty($puuidBind) && $this instanceof IPatientCompartmentResourceService)` in `createOpenEMRSearchParameters()`

This class does not implement that interface. It defines `getPatientContextSearchField()`, but nothing calls it. `searchForOpenEMRRecords()` also still accepts `$puuidBind`, but the base `getAll()` never passes it.

**Result:** in a patient-scoped context (patient portal, SMART `patient/*` scopes), both of these are now unrestricted:

- `GET /CareTeam/{id}` returns any patient's care team.
- `GET /CareTeam` returns all patients' care teams.

This is a PHI disclosure.

**Fix:** add `IPatientCompartmentResourceService` to the `implements` list. Add a test that a patient-bound request cannot read another patient's care team.

### 2. `patient` reference search has no URL resolver — **Medium**

**Location:** `loadSearchParameters()` / `__construct()`

`patient` is declared as a `REFERENCE` search field. The base class says reference fields **must** have a `FhirUrlResolver`, but the constructor calls `parent::__construct()` without `$fhirApiURL`.

Searching `?patient=Patient/xyz` (or full URLs), or the patient binding from fix #1, may fail or mis-parse. Check how other US Core services pass the API URL, and do the same here.

### 3. `xlt()` used for data values in JSON output — **Medium**

**Location:** `setDisplay(xlt("Unknown"))` (twice), and `$description = xlt($dataRecordProvider['role_title'])`

`xlt()` translates **and** HTML-escapes its output, which is meant for HTML templates. In a FHIR JSON payload this corrupts values. For example, `&` becomes `&amp;` in a role title.

**Fix:** use `xl()`.

### 4. Comment says "first facility" but code takes the last — **Low/Medium**

**Location:** `$dataRecordProvider = end($dataRecordProviderList);`

The comment says "we are only going to grab the first facility", but `end()` returns the **last** element.

**Fix:** either use `reset()` or `$list[0]`, or correct the comment.

If the list is empty, `end()` returns `false`. The code then reads `$dataRecordProvider['role_code']` and `['provider_uuid']` from `false`. That emits notices and produces a participant with an empty `member` reference. Guard with `if (empty($dataRecordProviderList)) continue;`.

### 5. Loose and unguarded status check — **Low**

**Location:** `array_search($dataRecord['status'], self::CARE_TEAM_STATII) !== false`

- An undefined-index notice is raised if `status` is absent.
- `array_search` is non-strict.

**Fix:** use `in_array($dataRecord['status'] ?? null, self::CARE_TEAM_STATII, true)`.

### 6. Behaviour change in `searchForOpenEMRRecords` — **Low (verify)**

**Location:** `getAll($openEMRSearchParameters, true, $puuidBind)`

The `isAndCondition` argument changed from `false` to `true`. AND semantics are correct for FHIR search parameters, and the old OR was arguably a bug. Still, confirm that `CareTeamService::getAll` handles `ISearchField` objects with this flag, and add test coverage.

### 7. Facility taxonomy parsing — **Low**

**Location:** `explode(':', $dataRecordFacility['facility_taxonomy'])`

- Unprefixed values fall through to NUCC, which is fine.
- Any other prefix (e.g. `NUCC:` or something unexpected) is also silently labeled NUCC.
- The TODO about column size should be resolved or turned into a tracked issue, not merged as a conversation note to other people.

### 8. Maintainability nits — **Trivial**

- `USCGI_PROFILE_URI` looks like a typo for US Core IG (`USCIG`). It also lacks a visibility modifier, unlike the other constants.
- There are several stray blank lines: after the facility loop, around `setSubject`, and after the `$careTeamService` property.
- Role-coding construction is duplicated between the provider and facility branches. Consider a helper, e.g. `createRoleCoding($taxonomy, $fallbackTitle)`.
- `meta.lastUpdated` is always "now" and `versionId` is always `1`. This is pre-existing, but misleading for US Core consumers.

---

**Blocking:** #1 must be fixed before merge. #2 and #3 should also be addressed in this PR.
