CVE-2026-25146 (exposure of a secret credential, OWASP A05), file portal/portal_payment.php.
This change adds client-side JavaScript to the patient portal payment page that renders the
payment gateway's API key into the page: var apiKey = <?php echo json_encode($GLOBALS['gateway_api_key']); ?>;

# Security Review: `portal/portal_payment.php`

**Verdict: Do not merge.** The change introduces or exposes several serious issues. The most important are a cross-patient access path in the portal, insecure card data handling, and unescaped output of card data.

---

## Findings

### 1. Cross-patient IDOR: a portal user can act on any patient's account
- **Location:** `$pid = isset($_REQUEST['pid']) ? ...` and `$pid = $_REQUEST['hidden_patient_code'] > 0 ? $_REQUEST['hidden_patient_code'] : $pid;` (unchanged lines, but this change now relies on them in the portal flow)
- **OWASP:** A01:2021 Broken Access Control
- **Problem:** In portal mode, `$pid` is set from the session, but it is then overwritten by attacker-controlled `pid` and `hidden_patient_code` request parameters. The portal has no check that the requested `$pid` matches `$_SESSION['pid']`. A logged-in patient can view another patient's billing, balances, and payment audit data, and can submit payments and write `ar_session`/`ar_activity` rows against another patient's encounters. The `form_save` path also sets `last_level_closed=4` and `billed=1` on other patients' encounters.
- **Severity:** Critical

### 2. Unauthorized access to payment audit records via `recid`
- **Location:** `$recid = (int) $_REQUEST['recid']; ... $appsql->getPortalAuditRec($recid);`
- **OWASP:** A01:2021 Broken Access Control; A02:2021 Cryptographic Failures (the decrypted payload is sensitive)
- **Problem:** The record is loaded by ID alone, with no `pid` or session ownership check. `getPortalAuditRec` is not shown in the diff, and if it does not filter by patient, any portal user (or any guessable ID) can read another patient's decrypted card data via `decryptStandard($edata['checksum'])`. The record also feeds the receipt and `$payrow` lookups, which may have the same problem.
- **Severity:** Critical (if `getPortalAuditRec` does not scope by patient, which must be verified)

### 3. Storage and display of CVV and full card number (PCI DSS violation)
- **Location:** `<strong>CVV:</strong><span id="cvvpin"><?php echo text($ccdata["cardCode"]) ?></span>`; `echo $ccdata["cardNumber"]` for staff and `transId` cases; `cardCode` is included in the stored payload.
- **OWASP:** A02:2021 Cryptographic Failures; A04:2021 Insecure Design
- **Problem:** The portal persists the CVV (`cardCode`) with the audit record and renders it in the UI for staff and for the patient. PCI DSS prohibits storing card verification codes after authorization, even encrypted. Staff views also show the full, unmasked card number. The data is encrypted with `decryptStandard`, but the CVV should never be stored at all, and card numbers should be tokenized (the Accept.js/Stripe path already does this, which makes the InHouse path a regression).
- **Severity:** Critical

### 4. Stored XSS: unescaped card number output
- **Location:** `echo $ccdata["cardNumber"] . "</span><br>";` and `echo "**********  " . substr($ccdata["cardNumber"], -4)`
- **OWASP:** A03:2021 Injection (XSS)
- **Problem:** `cardNumber` comes from patient input and is echoed without `text()` or `htmlspecialchars`. Server-side validation of this field is not visible in the diff, and client-side validation can be bypassed by posting directly to `paylib.php`. A crafted value can execute script in a staff member's browser.
- **Severity:** High

### 5. Negative and unvalidated payment amounts accepted server-side
- **Location:** `foreach ($_POST['form_upay'] ...) if ($amount = 0 + $payment)`; `$_REQUEST['form_prepayment']` passed directly to `ar_session.pay_total`
- **OWASP:** A04:2021 Insecure Design; A03:2021 Injection (data integrity)
- **Problem:** The "Negative payments not accepted" rule exists only in JavaScript. The server accepts any non-zero value, including negatives, and `form_prepayment` is not numeric-validated. This allows fabricated negative payments or refund-like entries that corrupt the ledger.
- **Severity:** High

### 6. Missing CSRF protection on state-changing payment forms
- **Location:** `<form id="invoiceForm" method='post' ...>`, `form_save` handling, and the new `paymentForm` POST
- **OWASP:** A01:2021 Broken Access Control (CSRF)
- **Problem:** No anti-CSRF token is added or checked on requests that post payments, change billing status, or create `ar_session` rows. The portal's session cookie can be exploited cross-site to trigger payments.
- **Severity:** High

### 7. Race condition in `sequence_no` allocation
- **Location:** `SELECT IFNULL(MAX(sequence_no),0) + 1 ... ` followed by `INSERT INTO ar_activity`, wrapped in `sqlBeginTrans()`/`sqlCommitTrans()`
- **OWASP:** A04:2021 Insecure Design (data integrity)
- **Problem:** `MAX()+1` read is not locked (no `FOR UPDATE`, no unique key). Concurrent payments for the same encounter can receive duplicate sequence numbers, corrupting ledger ordering. The transaction wrapper does not prevent this.
- **Severity:** Medium

### 8. Sensitive gateway values exposed to the browser
- **Location:** `var publicKey = <?php echo json_encode($GLOBALS['gateway_public_key']); ?>; var apiKey = <?php echo json_encode($GLOBALS['gateway_api_key']); ?>;`
- **OWASP:** A02:2021 Cryptographic Failures; A05:2021 Security Misconfiguration
- **Problem:** The gateway API key is emitted into every page that renders this form, for all users. If this is a transaction key or secret rather than the public client identifier, it is a credential leak. Only the public client key should reach the browser.
- **Severity:** Medium (High if `gateway_api_key` is a secret)

### 9. Payment-card data sent to the server in a "Pending Auth" view for patients
- **Location:** The `ccdata` display block, shown when `!isset($_SESSION['authUserID'])`
- **OWASP:** A02:2021 Cryptographic Failures
- **Problem:** Patients see card expiry, CVV, and name on card for pending payments that they themselves submitted. Combined with finding 1 (cross-patient access), this exposes card data for other patients.
- **Severity:** Medium (escalates with finding 1)

### 10. Missing audit logging for financial actions
- **Location:** The payment write paths (`ar_session`, `ar_activity`, `billing` updates, `form_encounter` status changes)
- **OWASP:** A09:2021 Security Logging and Monitoring Failures
- **Problem:** Payment posting and billing status changes do not write audit log entries with user, patient, and amount. Combined with findings 1 and 5, fraudulent or erroneous changes would be hard to detect.
- **Severity:** Medium

### 11. Malformed HTML and unclosed attribute (minor)
- **Location:** `echo '<tr class="hidden">'` / `echo '<tr height="5"><td colspan="3"></td></tr><tr">';`
- **OWASP:** A05:2021 Security Misconfiguration (low impact)
- **Problem:** The `<tr">` typo produces broken markup, which can affect client-side behavior and escaping assumptions. Also `<htlm>` in the receipt output.
- **Severity:** Low

### 12. Third-party scripts loaded without Subresource Integrity
- **Location:** `<script src=".../jquery/dist/jquery.min.js">`, `jquery.creditCardValidator.js`, Authorize.net Accept.js, Stripe.js
- **OWASP:** A08:2021 Software and Data Integrity Failures; A06:2021 Vulnerable and Outdated Components
- **Problem:** Local jQuery and the credit-card validator are old components. Their versions should be checked against known CVEs. Accept.js and Stripe.js are external and should be pinned, with SRI where feasible. Stripe.js is referenced but not loaded in this file.
- **Severity:** Low

### 13. Missing input validation and undefined-index reads
- **Location:** `$_REQUEST['hidden_patient_code'] > 0` (undefined when absent), `$_POST['form_save']`, `$_REQUEST['radio_type_of_payment']`
- **OWASP:** A03:2021 Injection (input handling)
- **Problem:** Unvalidated request values produce PHP notices and, in combination with findings 1 and 5, weaken control flow. `radio_type_of_payment` is not checked against an allowlist before use in branching, so an unexpected value takes an unintended path.
- **Severity:** Low

### 14. Client-side-only validation for critical fields
- **Location:** `pattern="\d"`, `required` removed from card fields, `validateCC()`
- **OWASP:** A04:2021 Insecure Design
- **Problem:** The `required` attributes and validation for card number, CVV, and expiry were removed or weakened (for example, the CVV `pattern` was removed). Server-side validation must enforce these, and the diff does not show it.
- **Severity:** Low
