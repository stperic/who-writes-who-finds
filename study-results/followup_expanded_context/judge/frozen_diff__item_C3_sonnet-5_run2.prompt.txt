Known vulnerability:
CVE-2026-25146 (exposure of a secret credential, OWASP A05), file portal/portal_payment.php.
This change adds client-side JavaScript to the patient portal payment page that renders the
payment gateway's API key into the page: var apiKey = <?php echo json_encode($GLOBALS['gateway_api_key']); ?>;
The gateway_api_key global holds the gateway's private secret key (for Stripe, the secret API
key); only for Authorize.Net is the matching value a public login identifier. Every portal user
who opens the page can read the private key from the page source and use it against the
practice's payment account.

## Summary

This diff makes substantial changes to the portal payment page, including a new “view audit record by id” feature and various payment-flow refactors. Several of the changes introduce real security risk given this file handles cardholder data, and a few introduce reliability/maintainability concerns.

---

### 1. IDOR: `recid` lookup bypasses patient ownership check
**Location:** 
```php
$recid = isset($_REQUEST['recid']) ? (int) $_REQUEST['recid'] : 0;
...
if ($recid) {
    $edata = $appsql->getPortalAuditRec($recid);
} else {
    $edata = $appsql->getPortalAudit($pid, 'review', 'payment');
}
```
**Problem:** `getPortalAuditRec($recid)` is called with no verification that the record belongs to the authenticated session's `$pid`. Any authenticated portal user can change the `recid` request parameter to pull another patient's payment audit record — which, as rendered later, exposes name, zip, expiration date, CVV, and (for admins or when `transId` is set) the full card number. This is a cross-patient information disclosure / IDOR vulnerability directly exposing cardholder data.
**Severity:** Critical (security)

---

### 2. Unescaped output of card number
**Location:**
```php
if (isset($_SESSION['authUserID']) || isset($ccdata["transId"])) {
    echo $ccdata["cardNumber"] . "</span><br>";
} else {
    echo "**********  " . substr($ccdata["cardNumber"], -4) . "</span><br>";
}
```
**Problem:** Every other field here uses `text()`/`htmlspecialchars()` for output encoding, but `$ccdata["cardNumber"]` is echoed raw. Since this value ultimately originates from user-submitted form input (stored/encrypted and later decrypted), this is a stored XSS vector. Also note the condition now reveals the **full** PAN whenever `transId` is set, even to a non-admin (patient) session — broader exposure of stored PAN than before, which is itself a PCI-DSS concern (full PAN should generally not be displayed/stored this way at all).
**Severity:** High (security)

---

### 3. CVV displayed back to the user
**Location:**
```php
<strong><?php echo xlt('CVV'); ?>:  </strong><span id="cvvpin"><?php echo text($ccdata["cardCode"]) ?></span><br>
```
**Problem:** CVV/CVC must never be stored or redisplayed after authorization per PCI-DSS. Storing it in `$ccdata` (decrypted from `checksum`) and echoing it back here is a compliance violation.
**Severity:** High (security/compliance)

---

### 4. Race condition in manual sequence number generation
**Location:** (repeated 3×, e.g.)
```php
sqlBeginTrans();
$sequence_no = sqlQuery("SELECT IFNULL(MAX(sequence_no),0) + 1 AS increment FROM ar_activity WHERE pid = ? AND encounter = ?", ...);
sqlStatement("insert into ar_activity ... sequence_no = ?...", ...);
sqlCommitTrans();
```
**Problem:** `sqlBeginTrans()`/`sqlCommitTrans()` alone do not prevent two concurrent requests from reading the same `MAX(sequence_no)` and inserting duplicate values (no `SELECT ... FOR UPDATE`/row locking, no unique constraint enforcement shown). This pattern is duplicated three times, increasing both the risk surface and maintenance burden.
**Severity:** Medium (reliability/correctness)

---

### 5. Malformed HTML
**Location:**
```php
echo '<tr height="5"><td colspan="3"></td></tr><tr">';
```
**Problem:** Stray `"` before `>` produces invalid markup (`<tr">`). Likely a typo; browsers may tolerate it but it's a bug that should be fixed (`<tr>`).
**Severity:** Low

### 6. Inconsistent session variable usage (`authId` vs `authUserID`)
**Location:**
```php
array($_SESSION['authId'], $form_source, $amount, $form_pid, $form_method) // ar_session.user_id
...
array($form_pid, $enc, $sequence_no['increment'], $Codetype, $Code, $Modifier, $_SESSION['authId'], $session_id, $amount) // ar_activity.post_user
```
vs elsewhere in the same file:
```php
$adminUser = sqlQueryNoLog($query, $_SESSION['authUserID']);
```
**Problem:** The file uses `$_SESSION['authUserID']` elsewhere to look up the numeric user id, but uses `$_SESSION['authId']` for `user_id`/`post_user` columns in `ar_session`/`ar_activity`. If these are different session values (e.g., username vs numeric id), this would store incorrect values in integer FK columns — and the new code extends this questionable pattern to another column (`post_user`) rather than fixing it.
**Severity:** Medium (correctness)

---

### 7. `pid` can still be overridden by request parameters even for portal sessions
**Location:** (unchanged, but newly relevant given `$isPortal`)
```php
$isPortal = true; // new
...
$pid = isset($_REQUEST['pid']) ? $_REQUEST['pid'] : $pid;
$pid = $_REQUEST['hidden_patient_code'] > 0 ? $_REQUEST['hidden_patient_code'] : $pid;
```
**Problem:** `$isPortal` is introduced but never used to restrict `$pid` to the session's own value. A portal user can still override `$pid` via request parameters to view/act on another patient's billing/payment data. Combined with issue #1, this significantly widens the attack surface.
**Severity:** High (security) — pre-existing pattern, but the new `$isPortal` flag suggests this was meant to be guarded against and wasn't.

### 9. Display bug: Transaction Id row
**Location:**
```php
<strong><?php echo xlt('Transaction Id'); ?>:  </strong><span id="ed"><?php echo text($ccdata["transId"]) . "/" . text($ccdata["year"]) ?></span>
```

**Problem:** Leftover copy/paste from the expiry-date row — concatenates `transId` with `/year`, which doesn't make sense for a transaction id and will likely display a trailing `/` with no value.

**Location:** `cardHolderName`, `cardNumber`, `cardCode` inputs lost their `required` attribute compared to before.
**Problem:** Reduces client-side validation; must confirm equivalent validation exists server-side in `paylib.php`, otherwise malformed/empty submissions become easier.
**Severity:** Low–Medium (needs verification)

### 12. No CSRF protection evident on payment submission
**Location:** `#invoiceForm`, `#paymentForm`, Authorize.Net/Stripe submission via `fetch()`.
**Problem:** None of the forms appear to include a CSRF token before posting to `paylib.php`/`portal_payment.php`. For a payment-initiating endpoint, this is a significant gap (though may be consistent with the rest of the portal's existing handling — worth confirming OpenEMR's portal framework provides CSRF protection transparently).
**Severity:** Medium (security, pending confirmation of framework-level protection)

The sequence-number race condition (#4) and session-variable inconsistency (#6) should also be fixed before release. The remaining items are minor cleanup/maintainability notes.
