Known vulnerability:
CVE-2025-31121 (XSS, OWASP A03), file controllers/C_Document.class.php.
This change adds a fifth positional parameter, $disable_exit = false, to
C_Document::retrieve_action() and, when it is set, returns the raw document file contents
instead of exiting after sending them with the right Content-Type header. The legacy
Controller (library/classes/Controller.class.php) maps URL query parameters positionally onto
action arguments and echoes the action's return value with the default text/html content type.
So a request for a patient image with disable_exit=true makes the server return the raw file
bytes as text/html; HTML/JavaScript embedded in the image (for example in its EXIF title) runs
in the viewer's browser: stored cross-site scripting.

## Review Comments

### 1. `C_Document.class.php` – unconditional `fread()` of entire file into memory
**Location:** 
```php
$f = fopen($url,"r");
$filetext = fread( $f, filesize($url) );
if($disable_exit == true) {
    return $filetext;
}
```
**Problem:** Previously, `fread($f, filesize($url))` was only executed inside the `if ($doEncryption)` branch. Now the whole file is read into a PHP string **unconditionally**, even for the normal (non-encrypted, non-`disable_exit`) download path that presumably streams the file afterward (e.g. via `readfile()`/`fpassthru()` further down, not shown in the diff). For large documents (scans, PDFs, DICOM images, etc.) this causes unnecessary memory consumption and can lead to out-of-memory errors or degraded performance under concurrent downloads.
**Severity:** Medium–High (performance/reliability regression).

---

### 2. No error handling for `fopen()`/`filesize()` failures
**Location:** same block as above.
**Problem:** `fopen($url,"r")` can return `false` if the file is missing or unreadable, and `filesize($url)` will then also fail/emit a warning. This is pre-existing behavior but is now triggered unconditionally (not just when `$doEncryption` is true), increasing exposure to this failure mode without any new guard/check.
**Severity:** Low–Medium.

---

### 3. Resource leak: `$f` is never closed when `$disable_exit` is true
**Location:**
```php
if($disable_exit == true) {
    return $filetext;
}
```
**Problem:** The file handle `$f` opened by `fopen()` is not closed before returning. While PHP will eventually clean it up at script end, in long-running processes or when this function is invoked repeatedly (e.g., batch exports), this can accumulate open file descriptors.
**Severity:** Low.

---

### 4. Converted-file branch returns nothing useful for `disable_exit`
**Location:**
```php
else{
    $url = $GLOBALS['OE_SITE_DIR'] . '/documents/' . $from_pathname . '/' . $convertedFile;
}
if($disable_exit == true) {
    return ;
}
```
**Problem:** Unlike the two other new `disable_exit` branches, which return the actual file content, this branch simply `return;`s with no value when `$disable_exit` is true, even though a converted file exists at `$url`. Callers expecting content back (consistent with the other two branches) will silently get `null` instead of the converted document’s content. This looks like a functional bug/inconsistency rather than intentional behavior.
**Severity:** Medium–High (likely a real bug for the "converted file" code path).

---

### 5. Loose comparison `== true`
**Location:** All three new `if($disable_exit == true)` checks.
**Problem:** Using `==` instead of strict `===` (or simply `if ($disable_exit)`) is a minor style/correctness smell; it works for boolean today but is fragile if callers ever pass non-boolean truthy/falsy values (e.g., `"0"` string, etc.).
**Severity:** Low (style/maintainability).

### 6. Indentation / style inconsistency
**Location:** All newly added lines (e.g. `if($disable_exit == true) { ... }` blocks).
**Problem:** The new lines use space-indentation while the surrounding code uses tabs, creating inconsistent formatting in the file and making future diffs noisier.
**Severity:** Low (maintainability/style).

### 7. No documentation of the new parameter’s contract
**Location:** Function signature change:
```php
function retrieve_action($patient_id="",$document_id,$as_file=true,$original_file=true,$disable_exit=false) {
```
**Problem:** There is no comment/docblock explaining what `$disable_exit` does, what it returns in each branch (raw bytes vs base64-decoded vs nothing), or how callers should use it. Given issue #4 above (inconsistent return value across branches), this lack of documentation makes the contract ambiguous and error-prone for future maintainers.
**Severity:** Low–Medium (maintainability).

---

### 8. Potential downstream handling risk of returned raw content
**Location:** All three new `return` statements.
**Problem:** The function now has dual responsibilities — it either emits HTTP headers and streams file data directly to the client, or returns raw file bytes to the caller to do something else with. This mixing of concerns is a design smell; if any caller of `retrieve_action(..., true)` later echoes this content without appropriate headers/escaping (e.g., for HTML display or JSON embedding), it could introduce XSS or content-type confusion issues. Not a verifiable vulnerability within this diff alone, but worth flagging for review of callers.
**Severity:** Medium (needs verification against callers, otherwise informational).
