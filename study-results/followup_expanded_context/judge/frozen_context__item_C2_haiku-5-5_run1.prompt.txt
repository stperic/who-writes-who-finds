Known vulnerability:
CVE-2026-24487 (broken access control / cross-patient data exposure, OWASP A01), file
src/Services/FHIR/FhirCareTeamService.php. This change rewrites the FHIR CareTeam service: it
removes the service's own getOne() override that scoped results to the requested patient, adds
getPatientContextSearchField(), and implements IResourceUSCIGProfileService but not
IPatientCompartmentResourceService. FhirServiceBase::getAll() applies patient-context filtering
only when the service is an instance of IPatientCompartmentResourceService, so for
patient-scoped API access (for example a SMART patient-context token) CareTeam requests are no
longer filtered by patient and return care teams for every patient in the system.

## Review: FhirCareTeamService changes

### 1. Patient-context binding is not enforced (security, high)

The class now defines `getPatientContextSearchField()` and adds a `patient` search parameter, but it does not implement `IPatientCompartmentResourceService`. `FhirServiceBase` only applies patient binding when that interface is present:

- `getOne()`: `isset($puuidBind) && $this instanceof IPatientCompartmentResourceService`
- `createOpenEMRSearchParameters()`: `!empty($puuidBind) && $this instanceof IPatientCompartmentResourceService`

As written, a request made in a patient-bound context (`$puuidBind` set) will not restrict results to that patient. `searchForOpenEMRRecords($openEMRSearchParameters, $puuidBind = null)` also ignores its `$puuidBind` argument. Care team data is patient-specific, so this could expose other patients' care teams. The fix is to add `IPatientCompartmentResourceService` to the `implements` list and ensure the bind is applied in `searchForOpenEMRRecords` or the base path.

### 2. `getOne()` removed, behavior silently changed (reliability, medium)

The override that called `careTeamService->getOne()` and parsed the record was deleted, so lookups now go through the base `getOne()`, which runs a `_id` search via `getAll()`. This is a different code path with different binding behavior (see issue 1), and the PR does not explain the change. It should be justified or tested, especially for the patient-bound case.

### 3. Changed argument to `careTeamService->getAll()` (correctness, medium)

`searchForOpenEMRRecords` changed the second argument from `false` to `true` without explanation. If that flag controls output shape, every consumer of this path is affected. The change needs a comment or a test.

### 4. Fragile handling of the `providers` structure (correctness, medium)

```php
foreach ($dataRecord['providers'] as $dataRecordProviderList) {
    $dataRecordProvider = end($dataRecordProviderList);
```

- If `$dataRecordProviderList` is empty, `end()` returns `false`. Then `$dataRecordProvider['provider_uuid']` yields `null`, and `Practitioner/` is emitted with no ID.
- The nested-array shape is an implicit contract with `CareTeamService`. A missing or differently shaped key will raise undefined-index warnings.

Guard against empty lists and validate the required keys.

### 5. Undefined-index access on `status` and other keys (reliability, low)

`$dataRecord['status']`, `$dataRecord['puuid']`, `role_title`, and `facility_taxonomy` are read directly. Missing keys produce PHP notices. `status` should use `$dataRecord['status'] ?? null`.

### 6. Status validation (maintainability, low)

`array_search(...) !== false` should be `in_array($value, self::CARE_TEAM_STATII, true)`. The strict form is clearer and avoids loose-comparison pitfalls.

### 7. Inconsistent constant declarations (maintainability, low)

`USCGI_PROFILE_URI` is declared as a bare `const` with no visibility, while the status constants are `private const`. Its name is also an abbreviation of "US Core". Use a consistent visibility and a clearer name.

### 8. Minor cosmetics (low)

- Several stray blank lines were added around the participant loops and the `setSubject` call.
- The comment "US Core only allows onBehalfOf…" is placed above a block that does not clearly match it.
- The `// TODO` about facility taxonomy column size references individuals rather than a tracked issue.

### Summary

The first issue is a blocking security concern: patient-scoped requests are not restricted. The `getOne` removal and the `searchForOpenEMRRecords` flag change need explanation or tests before merge. The remaining items are robustness and style improvements.
