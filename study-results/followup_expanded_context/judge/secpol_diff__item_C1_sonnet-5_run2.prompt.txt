Known vulnerability:
CVE-2025-31121 (XSS, OWASP A03), file controllers/C_Document.class.php.
This change adds a fifth positional parameter, $disable_exit = false, to
C_Document::retrieve_action() and, when it is set, returns the raw document file contents
instead of exiting after sending them with the right Content-Type header. The legacy
Controller (library/classes/Controller.class.php) maps URL query parameters positionally onto
action arguments and echoes the action's return value with the default text/html content type.
So a request for a patient image with disable_exit=true makes the server return the raw file
bytes as text/html; HTML/JavaScript embedded in the image (for example in its EXIF title) runs
in the viewer's browser: stored cross-site scripting.

## Summary

This diff adds a `$disable_exit` flag to `C_Document::retrieve_action()` so the function can **return** file bytes instead of streaming them to the browser via `header()` + direct output (and presumably `exit`, given the parameter's name). This is a meaningful behavioral change to a function that handles **PHI document access**, and it introduces several concerns. I don't have visibility into the authorization logic that presumably exists earlier in the function (before line 384) or into the new callers that will use `disable_exit=true`, so some of these are flagged as "verify" items rather than confirmed exploits.

---

### 1. Bypassing download-enforcement headers / potential stored XSS or MIME-confusion
**Location:** `retrieve_action()`, all three new `if ($disable_exit == true) { return ...; }` blocks  
**OWASP Category:** A05:2021 – Security Misconfiguration / A03:2021 – Injection (XSS)  
**Problem:** The original flow always sent `Content-Disposition`/`Content-Type`-style headers (forcing a download, preventing inline rendering of potentially malicious file content such as HTML/SVG/JS uploaded as a "document"). The new code path returns the **raw bytes with no headers at all**. If any new caller echoes this return value back to a browser (e.g., to embed it in another page, API response, or merge workflow) without explicitly re-applying `Content-Disposition: attachment` and a safe `Content-Type`, a malicious uploaded document (e.g., an HTML or SVG file) could be rendered inline and executed as script in the victim's browser (stored XSS / reflected file download).  
**Severity:** Medium–High (depends entirely on how the new return value is consumed by callers not shown in this diff — needs verification).

---

### 2. New code path may skip access-control/audit enforcement for future callers
**Location:** `retrieve_action()` signature change (+`$disable_exit`)  
**OWASP Category:** A01:2021 – Broken Access Control / A04:2021 – Insecure Design  
**Problem:** `retrieve_action()` was designed as an HTTP action handler, presumably with authorization checks tied to the request/session context above line 384 (not shown). Turning it into a general-purpose "give me the file bytes" helper creates an internal API that could be invoked from a different context (e.g., batch export, merge, API endpoint) where the original authorization assumptions (current logged-in user, ACL, patient_id binding) may not hold. Nothing in the diff proves the access checks still run for the `disable_exit` branch — this needs explicit verification, since reusing this method from a new context is an easy way to accidentally bypass per-document ACL checks.  
**Severity:** Medium (potential High if any new caller skips auth) — requires review of all new call sites.

---

### 3. Successful retrievals via the new path are not logged
**Location:** New `return` statements (CouchDB block, file-read block, converted-file block)  
**OWASP Category:** A09:2021 – Security Logging and Monitoring Failures  
**Problem:** The existing code calls `document_upload_download_log()` on *failure* (e.g., CouchDB retrieval failure), implying download/access logging is part of the compliance design (important for PHI/HIPAA audit trails). The new early `return` paths bypass the rest of the function (including any logging that may occur after header output further down) without recording that the document was accessed/exported. This creates a gap in the audit trail for document access via this new mode.  
**Severity:** Medium (compliance/audit-trail impact for medical records system).

---

### 4. Loose comparison on security-relevant flag
**Location:** `if($disable_exit == true)` (all three occurrences)  
**OWASP Category:** A04:2021 – Insecure Design (minor hardening issue)  
**Problem:** Using `==` instead of `===` for a boolean/behavior-switching flag allows PHP type-juggling (e.g., a string `"1"`, non-empty string, or object could evaluate to `true` unexpectedly if this value is ever influenced indirectly by request data). Low likelihood here since it's a function parameter, but it's poor practice for a flag that changes security-relevant output behavior.  
**Severity:** Low.

---

### 5. Unmanaged file handle / unvalidated `fopen($url, "r")`
**Location:** `$f = fopen($url,"r"); $filetext = fread($f, filesize($url));` (moved up, now runs for both encrypted and non-encrypted output, and now also for the `disable_exit` return path)  
**OWASP Category:** A05:2021 – Security Misconfiguration (resource handling) / potentially A10:2021 – SSRF if `$url` can be remote  
**Problem:** Pre-existing issue surfaced/extended by this change: there's no error check if `fopen()` fails (returns `false`), no `fclose($f)` call (file handle leak), and no validation that `$url` is a local, expected document path. If `$url` is ever derived from data that could contain a scheme (`http://`, `php://`, etc.) due to upstream validation gaps, `fopen()` with `allow_url_fopen` enabled could be abused for SSRF or local file disclosure. This code is now exercised by more branches (encrypted, non-encrypted, and disable_exit), increasing the blast radius of any latent issue in how `$url` is constructed.  
**Severity:** Low–Medium (depends on how `$url`/document path is validated upstream — flagged because this change touches and extends the exercise of this code).

---

### 6. Pre-existing: no visible authorization/ownership check between `$patient_id` and `$document_id`
**Location:** Function overall (context above line 384 not shown in diff)  
**OWASP Category:** A01:2021 – Broken Access Control (IDOR)  
**Problem:** Not confirmable from the diff, but worth flagging: since `$patient_id` defaults to `""` and `$document_id` is attacker/user-suppliable, the function must strictly verify that the requesting user is authorized to access *that specific* document (not just that the document exists). This existed before the change but is now reachable through an additional code path (`disable_exit`) — recommend explicitly confirming the authorization check covers all three return points added by this diff.  
**Severity:** Needs verification — potentially High if authorization is not enforced identically for the new path.

---

## Recommendations
1. When `disable_exit=true`, have the caller explicitly apply `Content-Type`/`Content-Disposition` headers before emitting any content back to a browser, or ensure the returned bytes are never sent directly as an HTTP response.
2. Confirm and document that every existing authorization/ACL check in `retrieve_action()` runs unconditionally before any of the three new `return` statements.
3. Add explicit audit logging (success case) for the `disable_exit` return paths to preserve the document access audit trail.
4. Replace `== true` with `=== true` (or treat as a strict boolean).
5. Add error handling around `fopen()`/`fread()` (check for `false`), and ensure the file handle is closed (`fclose`) in all branches.
6. Audit/confirm how `$url` is constructed to rule out path traversal or SSRF via unexpected schemes.

No other issues were identified in the diff beyond the above.
