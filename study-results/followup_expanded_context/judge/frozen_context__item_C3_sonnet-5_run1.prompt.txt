Known vulnerability:
CVE-2026-25146 (exposure of a secret credential, OWASP A05), file portal/portal_payment.php.
This change adds client-side JavaScript to the patient portal payment page that renders the
payment gateway's API key into the page: var apiKey = <?php echo json_encode($GLOBALS['gateway_api_key']); ?>;
The gateway_api_key global holds the gateway's private secret key (for Stripe, the secret API
key); only for Authorize.Net is the matching value a public login identifier. Every portal user
who opens the page can read the private key from the page source and use it against the
practice's payment account.

<review>
## Security Issues

**1. IDOR via `recid` parameter — Critical**
`portal/portal_payment.php`, new block:
```php
$recid = isset($_REQUEST['recid']) ? (int) $_REQUEST['recid'] : 0;
...
if ($recid) {
    $edata = $appsql->getPortalAuditRec($recid);
}
```
`$recid` comes straight from the request and is used to fetch an arbitrary audit/payment record (which contains decrypted credit‑card data: name, full PAN, CVV, zip, expiry). There is no check that the record belongs to `$pid`/the current session's patient. Any authenticated (or portal) user can enumerate `recid` values and pull another patient's stored card data. This needs an ownership check (`WHERE pid = ?` or explicit verification against `$_SESSION['pid']`).

**2. CVV storage/display — Critical (PCI-DSS violation)**
```php
<strong><?php echo xlt('CVV'); ?>:  </strong><span id="cvvpin"><?php echo text($ccdata["cardCode"]) ?></span>
```
CVV/CVC values must never be retained after authorization, let alone re-displayed. Storing and echoing `cardCode` is a severe compliance/security problem independent of who can view it.

**3. Full PAN exposure condition widened — High**
```php
if (isset($_SESSION['authUserID']) || isset($ccdata["transId"])) {
    echo $ccdata["cardNumber"] . "</span><br>";
}
```
The added `|| isset($ccdata["transId"])` means the **unmasked card number** is now shown to unauthenticated portal sessions whenever a transaction id exists, not just to staff. Combined with issue #1, this significantly broadens who can see a raw PAN.

**4. Gateway secret key sent to the browser — Critical**
```php
var publicKey = <?php echo json_encode($GLOBALS['gateway_public_key']); ?>;
var apiKey = <?php echo json_encode($GLOBALS['gateway_api_key']); ?>;
```
`gateway_api_key` is documented in globals as "Auth Name **or API Secret** for Stripe". This is echoed unconditionally into client-side JS regardless of which gateway is active, even though it's never used by the Stripe.js flow shown (only `publicKey` is used there). This risks leaking a merchant secret key to every page view.

## Correctness Issues

**5. Wrong session key used for `post_user` — Medium/High**
```php
$insrt_id = sqlInsert(
    "... post_user ...",
    array($form_pid, $enc, $sequence_no['increment'], $Codetype, $Code, $Modifier, $_SESSION['authId'], $session_id, $amount)
);
```
This replaces a previously hardcoded literal with `$_SESSION['authId']`, but every other insert in this same file uses `$_SESSION['authUserID']`. `authId` does not appear to be set anywhere, so `post_user` will likely be recorded as NULL/empty, corrupting the audit trail for copay postings.

**6. Race condition generating `sequence_no` — Medium**
```php
sqlBeginTrans();
$sequence_no = sqlQuery("SELECT IFNULL(MAX(sequence_no),0) + 1 AS increment FROM ar_activity WHERE pid = ? AND encounter = ?", ...);
sqlInsert(... $sequence_no['increment'] ...);
sqlCommitTrans();
```
This pattern (repeated 3 times) is not safe under concurrency — without `SELECT ... FOR UPDATE` or a unique/auto-increment column, two simultaneous requests for the same encounter can compute the same `sequence_no`, causing duplicate values. `sqlBeginTrans()/sqlCommitTrans()` alone does not prevent this without row locking, and there's no rollback on failure.

**7. Malformed HTML — Low/Medium**
```php
echo '<tr height="5"><td colspan="3"></td></tr><tr">';
```
Produces a broken `<tr">` tag, which can cause unpredictable table rendering in some browsers.

## Maintainability / Reliability Nits

**8. Reduced client-side validation** — `required`/`pattern` attributes were dropped from `cardHolderName`, `cardNumber`, and `cardCode` inputs compared to before, weakening basic client-side sanity checks (server-side validation should still be verified, but this is a regression).

**9. Hardcoded expiration year list** (`2019`–`2028`) in the `expYear` select will need to be manually maintained/updated — minor maintenance burden.

**10. Duplicated sequence_no lookup logic** appears three times with only minor variation; should be factored into a shared helper to avoid drift/bugs across copies.

**11. Unused `$isPortal` flag** — introduced but not referenced anywhere in the shown diff; if it's genuinely unused, it's dead code.

**12. Mixed use of `idSqlStatement` vs `sqlInsert`** for functionally similar inserts — stylistic inconsistency that could confuse future maintainers about return value semantics.
