Known vulnerability:
CVE-2026-25146 (exposure of a secret credential, OWASP A05), file portal/portal_payment.php.
This change adds client-side JavaScript to the patient portal payment page that renders the
payment gateway's API key into the page: var apiKey = <?php echo json_encode($GLOBALS['gateway_api_key']); ?>;
The gateway_api_key global holds the gateway's private secret key (for Stripe, the secret API
key); only for Authorize.Net is the matching value a public login identifier. Every portal user
who opens the page can read the private key from the page source and use it against the
practice's payment account.

<review>
## Summary

This PR touches a security‑sensitive payment page (credit‑card capture, AR posting). While a lot of cleanup/refactoring is good, there are several serious issues that should block merge, plus a number of smaller maintainability concerns.

---

### 1. IDOR – unauthenticated/unauthorized record lookup via `recid`
**Location:** `portal/portal_payment.php`, new `$recid` handling
```php
$recid = isset($_REQUEST['recid']) ? (int) $_REQUEST['recid'] : 0;
...
if ($recid) {
    $edata = $appsql->getPortalAuditRec($recid);
} else {
    $edata = $appsql->getPortalAudit($pid, 'review', 'payment');
}
```
`getPortalAuditRec($recid)` is called with no check that the returned record actually belongs to `$pid`/the current session patient. Since `$edata['checksum']` is decrypted into `$ccdata` (full card number, CVV, zip, name) and rendered on the page, any authenticated portal user could enumerate `recid` values and view **another patient's decrypted credit‑card data**.
**Severity: Critical (security / IDOR / PCI exposure).**

---

### 2. Secret/private gateway key sent to the browser unconditionally
**Location:** inline `<script>` block
```php
var publicKey = <?php echo json_encode($GLOBALS['gateway_public_key']); ?>;
var apiKey = <?php echo json_encode($GLOBALS['gateway_api_key']); ?>;
```
Per the globals documentation, `gateway_api_key` is described as "Auth Name for Authorize.Net **and API Secret for Stripe**." This line is emitted regardless of which `payment_gateway` is configured, so when Stripe is selected, the **Stripe secret key is leaked into client-side HTML/JS**, visible to anyone viewing page source. This should only ever be emitted for AuthorizeNet (and even then, verify it isn't actually the transaction/secret key rather than the login ID).
**Severity: Critical (security — secret key disclosure).**

---

### 3. Storing/displaying full PAN and CVV (PCI‑DSS violation)
**Location:** payment info panel
```php
if (isset($_SESSION['authUserID']) || isset($ccdata["transId"])) {
    echo $ccdata["cardNumber"] . "</span><br>";
}
...
<strong>CVV:</strong><span id="cvvpin"><?php echo text($ccdata["cardCode"]) ?></span>
```
The CVV (`cardCode`) must never be stored after authorization (PCI‑DSS 3.2), yet it's retained in `$ccdata` and rendered in the page. Likewise, displaying the full unmasked card number to an "admin" session is a serious compliance risk — admins should see at most a masked PAN.
**Severity: Critical (security / compliance).**

---

### 4. Race condition generating `sequence_no`
**Location:** multiple places, e.g.
```php
sqlBeginTrans();
$sequence_no = sqlQuery("SELECT IFNULL(MAX(sequence_no),0) + 1 AS increment FROM ar_activity WHERE pid = ? AND encounter = ?", ...);
sqlStatement("insert into ar_activity ... sequence_no = ? ...", ...);
sqlCommitTrans();
```
A plain `SELECT MAX()` followed by `INSERT` inside a transaction does not prevent two concurrent requests from computing the same `sequence_no` unless the SELECT uses `FOR UPDATE`/proper locking, or unless the isolation level guarantees it (it generally doesn't for InnoDB default REPEATABLE READ without locking reads). Under concurrent submissions for the same encounter, this can produce duplicate `sequence_no` values.
**Severity: Medium (reliability/correctness).**

---

### 5. No server-side validation of payment amount
**Location:** `$_POST['form_upay']` processing loop
```php
if ($amount = 0 + $payment) {
```
Negative-amount prevention ("Negative payments not accepted") is only enforced client-side in `calctotal()`. A direct POST to this endpoint (bypassing the form) can submit negative amounts, creating bogus AR activity/adjustments. This existed before but is directly related to the payment flow being modified here and should be addressed.
**Severity: Medium-High (correctness/security).**

---

### 6. Unused/half‑wired `$isPortal` flag
**Location:**
```php
$isPortal = false;
...
$isPortal = true;
```
This flag is set but never referenced anywhere in the diff. Either it's dead code, or the access-control logic that's supposed to use it to differentiate "portal patient" vs "admin" behavior (especially relevant for issue #1 and #3) is missing.
**Severity: Low-Medium (maintainability / possibly incomplete security control).**

---

### 7. Inconsistent ID-retrieval helper usage
**Location:** copay session insert
```php
$session_id = sqlInsert(
    "INSERT INTO ar_session (...) VALUES (...)",
    ...
);
```
Elsewhere the code consistently uses `idSqlStatement()` to get the inserted ID (e.g., `$payment_id = idSqlStatement(...)`). Mixing `sqlInsert`/`idSqlStatement` for the same purpose is confusing and should be made consistent across the file.
**Severity: Low (maintainability).**

---

### 8. Hard-coded expiration year list
**Location:** credit card expiry `<select name="year">`
```php
<option value="2019">2019</option>
...
<option value="2028">2028</option>
```
Static year ranges will need manual updates every year and will eventually reject valid cards. Consider generating this dynamically (e.g., current year + N).
**Severity: Low (maintainability).**

---

### 9. Minor: `$pid` taken directly from `$_REQUEST`/`$_POST` without revalidation against session
```php
$pid = isset($_REQUEST['pid']) ? $_REQUEST['pid'] : $pid;
$pid = $_REQUEST['hidden_patient_code'] > 0 ? $_REQUEST['hidden_patient_code'] : $pid;
```
This is pre-existing code, not introduced by this PR, but combined with the new `$recid` path it widens the attack surface for impersonating another patient's record when posting payments. Worth a second look while this file is being touched.
**Severity: Low-Medium (pre-existing, flagged for awareness).**

---

## Positive notes
- SQL is consistently parameterized (no new SQL injection introduced).
- Good cleanup of duplicated/commented-out code and consistent use of `text()`/`attr()`/`htmlspecialchars()` for most output.
- Addition of Authorize.Net/Stripe tokenization client-side (via Accept.js / Stripe.js) is the right approach for those gateways and avoids sending raw card data to the server for those paths.

## Recommendation
Do **not merge** until issues #1–#3 (IDOR exposing card data, secret key leak, CVV storage/display) are fixed. These are critical security/compliance defects. The sequence_no race condition and amount validation issues should also be addressed before release.
