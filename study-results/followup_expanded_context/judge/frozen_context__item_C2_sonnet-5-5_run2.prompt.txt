Known vulnerability:
CVE-2026-24487 (broken access control / cross-patient data exposure, OWASP A01), file
src/Services/FHIR/FhirCareTeamService.php. This change rewrites the FHIR CareTeam service: it
removes the service's own getOne() override that scoped results to the requested patient, adds
getPatientContextSearchField(), and implements IResourceUSCIGProfileService but not
IPatientCompartmentResourceService. FhirServiceBase::getAll() applies patient-context filtering
only when the service is an instance of IPatientCompartmentResourceService, so for
patient-scoped API access (for example a SMART patient-context token) CareTeam requests are no
longer filtered by patient and return care teams for every patient in the system.

## Review findings

**1. Patient-compartment enforcement is missing (High, security)**
- Location: class declaration, `getPatientContextSearchField()`.
- The class adds `getPatientContextSearchField()` but only declares `implements IResourceUSCIGProfileService`. It does not implement `IPatientCompartmentResourceService`.
- `FhirServiceBase::getOne()` and `createOpenEMRSearchParameters()` only apply the `$puuidBind` restriction when `$this instanceof IPatientCompartmentResourceService`.
- This PR also deletes the old `getOne()` override, which passed `$puuidBind` straight to `CareTeamService::getOne()`.
- As a result, a patient-scoped token (`patient/CareTeam.read`) will no longer be restricted to its own patient's care teams, for both read and search. This is a regression and a possible data leak.
- Fix: add `IPatientCompartmentResourceService` to the class declaration, and add a test that a bound patient cannot read another patient's CareTeam.

**2. The `patient` reference search will probably not work (High)**
- Location: `loadSearchParameters()` and the constructor.
- `patient` is declared as `SearchFieldType::REFERENCE`. The base class says reference fields require a `FhirUrlResolver`, which is only created when `$fhirApiURL` is passed to `parent::__construct()`.
- This service still calls `parent::__construct()` with no argument. Searching `?patient=Patient/xyz` is therefore likely to fail or behave incorrectly.

**3. Assumptions about `CareTeamService` that this diff does not verify (High)**
- Location: `searchForOpenEMRRecords()`, `parseOpenEMRRecord()`.
- The second argument of `getAll()` flips from `false` to `true` with no explanation. It must match the `CareTeamService::getAll` signature.
- `CareTeamService` is not part of this diff. The code now expects `ISearchField` objects, a `status` column and `careteam_status`, and `providers` as a nested list (`role_code`, `role_title`, `facility_uuid`, `provider_uuid`). It also expects `facilities` as arrays (`uuid`, `facility_taxonomy`).
- If those service changes are not in the same PR or already merged, this will break at runtime.

**4. `end()` does not take the "first facility" and has no empty-list guard (Medium)**
- Location: the providers loop.
- The comment says "grab the first facility", but `end()` returns the last element.
- If `$dataRecordProviderList` is empty, `end()` returns `false`, and the following array accesses produce warnings and a `Practitioner` reference with a null ID.
- Fix: use `reset()` if "first" is intended, and skip the entry when the list is empty.

**5. `xlt()` is the wrong function for API output (Medium)**
- Location: `xlt($dataRecordProvider['role_title'])`, `xlt("Unknown")`.
- `xlt` HTML-escapes its output, which is intended for HTML contexts. FHIR JSON will contain escaped entities such as `&amp;` in `display`.
- Translating clinical display text in an API response is also questionable. `xlt` on a dynamic DB value is not translatable anyway, and `xlt(null)` can raise a deprecation if `role_title` is null.
- Fix: use plain text, or `xl()` at most.

**6. Undefined-index and global-function risks (Medium)**
- Location: `$dataRecord['status']`, `lookup_code_descriptions()`.
- `$dataRecord['status']` is read without an `isset` check.
- `array_search(...) !== false` should be `in_array($x, ..., true)`.
- `lookup_code_descriptions()` is a legacy global from `library/`. It may not be loaded in the FHIR/API context, so the file should explicitly ensure it is available.

**7. Search and parse behaviour is inconsistent for status (Medium)**
- Location: `status` search parameter versus the `parseOpenEMRRecord()` default.
- Unknown or null DB statuses are reported as `active` in the output, but a search for `status=active` filters on the raw column. Records can show as active yet not be returned by that search.

**8. Inconsistent code system handling (Low/Medium)**
- Location: provider role versus facility role coding.
- The provider role always uses `NUCC_PROVIDER` after stripping any prefix. The facility role checks for a `SNOMED-CT` prefix.
- A provider `role_code` with a non-NUCC prefix will be labelled with the wrong system.
- The facility `facility_taxonomy` has an open TODO about its column size, so merging with an unresolved TODO naming individuals is poor practice.

**9. Meta values are fabricated (Low)**
- Location: `$fhirMeta`.
- `lastUpdated` is the current time on every request and `versionId` is hardcoded to `'1'`. Clients caching or comparing on these will be misled.
- The profile URI is also never added to `meta.profile` here. This is probably handled elsewhere, but worth confirming.

**10. Maintainability and style (Low)**
- `USCGI_PROFILE_URI` looks like a typo for `USCDI`/`USCORE`, and the constant has no visibility modifier.
- There are stray blank lines, a mis-formatted constant array with a leading-comma line break, and duplicated role-coding code that could be extracted into a helper.
- `createProvenanceResource` throws `BadMethodCallException` for a wrong type. Other services probably handle this differently, so confirm consistency.
- No tests are included for the new search parameters, the role mapping, or the provenance output.
