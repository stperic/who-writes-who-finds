# Code Review: portal_payment.php

## Issues Found

### 1. **CRITICAL SECURITY: Potential SQL Injection via `$_REQUEST['recid']`**
**Location:** Line 59
```php
$recid = isset($_REQUEST['recid']) ? (int) $_REQUEST['recid'] : 0;
```
**Issue:** While the `(int)` cast provides some protection, this is passed directly to `getPortalAuditRec($recid)` without validation. The underlying implementation should be verified to ensure it's properly parameterized.

**Severity:** HIGH - Requires verification of `getPortalAuditRec()` implementation

---

### 2. **CRITICAL SECURITY: Unvalidated User Input in Payment Processing**
**Location:** Lines 210-230+ (payment processing section)
**Issue:** Multiple instances of `$_POST` and `$_REQUEST` data being used in SQL queries without apparent parameterization:
- `$_REQUEST['form_prepayment']` (line 228)
- `$_REQUEST['radio_type_of_payment']` (multiple uses)
- `$_POST['form_upay']` array iteration

**Severity:** CRITICAL - Direct SQL injection risk

---

### 3. **SECURITY: Insufficient Authorization Checks**
**Location:** Lines 27-32
```php
if (isset($_SESSION['pid']) && isset($_SESSION['patient_portal_onsite_two'])) {
    $pid = $_SESSION['pid'];
    $ignoreAuth = true;  // DANGEROUS!
```
**Issue:** Setting `$ignoreAuth = true` in portal context bypasses authorization. Then at line 59:
```php
$pid = isset($_REQUEST['pid']) ? $_REQUEST['pid'] : $pid;
```
The `$pid` can be overridden from `$_REQUEST`, potentially allowing a logged-in patient to access another patient's data.

**Severity:** CRITICAL - Authorization bypass

---

### 4. **CORRECTNESS: Race Condition in Transaction Logic**
**Location:** Lines 254-262 and similar blocks
```php
$sequence_no = sqlQuery("SELECT IFNULL(MAX(sequence_no),0) + 1 AS increment FROM ar_activity WHERE pid = ? AND encounter = ?", array($form_pid, $enc));
$insrt_id=sqlInsert(
    "INSERT INTO ar_activity (pid,encounter,sequence_no,...)".
    " VALUES (?,?,?,?,?,?,0,now(),?,?,?,'PCP')",
    array($form_pid, $enc, $sequence_no['increment'], ...)
);
sqlCommitTrans();
```
**Issue:** The sequence number is calculated then used without atomicity guarantee. Between the SELECT and INSERT, another concurrent request could insert a record with the same sequence number.

**Severity:** MEDIUM - Data integrity issue in high-concurrency scenarios

## Summary

**Critical Issues (3):** 
- Unvalidated `$_REQUEST` data in SQL queries
- Authorization bypass via `$pid` override

**Recommended Actions:**
1. Add strict parameter validation/parameterization for all database queries
2. Remove ability to override `$pid` from `$_REQUEST` when `$ignoreAuth` is true
3. Implement atomic transactions for sequence number generation
4. Add null checks for all query results
5. Audit the `getPortalAuditRec()` implementation
6. Standardize XSS escaping approach across the file
