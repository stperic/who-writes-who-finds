Known vulnerability:
CVE-2026-25146 (exposure of a secret credential, OWASP A05), file portal/portal_payment.php.
This change adds client-side JavaScript to the patient portal payment page that renders the
payment gateway's API key into the page: var apiKey = <?php echo json_encode($GLOBALS['gateway_api_key']); ?>;
The gateway_api_key global holds the gateway's private secret key (for Stripe, the secret API
key); only for Authorize.Net is the matching value a public login identifier. Every portal user
who opens the page can read the private key from the page source and use it against the
practice's payment account.

# Code Review: `portal/portal_payment.php`

## Critical

**1. IDOR via `recid`: any user can load any patient's payment audit record**
- **Where:** `$recid = (int) $_REQUEST['recid']` → `$appsql->getPortalAuditRec($recid)`
- **Problem:** The record is fetched by ID alone. Nothing checks that it belongs to `$_SESSION['pid']` or that the caller is an authorized admin.
- **Impact:** A portal patient can iterate `recid` values and read other patients' decrypted card data (`checksum` → `$ccdata`) and invoice data.
- **Related:** The pre-existing `$pid = $_REQUEST['pid'] / hidden_patient_code` override has the same problem. It lets a portal session view, and post against, another patient's invoices.
- **Fix:** The new `$isPortal` flag is set but never used. It looks like it was meant to fix exactly this. When `$isPortal` is true:
  - force `$pid = $_SESSION['pid']`, and
  - verify the audit record's `patient_id` equals that pid.

**2. Full card number shown unmasked to patients, and output is not escaped**
- **Where:** `if (isset($_SESSION['authUserID']) || isset($ccdata["transId"])) { echo $ccdata["cardNumber"] ...`
- **Problem:** Once a `transId` exists, the full PAN is shown to the portal patient. The masking branch is skipped.
- **Also:** The value is echoed raw (no `text()`), so it is an XSS sink.
- **Fix:** Always mask for portal users. Always escape the output.

**3. CVV and full PAN stored and displayed (PCI-DSS violation)**
- **Where:** The InHouse flow still serializes card number and CVV into the audit record. The admin view renders `cardCode`.
- **Problem:** Storing the CVV after authorization is prohibited under PCI-DSS, encrypted or not.
- **Fix:** Now that tokenizing gateways exist, deprecate InHouse, or at minimum never persist or display the CVV.

## High

**4. Client-side handlers bound before their elements exist**
- **Where:** The head `<script>` binds `$('#openPayModal').on('show.bs.modal')`, `$('#invoiceForm').on('submit')` and `$('#paySubmit').click`.
- **Problem:** These are bound at parse time, with no `$(function(){...})` wrapper, before the elements exist. The bindings silently do nothing.
- **Impact:**
  - `#payTotal` and `#paymentAmount` are never populated, so the gateway receives an empty `payment`.
  - The new InHouse `#paySubmit`, which now lives in the modal footer, never fires.

**5. Gateway SDKs are never loaded**
- **Problem:** No `<script>` loads Accept.js (Authorize.Net) or `https://js.stripe.com/v3/`.
- **Impact:** `Accept.dispatchData` and `Stripe(publicKey)` will throw `ReferenceError`. The Stripe block runs at load, so it breaks the rest of the script too.

**6. Secret key exposure risk**
- **Where:** `var apiKey = <?php echo json_encode($GLOBALS['gateway_api_key']); ?>`
- **Problem:** This is emitted to every portal page regardless of gateway.
- **Fix:** Confirm this is only the Authorize.Net API Login ID and never a transaction or secret key. Emit it only for the gateway that needs it.

**7. Charge amount comes from the client**
- **Where:** `payment` / `invValues` are taken from the browser.
- **Problem:** `paylib.php` (not shown) must recompute the amount server-side from the invoice. If it doesn't, the patient controls the amount charged and posted.

**8. `sequence_no` generation is racy and transactions are incomplete**
- **Problem with the sequence:** `SELECT MAX(sequence_no)+1` without `FOR UPDATE` (or a locking read) does not prevent duplicates under concurrency.
- **Problem with the transaction scope:**
  - The `ar_session` insert and `frontPayment()` are outside the transaction.
  - There is no rollback on failure.
  - The result is partial postings (a session row without activity, or vice versa).
- **Fix:** Wrap the whole posting for an encounter in a single transaction, with a locking read.

## Medium

**9. Totals computed from formatted strings**
- **Where:** `$sum_balance += $balance * 1` and the `$sum_*` accumulators.
- **Problem:** `$balance` is the return value of `bucks()`, which may be `''` or a locale-formatted string such as `1,234.00`.
- **Impact:**
  - On PHP 8, arithmetic on a non-numeric string throws `TypeError`.
  - On PHP 7, it gives warnings and wrong totals.
- **Fix:** Accumulate raw numeric values.

**10. Behavior change: `calendar_arrived()` removed**
- **Problem:** Copay with `enc == 0` previously created or found today's encounter. Now it posts `ar_activity` against encounter 0.
- **Fix:** If this path is dead, assert or reject `enc == 0` explicitly.

**11. `post_user` / `user_id` inconsistency**
- **Problem:** The copay path uses `$_SESSION['authId']`, while other paths use `$_SESSION['authUserID']`.
- **Impact:** In a portal session neither may be set, which writes NULL/0 audit users.

**12. No CSRF protection**
- **Problem:** The state-changing `form_save` POST has no CSRF token. This is pre-existing, but the endpoint is being reworked.

**13. Authorize.Net errors only reach the console**
- **Where:** In `acceptResponseHandler`, errors go to `console.log`.
- **Problem:** The user gets no feedback and the modal just sits there.

## Low / Maintainability

- **Copy/paste bug:** The Transaction Id line appends `"/" . $ccdata["year"]`. It also reuses `id="ed"` and `id="cvvpin"`.
- **Malformed HTML:** `echo '...<tr">'` contains a stray quote.
- **Duplicate IDs across forms:** `mode`, `cardHolderName`, `payTotal`, `paymentAmount`, `cc_type`, `invValues`. `$("#mode")` only hits the first one.
- **Broken input patterns:**
  - `pattern="\d"` on `cardNumber` and `zip` matches only a single digit.
  - The `required` attributes were removed.
- **Duplicate Stripe tokens:** `stripeTokenHandler` appends a new hidden `stripeToken` on every retry.
- **Unclear payment-method filter:** In `if ($id != 'credit_card' || $id == 'debit' || ...)`, the extra OR terms are dead code. Simplify to `!= 'credit_card'`.
- **Unused flag:** `$isPortal` is set but never used (see item 1).
- **Unescaped JSON in `<script>`:** `json_encode` output is placed in `<script>` without `JSON_HEX_TAG`. This is minor, but translations containing `</script>` would break out.
- **Server-side enforcement:** The Copay radio is hidden via CSS for portal users, but nothing prevents posting `radio_type_of_payment=copay`.
