## Review: FhirCareTeamService changes

The PR adds US Core CareTeam support: search parameters, a richer resource mapping, a provenance hook, and a profile URI. I found several issues, the most important being an undocumented change to the search semantics and a removed `getOne` override that needs verification.

### Issues

**1. `searchForOpenEMRRecords` flips a boolean argument with no explanation (High)**
- Location: `searchForOpenEMRRecords()`, `getAll($openEMRSearchParameters, true, $puuidBind)`
- The second argument was `false` and is now `true`. If it controls AND/OR combination of search fields, this silently changes results for every multi-parameter query (for example `patient` plus `status`). The diff doesn't mention it.
- Fix: confirm the parameter's meaning in `CareTeamService::getAll`, document why it changed, and add a test covering combined parameters.

**2. `getOne` removed without a replacement (High, verify)**
- Location: the deleted `getOne($fhirResourceId, $puuidBind = null)` method.
- The removed method looked up the record and parsed it. Without it, single-resource reads depend on the base class's fallback. If the base class's `getOne` doesn't call `parseOpenEMRRecord`, or doesn't handle `puuidBind`, reads will return raw or wrong data, or leak records across patients.
- Fix: confirm the base implementation handles this, or restore the method. Add a read test.

**3. Comment contradicts code: first vs last facility (Medium)**
- Location: provider loop, `$dataRecordProvider = end($dataRecordProviderList);`
- The comment says "we are only going to grab the first facility", but `end()` returns the last element.
- Fix: use `reset()` for the first element, or correct the comment if last is intended.

**4. Unguarded `end()` on possibly empty provider list (Medium)**
- Location: same loop.
- If `$dataRecordProviderList` is empty, `end()` returns `false`. The subsequent `$dataRecordProvider['role_code']` and `$dataRecordProvider['provider_uuid']` accesses then emit warnings and build a `Practitioner/` reference with a null ID.
- Fix: skip the entry when the list is empty or the lookup returns no provider.

**5. Unchecked array keys (Medium)**
- Locations: `$dataRecord['status']`, `$dataRecordProvider['role_title']`, `$dataRecordProvider['facility_uuid']`, `$dataRecordFacility['uuid']`, and others.
- Missing keys produce PHP notices. `xlt($dataRecordProvider['role_title'])` with a null value also triggers deprecation warnings on PHP 8.1+.
- Fix: use `?? null` or validate the row shape up front.

**6. Facility role fallback is inconsistent (Low)**
- Location: facility loop, `if (empty($description)) { $description = null; }`
- Provider code falls back to `role_title`, but facility code sets display to `null`. The intent is unclear. Also the `$codeParts[0] === "SNOMED-CT"` check is case-sensitive.
- Fix: make the fallbacks consistent and document the intent.

**7. Status validation uses `array_search` (Low)**
- Location: `if (array_search($dataRecord['status'], self::CARE_TEAM_STATII) !== false)`
- `in_array($value, $array, true)` is clearer and strict.
- The constant name `CARE_TEAM_STATII` is also non-standard; `CARE_TEAM_STATUSES` would read better.

**8. `createProvenanceResource` changes behavior (Medium, verify)**
- Location: `createProvenanceResource()`
- It now throws `\BadMethodCallException` on wrong input and constructs `FhirProvenanceService` directly. Callers that previously got `null` now get an exception. The `new` inside the method also makes it hard to mock. Confirm that `createProvenanceForDomainResource` exists and that no caller depends on the old no-op.

**9. Style and maintainability (Low)**
- Duplicated `new FHIRCodeableConcept()` / `new FHIRCoding()` blocks in both loops could be a helper method.
- Multiple stray blank lines, including a run of four before `if ($encode)`.
- `const USCGI_PROFILE_URI` lacks a visibility modifier and doesn't match the `CARE_TEAM_` naming used elsewhere in the class.
- The `// TODO` referencing specific people in code is better tracked in an issue.

**10. No tests in the diff (Medium)**
- The change alters search semantics, removes a read path, and adds a new mapping with several fallback branches. None of this has test coverage in the PR.

### Summary
Items 1 and 2 should be resolved before merge, since they can change search and read results for existing clients. Items 3–5 are correctness and robustness problems in the new mapping code. The rest are cleanup. The PR needs tests for the search change, the single-record read, and the empty-provider and missing-field cases.
