# Security Review: `library/classes/Controller.class.php` (Controller routing refactor)

## Summary

The new controller whitelist (`VALID_CONTROLLERS`) is a real improvement. It removes the dynamic `C_<anything>.class.php` include path.

However, the refactor also removes two protections on the action name:
- the old character sanitization, and
- the `method_exists()` check.

The old code's comment warned that `is_callable()` is always true on Smarty 4 objects because Smarty defines `__call()`. As a result, attackers now control which method name is invoked and with what arguments, and can reach Smarty's magic-method machinery. Several older problems (GET-triggered state changes, thin controller-level access control) also carry forward.

---

## 1. Action dispatch reaches Smarty `__call()` with attacker-controlled method names

**Severity: High**

- **Location:** `dispatch()`, specifically:
  - `$action = is_string($params['action'] ?? null) ? $params['action'] : 'default';`
  - `is_callable([$controllerObj, $processMethod])`
  - `is_callable([$controllerObj, $actionMethod])`
  - `$controllerObj->$method(...array_values($args))`
- **OWASP category:**
  - A03 Injection
  - A04 Insecure Design
  - A01 Broken Access Control

**Problem: three changes combine**

1. **Action is no longer sanitized.** The old code applied `preg_replace("/[^A-Za-z0-9_]/", "", ...)` to the action. The new code uses `$params['action']` raw. In `act()` it is the raw second query key; in `dispatch()` it is the raw `action` value.
2. **`method_exists()` was dropped.** All controllers extend `Controller extends Smarty`. Smarty 4 implements `__call()`, so `is_callable()` returns true for *every* method name. The removed comment said exactly this.
3. **The `else` branch is effectively dead.** The `NotFoundHttpException` branch is never reached. Any `action=<x>` results in `$controllerObj->{"<x>_action"}(...)` being called. Non-existent methods are routed into `Smarty::__call()` → `Smarty_Internal_Extension_Handler::_callExternalMethod()`, with user-supplied positional arguments taken from the rest of the query string.

**Impact**

- **Unintended Smarty methods become reachable.** The extension handler parses `get*`/`set*` prefixes and resolves extension objects via `$smarty->ext->{name}`. That lazy-loads `Smarty_Internal_Method_<Name>` classes through the autoloader. This exposes a surface of Smarty internals that was never meant to be an HTTP endpoint, such as template/config/plugin directory setters and registration methods, with attacker-chosen arguments.
- **Possible path traversal into the autoloader.** Unsanitized method names now flow into class-name construction. Smarty's sysplugins autoloader builds a file path from the lower-cased class name. Whether `../` sequences survive the `preg_match` in `_callExternalMethod` depends on the exact Smarty version. Either way, it is a dangerous path that the old sanitization closed off.
- **Process path bypasses existence checks.** On the process path (`$isProcessing`), `$actionMethod` is called unconditionally, with no existence check at all.

**Fix**

- Validate the action strictly, e.g. `preg_match('/^[a-z][a-z0-9_]*$/i', $action)`.
- Restore `method_exists()`, or better, check with `ReflectionMethod` that the method is public and declared on the concrete controller class (not `Smarty`/`Controller`).
- Ideally, use a per-controller allow-list of actions.

## 2. Reflected XSS / information disclosure via exception messages

**Severity: Medium**

- **Location:**
  - `throw new NotFoundHttpException("Action '$action' does not exist on controller: $className");`
  - `throw new BadRequestHttpException(...)`
  - Indirectly, Smarty's `SmartyException("Call of unknown method '<name>'.")` raised through `__call`
- **OWASP category:**
  - A03 Injection (XSS)
  - A05 Security Misconfiguration

**Problem**

- The old code only echoed the *sanitized* action, which was alphanumeric plus underscore.
- The new code embeds the raw, attacker-controlled `$action` in exception messages.
- Because of issue #1, the usual path is a `SmartyException` that contains the raw method name.
- If these exceptions reach a renderer that prints the message without HTML escaping, a crafted link becomes reflected XSS in an authenticated EMR session. Examples of such renderers: PHP `display_errors`, a debug error handler, or a generic catch block that echoes `$e->getMessage()`.
- Messages also disclose internal class names.

**Fix**

- Don't interpolate user input into exception messages, or validate the action first (issue #1).
- Make sure the top-level exception handler escapes messages and hides details in production.

## 3. GET request converted into a state-changing "process" (CSRF exposure)

**Severity: Medium (pre-existing, preserved and extended)**

- **Location:**
  - `if (isset($params['process'])) { unset($_GET['process']); ...; $_POST['process'] = "true"; }`
  - `$isProcessing = ($_POST['process'] ?? '') === 'true';`
- **OWASP category:**
  - A01 Broken Access Control (CSRF)
  - A04 Insecure Design

**Problem**

- Any GET request containing `process` causes `*_action_process` handlers to run. These are the state-changing save/update/delete handlers.
- They are triggered as if a form had been POSTed.
- A malicious link or `<img src=...>` can therefore trigger writes in a logged-in user's session, unless every individual `_process` method verifies a CSRF token. Many legacy controllers do not.
- The new `dispatch()` keeps this behavior. It also treats `$params['process']` from *any* caller as a trigger to write to the `$_POST` superglobal.

**Fix**

- Only enter the process path when `$_SERVER['REQUEST_METHOD'] === 'POST'`.
- Centrally verify the CSRF token (`CsrfUtils::verifyCsrfToken`) in `dispatch()` before calling any `_action_process` method.
- Remove the GET-to-POST promotion.

## 4. Incomplete controller-level authorization

**Severity: Medium (pre-existing, now codified)**

- **Location:** `CONTROLLER_ACL_MAP` and `checkControllerAcl()`
- **OWASP category:** A01 Broken Access Control

**Problem**

- Only `practice_settings` and `prescription` are gated.
- These whitelisted controllers have no ACL at the dispatcher level:
  - `document`
  - `document_category`
  - `hl7`
  - `insurance_company`
  - `insurance_numbers`
  - `patient_finder`
  - `pharmacy`
  - `x12_partner`
- Administrative data such as `x12_partner`, `insurance_company`, `insurance_numbers` and `pharmacy` is normally managed under Practice Settings. It can be reached directly (`?controller=pharmacy&action=edit&process=true`), skipping the `admin/practice` check applied to `practice_settings`.
- `document` and `patient_finder` expose PHI and rely entirely on checks inside each controller.
- The new explicit `controller=` parameter makes direct addressing of these controllers easier and more obvious.

**Fix**

- Give every whitelisted controller an ACL entry. For example:
  - `admin/practice` for `pharmacy`, `insurance_company`, `insurance_numbers` and `x12_partner`
  - `patients/docs` for `document` and `document_category`
  - an appropriate patients ACL for `patient_finder`
- Default-deny controllers that have no mapping.
- Keep the per-patient authorization checks inside the controllers themselves.

## 5. Argument handling changes (lower severity)

**Severity: Low**

- **Location:** the argument-building loop in `dispatch()` and the remapping loop in `act()`
- **OWASP category:** A04 Insecure Design

**Problems**

- **Values are passed positionally in query-string order.** `array_values($args)` means extra or reordered parameters supplied by an attacker shift which value lands in which method parameter. One example: an injected `sub_action`, or any extra key placed before `patient_id`. Previously the order was also attacker-influenced, but keys were sanitized and the mapping matched the legacy URL format. Now arbitrary keys, including array-valued `foo[]=` parameters, are forwarded straight into action and `__call` arguments.
- **`act()` no longer strips `process` before choosing the positional action.** A URL like `?document&process=true&...` makes `process` the action, which causes confusing routing.

**Fix**

- Bind arguments by name, e.g. via `ReflectionMethod::getParameters()`.
- Reject non-scalar values where scalars are expected.

---

## Positive changes

- The whitelist of controller names eliminates arbitrary controller file inclusion and class instantiation.
- Exceptions replace `echo ...; exit;`.

## Recommendation

**Do not merge as-is.** At minimum:
- restore action-name validation and the `method_exists()`/declaring-class check (#1, #2), and
- restrict process handling to POST with central CSRF verification (#3).

Address the ACL gaps (#4) in this PR or in a follow-up.
