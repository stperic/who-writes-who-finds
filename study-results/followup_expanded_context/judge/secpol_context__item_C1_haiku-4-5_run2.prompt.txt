Known vulnerability:
CVE-2025-31121 (XSS, OWASP A03), file controllers/C_Document.class.php.
This change adds a fifth positional parameter, $disable_exit = false, to
C_Document::retrieve_action() and, when it is set, returns the raw document file contents
instead of exiting after sending them with the right Content-Type header. The legacy
Controller (library/classes/Controller.class.php) maps URL query parameters positionally onto
action arguments and echoes the action's return value with the default text/html content type.
So a request for a patient image with disable_exit=true makes the server return the raw file
bytes as text/html; HTML/JavaScript embedded in the image (for example in its EXIF title) runs
in the viewer's browser: stored cross-site scripting.

# Security Review: C_Document.class.php Pull Request

I have identified **several critical security vulnerabilities** in this pull request:

---

## 1. **Broken Access Control + Identification and Authentication Failures**
**Location:** `retrieve_action()` function signature and throughout  
**OWASP Category:** A01:2021 – Broken Access Control / A07:2021 – Identification and Authentication Failures  
**Severity:** **CRITICAL**

**Problem:**  
The new `$disable_exit` parameter allows bypassing the normal file retrieval flow and returning raw file content. There is **no validation** that the caller is authorized to use this parameter or has legitimate reasons to disable the exit. The function already reads `$_POST['encrypted']` and `$_POST['passphrase']` but the `$disable_exit` parameter can be set by an external caller without authentication checks.

**Details:**
- Line 387: Parameter added with no access control validation
- Lines 433-435, 515-518, 553-555: Early returns bypass security headers and normal flow
- No caller authentication or authorization verification before allowing the bypass

**Recommendation:**  
Add explicit access control checks before honoring `$disable_exit`. Verify the caller has legitimate internal-only status.

---

## 2. **Insecure Design - Unsafe Parameter Handling**
**Location:** Lines 515-518  
**OWASP Category:** A04:2021 – Insecure Design  
**Severity:** **HIGH**

**Problem:**  
The file is opened and read unconditionally BEFORE checking `$disable_exit`:
```php
$f = fopen($url,"r");
$filetext = fread( $f, filesize($url) );
if($disable_exit == true) {
    return $filetext;
}
```

This means:
- File handles are opened even when they may not be needed
- No error handling for `fopen()` or `fread()` failures
- The file resource `$f` is never closed (resource leak)
- If `$disable_exit` is true, the file handle remains open

**Recommendation:**  
Move file operations inside conditional blocks and ensure proper resource cleanup with `fclose()`.

---

## 3. **Server-Side Request Forgery (SSRF)**
**Location:** Lines 515-518, and broader context with `$url` variable  
**OWASP Category:** A10:2021 – Server-Side Request Forgery (SSRF)  
**Severity:** **HIGH**

**Problem:**  
The `$url` variable is constructed from user-influenced paths (visible in context: `$from_pathname`). The code opens and reads files via `fopen($url)` without validating that `$url` points to an intended location. An attacker could potentially:
- Read arbitrary files from the server
- Access files outside the intended documents directory
- Exploit path traversal vulnerabilities

**Recommendation:**  
Implement strict path validation:
- Use `realpath()` to resolve the actual path
- Verify it's within the intended `documents/` directory
- Reject any path traversal attempts (`../`, `..\\`, etc.)

---

## 4. **Cryptographic Failures - Weak Encryption Logic**
**Location:** Lines 433-435 (CouchDB path) and line 434  
**OWASP Category:** A02:2021 – Cryptographic Failures  
**Severity:** **MEDIUM**

**Problem:**  
- Line 434: `return base64_decode($content);` - Decrypted content is returned without validation
- The passphrase comes directly from `$_POST['passphrase']` (line 387) with no strength validation

- No verification that the decryption was successful or authentic (no integrity check/HMAC)

**Recommendation:**

- Validate passphrase meets minimum security requirements
- Ensure only authenticated users can access decrypted content

## 6. **Broken Access Control - Missing Parameter Validation in Parent Class**
**Location:** `Controller.class.php` - `act()` method, lines 110-123  
**OWASP Category:** A01:2021 – Broken Access Control  
**Severity:** **MEDIUM** (pre-existing)

**Problem:**  
Arguments are parsed from URL/query string with regex filtering but minimal validation:
```php
$arg = preg_replace("/[^A-Za-z0-9_]/","",$arg);
```
This only allows alphanumeric and underscore characters, but doesn't validate *values* passed to functions. The `$disable_exit` parameter could be passed via URL/POST and the value isn't type-checked.

**Recommendation:**  
Validate that `$disable_exit` is explicitly boolean, not a string like `"true"` or `1`.

---

## 7. **Resource Leak**
**Location:** Lines 515-518  
**OWASP Category:** A04:2021 – Insecure Design  
**Severity:** **MEDIUM**

**Problem:**  
`fopen($url,"r")` opens a file handle but:
- If `$disable_exit == true`, the function returns without closing the handle
- The handle `$f` is never explicitly closed in this code path
- This leads to file descriptor exhaustion over time

**Recommendation:**  
```php
$f = fopen($url,"r");
if (!$f) {
    die("File open failed");
}
$filetext = fread($f, filesize($url));
fclose($f);
if($disable_exit == true) {
    return $filetext;
}
```
