Known vulnerability:
CVE-2026-24487 (broken access control / cross-patient data exposure, OWASP A01), file
src/Services/FHIR/FhirCareTeamService.php. This change rewrites the FHIR CareTeam service: it
removes the service's own getOne() override that scoped results to the requested patient, adds
getPatientContextSearchField(), and implements IResourceUSCIGProfileService but not
IPatientCompartmentResourceService. FhirServiceBase::getAll() applies patient-context filtering

## Security Review – `FhirCareTeamService.php`

### 1. Broken Access Control — Missing `IPatientCompartmentResourceService` interface
**Location:** Class declaration
```php
class FhirCareTeamService extends FhirServiceBase implements IResourceUSCIGProfileService
```
**Problem:** The PR adds `getPatientContextSearchField()` and registers a `'patient'` search parameter, clearly intending to support patient‑scoped queries. However, `FhirServiceBase` only auto-enforces the patient binding (`puuidBind`) in `createOpenEMRSearchParameters()` and `getOne()` when:
```php
$this instanceof IPatientCompartmentResourceService
```
Since the class implements **only** `IResourceUSCIGProfileService` (confirmed by the diff removing the previous no-interface declaration), the automatic "restrict results to the bound patient" logic will never fire for this service. If this resource is exposed through a patient-scoped API context (e.g., patient portal, SMART-on-FHIR patient-launch scope), a caller could potentially retrieve CareTeam resources belonging to other patients by supplying an arbitrary `_id` or `patient` parameter, because the hard binding check silently no-ops.
**Severity:** **High** — potential cross-patient data disclosure (PHI) if this service is used in any patient-restricted context.

---

### 2. Broken Access Control / Insecure Design — Unexplained change in `getAll()` boolean flag
**Location:**
```php
- return $this->careTeamService->getAll($openEMRSearchParameters, false, $puuidBind);
+ return $this->careTeamService->getAll($openEMRSearchParameters, true, $puuidBind);
```
**Problem:** The semantics of this positional boolean argument (likely `isAndCondition` or similar) are not visible in this diff. Changing it from `false` to `true` silently alters search-matching behavior (AND vs OR across multiple search fields). If this flag affects how facility/provider/patient restrictions combine, it could unintentionally broaden result sets or change which access-control filters are jointly enforced.
**Severity:** Medium — requires verification against `CareTeamService::getAll()` implementation; flag for explicit test coverage confirming it cannot broaden visibility across patients/providers.

---

### 3. Removed `getOne()` override — verify behavior parity
**Location:** Removed:
```php
public function getOne($fhirResourceId, $puuidBind = null) { ... $this->careTeamService->getOne($fhirResourceId, $puuidBind) ... }
```
**Problem:** The custom `getOne()` (which called `careTeamService->getOne()` directly, presumably with internal access checks) was removed in favor of the generic `FhirServiceBase::getOne()`, which builds a search via `_id` and (conditionally, see Finding #1) the patient binding. This is consistent with the new search-parameter design, but combined with Finding #1, the net effect is a loss of enforced patient-boundary filtering for single-record lookups. Verify that `careTeamService->getAll()` enforces equivalent record-level ownership checks independent of the FHIR service layer.
**Severity:** Medium (dependent on Finding #1).

---

### 4. Potential Injection — downstream call to `lookup_code_descriptions()`
**Location:**
```php
$description = lookup_code_descriptions($dataRecordProvider['role_code']);
...
$description = lookup_code_descriptions($dataRecordFacility['facility_taxonomy']);
```
**Problem:** This change routes `role_code` / `facility_taxonomy` values (sourced from provider/facility records) into a legacy global function not shown in this diff. If `lookup_code_descriptions()` builds SQL via string concatenation rather than parameterized queries, this introduces a SQL Injection vector wherever these fields can be influenced by user input (e.g., free-text taxonomy entry during facility/provider setup). This pre-existing function should be audited as part of this change since it is now invoked from a new code path.
**Severity:** Medium (contingent on implementation of `lookup_code_descriptions`) — flag for verification.

### 5. Data Integrity — Hardcoded `versionId`
**Location:**
```php
$fhirMeta->setVersionId('1');
```
**Problem:** Every resource always reports version `1`, regardless of actual update history. This misrepresents resource versioning to FHIR clients and could mask tampering or updates (loss of integrity signal for consumers relying on `versionId`/`lastUpdated` for optimistic concurrency or change detection). Pre-existing behavior, but worth flagging under Software & Data Integrity Failures since it's untouched despite the surrounding refactor.
**Severity:** Low.

### 6. Logic bug with possible data-exposure consequence — `end($dataRecordProviderList)`
**Location:**
```php
// provider can have more than facility matching... we are only going to grab the first facility for now
$dataRecordProvider = end($dataRecordProviderList);
```
**Problem:** Comment states "grab the first facility" but `end()` returns the **last** element. This is primarily a correctness bug, but it could result in associating a CareTeam participant with an unintended facility/organization record — a minor information-integrity concern (wrong organizational association disclosed in a clinical resource).
**Severity:** Low.
