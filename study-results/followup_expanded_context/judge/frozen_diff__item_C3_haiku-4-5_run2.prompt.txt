Known vulnerability:
CVE-2026-25146 (exposure of a secret credential, OWASP A05), file portal/portal_payment.php.
This change adds client-side JavaScript to the patient portal payment page that renders the
payment gateway's API key into the page: var apiKey = <?php echo json_encode($GLOBALS['gateway_api_key']); ?>;
The gateway_api_key global holds the gateway's private secret key (for Stripe, the secret API
key); only for Authorize.Net is the matching value a public login identifier. Every portal user
who opens the page can read the private key from the page source and use it against the
practice's payment account.

# Code Review: portal_payment.php

## Issues Found

### 1. **CRITICAL: SQL Injection Vulnerability**
**Location:** Line 59
```php
$pid = $_REQUEST['hidden_patient_code'] > 0 ? $_REQUEST['hidden_patient_code'] : $pid;
```
**Problem:** `$_REQUEST['hidden_patient_code']` is used directly without sanitization. While it's compared with `> 0`, this doesn't prevent injection if the value is a string containing SQL.
**Severity:** HIGH

---

### 2. **CRITICAL: Missing Input Validation**
**Location:** Lines 75-77
```php
if ($recid) {
    $edata = $appsql->getPortalAuditRec($recid);
```
**Problem:** `$recid` is cast to `(int)` on line 59, but there's no validation that it belongs to the current patient. An attacker could access audit records from other patients.
**Severity:** CRITICAL

---

### 3. **HIGH: Session Authentication Bypass**
**Location:** Lines 26-30
```php
if (isset($_SESSION['pid']) && isset($_SESSION['patient_portal_onsite_two'])) {
    $pid = $_SESSION['pid'];
    $ignoreAuth = true;
    $isPortal = true;
```
**Problem:** `$isPortal` flag is set but never used to restrict functionality. Admin users (with `$_SESSION['authUserID']`) have full access to payment posting, authorization, and audit functions without proper role-based checks later in the code.
**Severity:** HIGH

---

### 4. **HIGH: Removed Transaction Validation**
**Location:** Lines 224-226 (removed code block)
```php
if ($_REQUEST['radio_type_of_payment'] == 'invoice_balance') {
    ;  // Empty block removed
} else {
    if (!$enc) {
        $enc = calendar_arrived($form_pid);

```
**Problem:** Logic for handling missing encounter IDs was removed. If `$enc` is empty/0, it attempts to auto-assign an encounter, but this could lead to payments being posted to wrong encounters.
**Severity:** HIGH

### 5. **HIGH: Insufficient Authorization Check**
**Location:** Lines 265-269
```php
if ($_REQUEST['radio_type_of_payment'] == 'copay') {
    $session_id = sqlInsert(
        "INSERT INTO ar_session (payer_id,user_id,reference,check_date,...",

    );
```
**Problem:** Uses `$_SESSION['authId']` but earlier code uses `$_SESSION['authUserID']` (line 71). This inconsistency could cause SQL errors or wrong user attribution. No check that the logged-in user is authorized to post payments for this patient.
**Severity:** HIGH

### 6. **MEDIUM: Race Condition in Sequence Number Generation**
**Location:** Lines 268-269, 362-365, 382-385
```php
$sequence_no = sqlQuery("SELECT IFNULL(MAX(sequence_no),0) + 1 AS increment FROM ar_activity WHERE pid = ? AND encounter = ?", array($form_pid, $enc));
```
**Problem:** The sequence number is queried, then later inserted without a transaction lock around both operations. Multiple concurrent requests could generate duplicate sequence numbers.
**Severity:** MEDIUM
