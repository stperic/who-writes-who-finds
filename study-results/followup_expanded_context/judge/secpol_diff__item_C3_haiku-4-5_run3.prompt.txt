# Security Review of portal_payment.php

I have identified several security vulnerabilities in this code:

---

## 1. **Broken Access Control - Missing Authorization Check on `recid` Parameter**
**Location:** Line 59
```php
$recid = isset($_REQUEST['recid']) ? (int) $_REQUEST['recid'] : 0;
```
**Category:** Broken Access Control (A01:2021)

**Problem:** The code accepts a `recid` parameter and uses it to fetch audit records via `$appsql->getPortalAuditRec($recid)` (line 75) without any authorization checks. An authenticated user could potentially access payment audit records for other patients by manipulating the `recid` parameter.

**Severity:** HIGH

**Recommendation:** Add authorization checks to verify the user can only access audit records for their own patient ID or those they are authorized to view.

---

## 2. **SQL Injection via Unsafe Parameter Usage**
**Location:** Lines 268, 273, 276, etc.
```php
$session_id = sqlInsert(
    "INSERT INTO ar_session (...) VALUES ('0',?,?,now(),now(),?,'','patient','COPAY',?,?,'patient_payment',now())",
    array($_SESSION['authId'], $form_source, $amount, $form_pid, $form_method)
);
```

**Category:** Injection (A03:2021)

**Problem:** While parameterized queries are used (good), the `$form_method`, `$form_source`, and other user inputs from `$_POST` and `$_REQUEST` are passed directly without validation. Although they're parameterized, there's no input validation to ensure they contain expected values.

**Severity:** MEDIUM

**Recommendation:** Validate all user inputs against expected values using whitelists (e.g., payment methods should only be from list_options table).

---

## 3. **Missing CSRF Protection**
**Location:** Lines 205-406 (POST form handling)

**Category:** Security Misconfiguration (A05:2021)

**Problem:** The code checks `if ($_POST['form_save'])` but does not validate CSRF tokens. An attacker could forge a POST request to make unauthorized payments on behalf of an authenticated user.

**Severity:** HIGH

**Recommendation:** Implement CSRF token validation:
```php
if ($_POST['form_save']) {
    if (!isset($_POST['csrf_token']) || $_POST['csrf_token'] !== $_SESSION['csrf_token']) {
        die('CSRF token validation failed');
    }
    // ... rest of code
}
```

## 4. **Inconsistent Output Encoding - XSS Risk**
**Location:** Multiple locations, e.g., Lines 974-975, 1210
```php
echo htmlspecialchars($patdata['fname'], ENT_QUOTES) // Some places use attr()
echo text($ccdata["cardHolderName"]) // Other places use text()
echo xlt('...')  // Translation without proper encoding
```

**Category:** Cross-Site Scripting (A03:2021)

**Problem:** The code inconsistently uses different encoding functions (`htmlspecialchars()`, `attr()`, `text()`, `xlt()`). While these functions appear to provide escaping, mixing them creates cognitive load and risk of mistakes. The `xlt()` function's encoding behavior is unclear from this context.

**Severity:** MEDIUM

**Recommendation:** Consistently use the application's standard encoding function throughout. Verify that `xlt()` properly escapes output.

## 5. **Sensitive Data Exposure - Credit Card Information Logging**
**Location:** Lines 79-85
```php
$ccdata = json_decode(decryptStandard($edata['checksum']), true);
// Later displayed in HTML without clear PCI-DSS compliance
echo $ccdata["cardNumber"] . "</span><br>";  // Full CC visible to admins (line 1268)
```

**Category:** Cryptographic Failures (A02:2021)

**Problem:** Full credit card numbers are displayed in the UI (line 1268) and stored in the database. While there's decryption, PCI-DSS compliance requires that card data should never be fully displayed or stored server-side.

**Severity:** CRITICAL

**Recommendation:** 
- Never store full credit card numbers server-side
- Use tokenization from payment processors
- Only display last 4 digits: `substr($ccdata["cardNumber"], -4)`

## 6. **Insecure Session Handling**
**Location:** Lines 26-31
```php
session_start();

if (isset($_SESSION['pid']) && isset($_SESSION['patient_portal_onsite_two'])) {
    $pid = $_SESSION['pid'];
    $ignoreAuth = true;  // Setting ignoreAuth flag
```

**Category:** Identification and Authentication Failures (A07:2021)

**Problem:** The code sets `$ignoreAuth = true` based on session variables that could be manipulated. Session fixation/hijacking could allow attackers to bypass authentication.

**Severity:** HIGH

**Recommendation:** 
- Regenerate session ID after authentication: `session_regenerate_id(true)`
- Validate session data more rigorously
- Use httponly and secure flags on cookies

## 8. **Weak Transaction Integrity Controls**
**Location:** Lines 255-280

**Category:** Software and Data Integrity Failures (A08:2021)

**Problem:** Race condition: Multiple concurrent requests could generate the same `sequence_no`. The MAX query followed by INSERT is not atomic.

**Severity:** MEDIUM

**Recommendation:** Use database-level auto-increment or unique constraints to prevent race conditions.
