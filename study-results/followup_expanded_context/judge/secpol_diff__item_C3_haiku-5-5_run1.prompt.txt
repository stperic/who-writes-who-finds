# Security Review: `portal/portal_payment.php`

**Verdict: Not safe to merge.** The diff adds at least two critical access-control flaws and introduces stored XSS and PCI-scope card-data handling problems. I could not see `paylib.php`, `getPortalAuditRec()`, `decryptStandard()`, or the `sqlQuery` helpers, so some findings depend on how those behave. Those assumptions are noted below.

---

## Critical

### 1. Patient can override their session `pid` via request parameters (Broken Access Control, A01)
**Location:** around line 58
```php
$pid = isset($_REQUEST['pid']) ? $_REQUEST['pid'] : $pid;
$pid = $_REQUEST['hidden_patient_code'] > 0 ? $_REQUEST['hidden_patient_code'] : $pid;
```
**Problem:** In portal mode, `$pid` is set from the authenticated session. These lines then let any request parameter replace it. A logged-in portal patient can send `pid=<other patient>` or `hidden_patient_code=<other patient>` and then read that patient's invoices, balances, and patient-name data. The POST handler also writes `ar_session`, `ar_activity`, and `frontPayment` rows using `$_POST['form_pid']`, which is never checked against the session. The result is cross-patient payment posting and modification.
**Severity:** Critical
**Fix:** In portal mode, ignore request-supplied `pid`. Use only `$_SESSION['pid']`. Compare `form_pid` and `hidden_patient_code` to the session value and reject mismatches.

### 2. IDOR via `recid` exposes any patient's stored card data (Broken Access Control, A01)
**Location:** around lines 73–78
```php
$recid = isset($_REQUEST['recid']) ? (int) $_REQUEST['recid'] : 0;
if ($recid) {
    $edata = $appsql->getPortalAuditRec($recid);
}
```
**Problem:** `getPortalAuditRec()` is looked up by record ID with no check that the record belongs to the current patient or user. The record is then decrypted and rendered, including the full card number and CVV (see finding 4). Any portal user who can enumerate IDs can read other patients' card data.
**Severity:** Critical
**Fix:** Require `pid` ownership in the query, for example `WHERE id = ? AND pid = ?`, using the session pid in portal mode. For staff, verify an explicit permission.

## High

### 3. Stored XSS through unescaped card number output (Injection, A03)
**Location:** card display block
```php
echo $ccdata["cardNumber"] . "</span><br>";
...
echo "**********  " . substr($ccdata["cardNumber"], -4) . "</span><br>";
```
**Problem:** `cardNumber` comes from the patient's submitted form and is stored in the audit record. Neither output is escaped, so a crafted value such as `<img src=x onerror=...>` runs in the staff user's browser when they open the payment review page. Staff are the higher-value target. The same block also prints `$ccdata["cardNumber"]` unescaped for staff. The author escaped the other fields with `text()`, so this omission looks accidental.
**Severity:** High
**Fix:** Wrap every output in `text()`. Better, do not render or store the raw PAN at all (see finding 4).

### 4. Full PAN and CVV stored and displayed; PCI-DSS violation (Cryptographic Failures, A02)
**Location:** `$ccdata` decryption and display; `echo text($ccdata["cardCode"])`; `cardNumber` and `cardCode` in the audit payload
**Problem:**
- The audit payload stores the card number and CVV. Even when encrypted with `decryptStandard()`, PCI-DSS prohibits storing CVV/CVC after authorization. This also brings the storage into PCI scope.
- Staff see the full PAN (`isset($_SESSION['authUserID'])`) and the CVV on the review page.
- The CVV is still in the stored record in InHouse mode, so the earlier cleanup in the Authorize.Net branch does not cover it.
- Decrypting with a shared site-wide key means one key compromise exposes all stored cards.

**Severity:** High
**Fix:** Never persist CVV. Tokenize the card through the gateway, and store only the last four digits and token/transaction ID. Remove CVV rendering. Mask the PAN to last four for staff.

### 5. Raw PAN and CVV sent to the application server in InHouse mode (Cryptographic Failures, A02)
**Location:** `paySubmit` AJAX and `paymentForm` (InHouse / non-Stripe path)
**Problem:** The `cardNumber`, `cardCode`, and expiration fields are posted in the clear to `paylib.php`, which then stores them (finding 4). Tokenization is required to keep card data off the server.
**Severity:** High (in combination with the PCI issues above)
**Fix:** Use a hosted or tokenizing gateway (Accept.js, Stripe Elements) for all modes. Remove "InHouse" card capture, or restrict it to a fully PCI-scoped environment.

## Medium

### 6. No CSRF protection on payment-posting endpoints (A01 / Insecure Design)
**Location:** `$_POST['form_save']` handler, `invoiceForm` submit, `paylib.php` POST
**Problem:** There are no anti-CSRF tokens. A malicious page can auto-submit a POST that records payments, creates `ar_session` rows, or changes `last_level_closed` and `billed` flags, while the victim's staff or patient session is active.
**Severity:** Medium
**Fix:** Add a per-session CSRF token (OpenEMR's `CsrfUtils`) to all state-changing forms and verify it server-side.

### 7. No server-side validation of payment amounts (Insecure Design / Data Integrity, A04)
**Location:** `foreach ($_POST['form_upay'] ...)`, `form_prepayment`, `$amount = 0 + $payment`
**Problem:** The only check against negative payments is client-side (`calctotal`). The server accepts negative values, non-numeric `form_prepayment`, and amounts far above the balance. A negative `pay_amount` in `ar_activity` can reverse charges or create phantom credits. `form_prepayment` goes straight to `ar_session.pay_total` without validation.
**Severity:** Medium
**Fix:** Validate on the server: `is_numeric`, `> 0`, `<= outstanding balance`. Reject or cast the rest. Use `floatval`/`round` and enforce the currency scale.

### 8. Payment attribution uses the wrong session key (Logging & Monitoring, A09 / Integrity, A08)
**Location:** `post_user` values: `$_SESSION['authId']` in the copay branch, `$_SESSION['authUserID']` in the invoice branch, `$_SESSION['authUserID']` for `ar_activity` in the excess branch
**Problem:** The previous code used `3` as a fixed `post_user`. Portal sessions have no `authUserID`, so these rows get a null or wrong attribution. Staff actions are also inconsistently keyed (`authId` vs `authUserID`). The audit trail therefore cannot reliably show who posted a payment, and no explicit audit log entry is written for payment posting or for viewing card data.
**Severity:** Medium
**Fix:** Use one session identifier. In portal mode, record `pid` and a portal actor marker. Write audit events for payment creation and for card-data views.

### 9. Race condition in `sequence_no` allocation and no error handling (Data Integrity, A08)
**Location:** `SELECT IFNULL(MAX(sequence_no),0)+1 ...` followed by `INSERT`, wrapped in `sqlBeginTrans`/`sqlCommitTrans`
**Problem:** Two concurrent payments for the same encounter can read the same MAX and insert duplicate sequence numbers. Also, `sqlStatement` return values are not checked, and nothing rolls back if an insert fails, so a partial payment can commit.
**Severity:** Medium
**Fix:** Lock the rows (`SELECT ... FOR UPDATE`) or use an auto-increment column. Check return codes and roll back on failure.

## Low

### 10. Gateway API key emitted to every client (Sensitive Data Exposure, A02)
**Location:** `var apiKey = <?php echo json_encode($GLOBALS['gateway_api_key']); ?>;`
**Problem:** The key is printed into every patient page unconditionally. Authorize.Net's `apiLoginID` is designed to be public, but a Stripe or other secret key is not. If `gateway_api_key` is a secret, it is exposed to every browser.
**Severity:** Low (Medium if the value is a secret key)
**Fix:** Emit only publishable or client keys. Keep secret keys server-side.

### 11. `json_encode` output placed inside `<script>` without HTML escaping (XSS, A03)
**Location:** `var publicKey = <?php echo json_encode(...) ?>;` and similar
**Problem:** `json_encode` does not escape `</script>` or `<!--`. A config value containing `</script>` would break out of the script block. The risk is low because admins control these values.
**Severity:** Low
**Fix:** Use `json_encode($v, JSON_HEX_TAG | JSON_HEX_AMP | JSON_HEX_APOS | JSON_HEX_QUOT)`.

### 12. Client-side scripts without integrity checks (Vulnerable Components, A06 / Integrity, A08)
**Location:** `jquery/dist/jquery.min.js`, `jquery.creditCardValidator.js`, `textformat.js`, and the Stripe / Accept.js includes
**Problem:** Scripts are loaded without Subresource Integrity, and the jQuery version is not verified in this diff. The change also drops a version-specific path that may have been pinned.
**Severity:** Low
**Fix:** Pin and verify versions. Use SRI for CDN-hosted scripts. Check that the jQuery version has no known CVEs.

### 13. Unvalidated authorization number prompt (Integrity, A08)
**Location:** `getAuth()`
**Problem:** The authorization code is pre-filled from a field and written back with no format or length check. This is low risk but can let staff record arbitrary authorization codes.
**Severity:** Low
**Fix:** Validate the format server-side, and log the change.

## Informational / Needs Verification

- **Receipt path (`$_REQUEST['receipt']`)**: The receipt branch loads a payment record from request input. Verify that it enforces patient ownership, the same problem as finding 2.
- **Mixed `$_REQUEST` and `$_POST`**: `$_POST['form_save']` is used alongside `$_REQUEST` for other fields. Standardize on explicit `$_POST` for state-changing actions.
- **Undefined index**: `$_REQUEST['hidden_patient_code']` is read without `isset`, which raises a notice when the field is absent and could leak paths if display_errors is on.
- **`$ccdata` may be `null`**: If `decryptStandard()` fails, `$ccdata['authCode']` produces notices and undefined behaviour. Handle decryption failure explicitly.
- **Malformed HTML** (`<tr">`, `<htlm>`): not a security issue, but it may affect the `hidden` class logic that controls the copay option.
