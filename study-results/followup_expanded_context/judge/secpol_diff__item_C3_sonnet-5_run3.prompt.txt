# Security Review – `portal/portal_payment.php`

## 1. Critical: IDOR via new `recid` parameter (Broken Access Control – A01:2021)

**Location:**
```php
$recid = isset($_REQUEST['recid']) ? (int) $_REQUEST['recid'] : 0;
...
if ($recid) {
    $edata = $appsql->getPortalAuditRec($recid);
} else {
    $edata = $appsql->getPortalAudit($pid, 'review', 'payment');
}
```

**Problem:** The original code always scoped the audit/payment lookup to the authenticated session's `$pid`. The new `getPortalAuditRec($recid)` path fetches a payment-audit record **by raw numeric ID only**, with no check that the record actually belongs to the patient/session making the request (`$pid`/`$_SESSION['pid']`). Since `$recid` comes straight from `$_REQUEST`, any authenticated portal user (or anyone who can reach this endpoint, given `$ignoreAuth = true`) can enumerate `recid` values and pull **another patient's** decrypted payment payload (`$ccdata`), which includes full card number, expiration date, CVV (`cardCode`), cardholder name, zip, and invoice totals.

This is a textbook Insecure Direct Object Reference. The newly added `$isPortal` flag is set but never actually used to enforce that the retrieved record matches the current patient — a half-implemented access control.

**Severity:** Critical (sensitive PCI data + PII exposure across patients).

## 2. Critical: Storage and disclosure of full card number / CVV (Cryptographic Failures / Insecure Design – A02, A04:2021)

**Location:**
```php
echo $ccdata["cardNumber"] . "</span><br>";
...
<strong><?php echo xlt('CVV'); ?>: </strong><span id="cvvpin"><?php echo text($ccdata["cardCode"]) ?></span><br>
```

**Problem:** The application stores (encrypted, via `decryptStandard`) and later **displays the CVV and full PAN** in the browser. Storing the CVV at all after authorization is a PCI-DSS violation (CVV2/CVC2 must never be retained). Combined with issue #1, this data is reachable by unauthorized users. Even restricted to the admin branch, persisting/displaying raw CVV and full PAN is an architectural flaw, not just an encryption bug.

**Severity:** Critical.

## 3. High: `form_pid` trusted from client input for financial transactions (Broken Access Control – A01:2021)

**Location:**
```php
$form_pid = $_POST['form_pid'];
...
frontPayment($form_pid, ...);
idSqlStatement("insert into ar_session ... patient_id = ?", array(..., $form_pid, ...));
```
(and the pre-existing, related lines)
```php
$pid = isset($_REQUEST['pid']) ? $_REQUEST['pid'] : $pid;
$pid = $_REQUEST['hidden_patient_code'] > 0 ? $_REQUEST['hidden_patient_code'] : $pid;
```

**Problem:** The patient ID used to record payments/encounters is taken directly from POST data rather than being derived/verified against `$_SESSION['pid']`. A logged-in portal user can submit a crafted request with a different `form_pid`/`pid`/`hidden_patient_code` and post payments, adjustments, or balance changes against another patient’s account. This diff adds more code around this flow (sequence numbers, ar_activity inserts) without adding any ownership check.

**Severity:** High.

## 4. Medium/High: Unescaped output of card data (Injection – XSS, A03:2021)

**Location:**
```php
echo $ccdata["cardNumber"] . "</span><br>";
...
echo "**********  " . substr($ccdata["cardNumber"], -4) . "</span><br>";
```

**Problem:** Unlike most other fields in this file which are passed through `text()`/`htmlspecialchars()`/`attr()`, `cardNumber` is echoed raw. If this value (ultimately attacker-controlled input from the payment form, validated only client-side with a regex) ever contains HTML/script content, it will be rendered unescaped in the admin’s browser — a stored XSS that executes in a privileged (staff) session, enabling session hijacking or further admin-context attacks.

**Severity:** High (executes in admin context, though exploitation requires getting malicious data into `ccdata`).

## 5. Medium: Broken/undefined session variable used for audit trail (Security Logging & Monitoring Failures – A09:2021)

**Location:**
```php
$session_id = sqlInsert(
    "INSERT INTO ar_session (payer_id,user_id,reference,...)" .
    " VALUES ('0',?,?,now(),now(),?,'','patient','COPAY',?,?,'patient_payment',now())",
    array($_SESSION['authId'], $form_source, $amount, $form_pid, $form_method)
);
...
array($form_pid, $enc, $sequence_no['increment'], $Codetype, $Code, $Modifier, $_SESSION['authId'], $session_id, $amount)
```

**Problem:** `$_SESSION['authId']` is never set anywhere in this file (only `$_SESSION['authUserID']` is checked/used elsewhere). This means the `user_id`/`post_user` audit columns for copay transactions will be NULL/empty, weakening the audit trail for who posted a payment — important for a financial transaction log. This looks like a copy/paste bug that undermines traceability/non-repudiation.

**Severity:** Medium.

## 6. Medium: Reliance on client-side validation only for payment data (Insecure Design – A04:2021)

**Location:** Card form fields (`cardNumber`, `cardCode`, `cardHolderName`, etc.) had `required`/`pattern` attributes removed or weakened, and there is no visible server-side revalidation of card number format, CVV length, or expiry before it is stored/processed in `paylib.php` (not shown, but relied upon by this page).

**Problem:** HTML5 `pattern`/`required` attributes are trivially bypassed. There is no evidence of server-side validation of these fields before they are persisted (encrypted) and later redisplayed. This increases the attack surface for the XSS in #4 and for malformed/malicious data reaching storage.

**Severity:** Medium.

## 7. Low/Medium: Possible exposure of gateway API key to client (Security Misconfiguration / Cryptographic Failures – A02/A05:2021)

**Location:**
```php
var publicKey = <?php echo json_encode($GLOBALS['gateway_public_key']); ?>;
var apiKey = <?php echo json_encode($GLOBALS['gateway_api_key']); ?>;
```

**Problem:** `gateway_api_key` is emitted directly into client-side JavaScript. For Authorize.Net’s Accept.js flow this is expected to be a public API Login ID, but the generic naming (`gateway_api_key` vs. a dedicated “public”/“client” key) raises the risk that a more sensitive key (e.g., transaction key) could end up here through misconfiguration. This should be explicitly verified/renamed to make clear only a public-safe key is ever sent to the browser.

**Severity:** Low (if confirmed to be the intended public key) to High (if the transaction key is ever misconfigured into this field).

## 9. Informational: No CSRF protection visible on payment submission (Broken Access Control / Insecure Design – A01:2021)

**Location:** `#invoiceForm`, `#paymentForm`, AJAX posts to `./lib/paylib.php`.

**Problem:** No CSRF token is included in the POSTed forms/AJAX calls. Combined with `$ignoreAuth = true` and the `form_pid` trust issue (#3), a CSRF attack from a page the patient visits while authenticated to the portal could submit unauthorized payments/charges. This is a pre-existing design gap that this change continues to rely on without adding mitigation.

**Severity:** Medium (payment-related CSRF).

## 10. Informational: Race condition in manual sequence number generation (Data Integrity – A08:2021)

**Location:**
```php
sqlBeginTrans();
$sequence_no = sqlQuery("SELECT IFNULL(MAX(sequence_no),0) + 1 AS increment FROM ar_activity WHERE pid = ? AND encounter = ?", ...);
sqlStatement("insert into ar_activity set ... sequence_no = ?, ...", ...);
sqlCommitTrans();
```

**Problem:** `sqlBeginTrans`/`sqlCommitTrans` around a `SELECT MAX()+1` then `INSERT` pattern is a classic TOCTOU race condition unless the transaction isolation level and row locking are guaranteed elsewhere (e.g., `SELECT ... FOR UPDATE`). Concurrent payment submissions for the same encounter could generate duplicate `sequence_no` values, corrupting the financial ledger.

**Severity:** Low/Medium (data integrity, not directly exploitable remotely but a reliability/integrity concern in a financial table).
