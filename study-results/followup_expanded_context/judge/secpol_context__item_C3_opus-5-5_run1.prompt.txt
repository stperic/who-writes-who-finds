# Security Review: `portal/portal_payment.php`

## Summary

This change should not be merged as-is. Two problems are introduced by this PR:

- **The payment gateway secret is sent to the browser.** When Stripe is the gateway, `gateway_api_key` holds the Stripe secret key, and the PR writes it into the page for every portal patient.
- **A new IDOR exposes stored card data.** The new `recid` parameter lets a patient read any patient's stored payment record, including the decrypted card number and CVV.

The page also has serious older flaws that this change touches or relies on: patient ID taken from user input, CVV stored and displayed, card numbers echoed without escaping, and no CSRF protection.

---

## Findings

### 1. Gateway secret key exposed to every portal user (new)

- **Location:** the new JS block
  ```php
  var publicKey = <?php echo json_encode($GLOBALS['gateway_public_key']); ?>;
  var apiKey    = <?php echo json_encode($GLOBALS['gateway_api_key']); ?>;
  ```
- **Category:** A02 Cryptographic Failures (sensitive data exposure); also A05 Security Misconfiguration.
- **Problem:**
  - `globals.inc.php` describes `gateway_api_key` as "Auth Name for Authorize.Net and **API Secret for Stripe**." It is stored as an `encrypted` global, which shows it is meant to stay secret.
  - The value is written into the page's JavaScript no matter which gateway is configured.
  - With Stripe, any logged-in portal patient, or anyone who gets the page HTML through XSS, a cached page or a shared computer, can read the merchant's Stripe secret key.
  - With that key an attacker can issue refunds, create charges, list customers and payment data, change webhooks, and so on.
  - The Stripe client code doesn't even use `apiKey`; it only needs `publicKey`.
- **Severity:** **Critical**
- **Fix:**
  - Never send `gateway_api_key` or `gateway_transaction_key` to the client.
  - For Authorize.Net Accept.js, emit only the API Login ID, and only when `payment_gateway == 'AuthorizeNet'`.
  - For Stripe, emit only the publishable key.
  - Rotate any Stripe secret key that may already have been exposed.

### 2. IDOR via new `recid` parameter, exposing decrypted card data (new)

- **Location:**
  ```php
  $recid = isset($_REQUEST['recid']) ? (int) $_REQUEST['recid'] : 0;
  if ($recid) { $edata = $appsql->getPortalAuditRec($recid); }
  ...
  $ccdata = json_decode(decryptStandard($edata['checksum']), true);
  ```
- **Category:** A01 Broken Access Control
- **Problem:**
  - The audit record is loaded by a client-supplied ID. Nothing checks that the record belongs to `$_SESSION['pid']`, or that the caller is staff.
  - A portal patient can loop over `recid` values and get other patients' records decrypted and displayed: name on card, zip, card number, expiry, CVV, and auth/transaction IDs.
  - When `transId` is set, the full card number is shown even to non-staff, because of the condition `isset($_SESSION['authUserID']) || isset($ccdata["transId"])`.
- **Severity:** **Critical** (PCI cardholder data and PHI disclosure)
- **Fix:**
  - For portal sessions, require that the record's `patient_id` equals `$_SESSION['pid']`.
  - Allow arbitrary `recid` only for authenticated staff with billing ACL.

### 3. Patient ID taken from the request in portal context (pre-existing, relied on)

- **Location:**
  - `$pid = isset($_REQUEST['pid']) ? ... ;`
  - `$pid = $_REQUEST['hidden_patient_code'] > 0 ? ...;`
  - `$form_pid = $_POST['form_pid'];`
- **Category:** A01 Broken Access Control
- **Problem:**
  - A portal patient (authenticated with `$ignoreAuth = true`) can override `$pid` and view any patient's name, encounters, reasons for visit, balances and pending card data.
  - The new `postal_code` lookup adds to what is exposed.
  - The `form_save` branch uses the client-supplied `form_pid` to insert `ar_session`/`ar_activity` rows and update `form_encounter`/`billing` for arbitrary patients. In the `cash` path this includes marking encounters billed and closed.
  - The new `$isPortal` flag is set but never used to enforce anything.
- **Severity:** **High**
- **Fix:**
  - When `$isPortal` is true, force `$pid = $_SESSION['pid']` and ignore request values.
  - Reject `form_save` posting for portal sessions; posting should be staff-only and ACL-checked.

### 4. CVV stored and displayed (pre-existing, carried forward)

- **Location:** `<span id="cvvpin"><?php echo text($ccdata["cardCode"]) ?></span>`, together with the full PAN display for staff.
- **Category:** A02 Cryptographic Failures
- **Problem:**
  - In InHouse mode the CVV is stored in the audit table, encrypted only reversibly, and shown back to users.
  - Storing sensitive authentication data after authorization is prohibited by PCI DSS 3.2.
  - Showing the full PAN to all staff violates the masking requirements.
- **Severity:** **High**
- **Fix:**
  - Do not persist CVV.
  - Mask the PAN everywhere.
  - Prefer the tokenized gateways and deprecate InHouse card capture.

### 5. Stored XSS via unescaped card number

- **Location:** `echo $ccdata["cardNumber"] . "</span><br>";`
- **Category:** A03 Injection (XSS)
- **Problem:**
  - `cardNumber` comes from patient-supplied form input. The `pattern="\d"` restriction is client-side only.
  - It is echoed raw on the staff audit view, so a patient can plant script that runs in a staff session.
  - Other fields in the same block were changed to `text()`, but this one was missed.
- **Severity:** **Medium–High**
- **Fix:** `echo text($ccdata["cardNumber"])`, and apply the same to the masked branch.

### 6. No CSRF protection on state-changing POSTs

- **Location:** the `form_save` handling and the posts to `paylib.php`.
- **Category:** A01 Broken Access Control / A04 Insecure Design
- **Problem:** No CSRF token is checked. A malicious page can make a logged-in staff member post payments, or close and bill encounters.
- **Severity:** **Medium**
- **Fix:** Add and verify CSRF tokens.

### 7. Minor issues

- **Wrong patient ID in `user_id` (A09 Security Logging and Monitoring Failures, Low):**
  - In portal context, `$_SESSION['authUserID']` and `authId` may be unset, so `ar_session.user_id` and `post_user` are recorded as null or wrong.
  - This weakens the payment audit trail.
- **Unescaped output in `<script src>` and `action` (A03, Low):** `$GLOBALS['webroot']` and `assets_static_relative` are output without `attr()`. These are admin-controlled, so the risk is low.
- **Server-side amount validation (A04, Medium):**
  - The negative-amount check is only in client JS (`calctotal`).
  - The server should validate that amounts are positive and do not exceed the balance.

---

## Required Before Merge

1. Remove the `apiKey` emission and rotate the exposed secrets.
2. Enforce ownership checks on `recid`, `pid`, `hidden_patient_code` and `form_pid` for portal sessions.
3. Escape `cardNumber` output.
4. Stop storing and displaying CVV.
5. Add CSRF protection.
