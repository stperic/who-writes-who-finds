# Security Review: `FhirCareTeamService.php`

## Finding 1: Patient-scoped access control is lost (cross-patient data exposure)

**Location**
- `src/Services/FHIR/FhirCareTeamService.php`: the class declaration, the removed `getOne()` override, and `searchForOpenEMRRecords()`.
- The flaw comes from how this class interacts with `FhirServiceBase::getOne()`, `getAll()` and `createOpenEMRSearchParameters()`.

**OWASP category:** A01:2021 – Broken Access Control

**Severity:** High to Critical. This exposes PHI and breaks the patient-compartment security model for SMART patient-context access.

**Problem**

Before this change, the class had its own `getOne()`. It passed `$puuidBind` straight to `CareTeamService::getOne($fhirResourceId, $puuidBind)`, so the database layer limited results to the bound patient.

This PR removes that override. The class now uses `FhirServiceBase::getOne()` and `getAll()`. In the base class, the patient binding is only applied when the service is a patient-compartment service:

```php
if (isset($puuidBind) && $this instanceof IPatientCompartmentResourceService) { ... }
...
if (!empty($puuidBind) && $this instanceof IPatientCompartmentResourceService) {
    $patientField = $this->getPatientContextSearchField();
    $oeSearchParameters[$patientField->getName()] = ...;
}
```

`FhirCareTeamService` does not meet that condition:
- It implements only `IResourceUSCIGProfileService`.
- It does **not** implement `IPatientCompartmentResourceService`.
- It does define `getPatientContextSearchField()`, but the base class never calls it because the `instanceof` check fails.

The base class also has a pre-existing weakness that this change now depends on. `getAll()` calls `$this->searchForOpenEMRRecords($oeSearchParameters)` without passing `$puuidBind`. The CareTeam override does accept `$puuidBind = null` and forwards it to `careTeamService->getAll(...)`, but it always receives `null`. As a result, the `instanceof` check is the only remaining enforcement point.

**Impact**

A client with a patient-bound token (for example, a SMART `patient/CareTeam.read` scope, or the patient portal API) can read care teams that belong to other patients:
- `GET /fhir/CareTeam/{any-uuid}` returns any patient's care team.
- `GET /fhir/CareTeam` or `GET /fhir/CareTeam?status=active` returns care teams for **all** patients.
- `GET /fhir/CareTeam?patient={other-puuid}` returns a specific other patient's care team.

The exposed data includes patient UUIDs, practitioner and facility associations, and roles.

**Fix**
1. Declare the interface:
   ```php
   class FhirCareTeamService extends FhirServiceBase implements IResourceUSCIGProfileService, IPatientCompartmentResourceService
   ```
2. Defense in depth: change `FhirServiceBase::getAll()` to forward the binding, i.e. `$this->searchForOpenEMRRecords($oeSearchParameters, $puuidBind)`. Also check that every patient-data service implements `IPatientCompartmentResourceService`, preferably with an automated test that asserts each patient-scoped resource rejects cross-patient reads.
3. Add a regression test: with a patient-bound token, a CareTeam belonging to another patient must return no results or 404 for both read and search.

## Finding 2 (Low / informational): HTML-escaped strings placed in JSON output

**Location:** the `xlt($dataRecordProvider['role_title'])` and `xlt("Unknown")` calls in `parseOpenEMRRecord()`.

**OWASP category:** A03:2021 – Injection (output encoding misuse)

**Severity:** Low

**Problem:** `xlt()` translates a string and HTML-escapes it. The resulting FHIR JSON can therefore contain HTML entities such as `&amp;`. This is not exploitable here, since it over-escapes rather than under-escapes. However, it corrupts the data, and it may push consumers to "unescape" and then render the value unsafely. Use `xl()` for translation in API output and let the consumer encode for its own rendering context.

## No other significant issues found

- The `status` value is checked against an allowlist before it is emitted.
- Search parameters go through the typed search-field factory, which uses bound parameters. No SQL injection was found in this diff.
- The provenance generation added in this PR does not introduce new exposure beyond Finding 1.

**Recommendation:** Do not merge until Finding 1 is fixed.
