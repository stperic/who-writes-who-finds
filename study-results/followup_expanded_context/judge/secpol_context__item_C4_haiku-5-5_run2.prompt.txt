# Security Review: `interface/forms/eye_mag/report.php` (new file) and related `custom_report.php`

**Recommendation: do not merge.** The file has a confirmed SQL injection, several access-control gaps, and multiple XSS sinks. Some of the most serious problems are in `custom_report.php`, which this PR does not change but which renders this report.

Line numbers are approximate because the diff does not carry them, so locations are given by function and expression.

---

## High severity

### 1. SQL injection in `display_draw_image()`
- **Location:** `report.php`, `display_draw_image()`: `$sql = "SELECT * from documents where documents.url like '%".$filename."'";`
- **OWASP:** A03 Injection
- **Problem:** `$filename` is built by concatenating `$pid`, `$encounter`, `$zone` and `"_VIEW.jpg"` into a raw SQL string. `$pid` and `$encounter` originate from `$_REQUEST['ptid']` and `$_REQUEST['encid']` at the top level of the file, with no validation. The rest of the file uses parameterized queries, but this one does not. A value such as `encid=1' UNION SELECT ... -- ` injects into the query. `LIKE` also allows `%` and `_` wildcards to match unrelated documents.
- **Severity:** High. Reachable from a GET request, and the attacker can read arbitrary DB tables (for example `users.password`).
- **Fix:** Use a parameterized query. Build the filename after validating `$pid` and `$encounter` as integers, and use an exact match (`url = ?` with a full `file://` path) instead of `LIKE`.

### 2. Broken access control and IDOR in `report.php` (top level and `narrative()`)
- **Location:** top-level `$_REQUEST['ptid']`, `$_REQUEST['encid']`, `$_REQUEST['formid']`; `narrative()`; `eye_mag_report()`
- **OWASP:** A01 Broken Access Control
- **Problem:**
  - The file never calls `acl_check()` for `patients`/`med`/`demo` or `encounters`/`notes`. Access control is left entirely to the caller.
  - Patient, encounter, and form IDs come straight from the request. Nothing verifies that the encounter belongs to the patient, or that the current user is allowed to see that patient.
  - The top-level code sets `$pid` from the request. Because `report.php` is `include_once`'d from `custom_report.php`, this overwrites the session-derived `$pid` for the rest of that request (see item 3).
- **Severity:** High.
- **Fix:** Check `acl_check('patients', 'med')` (or the appropriate ACL) at the top of the file. Derive `$pid` from the session or verify it against the encounter. Validate all IDs as integers before use.

### 3. Access control gaps in `custom_report.php`
- **Location:** `custom_report.php`, the `documents`, `issue_*`, and `procedures` branches of the `$ar` loop.
- **OWASP:** A01 Broken Access Control
- **Problem:**
  - `documents`: each value is passed to `new Document($document_id)` and its notes and file content are rendered. There is no check that the document belongs to `$pid`, so any document ID can be rendered into the report.
  - `issue_<id>`: the row is loaded with `sqlQuery("... WHERE id = '$rowid'")` with no check that `lists.pid` matches `$pid`, and no `patients/med` ACL check. Title, comments, and diagnosis for any patient's issue can be retrieved.
  - `procedures`: gated by `$auth_med` but not checked against `$pid`.
- **Severity:** High.
- **Fix:** For each branch, verify ownership (`documents.foreign_id = $pid`, `lists.pid = $pid`, procedure order `patient_id = $pid`) and check the matching ACL.

### 4. Cross-site scripting (stored and reflected)
- **Location:** `report.php`, `narrative()`:
  - Unescaped output: `<?php echo $HPI1; ?>`, `$HPI2`, `$HPI3`, `$CHRONIC2`, `$CHRONIC3` (concatenated with `"&nbsp;".$CHRONIC2`), `$item['codetext']`, `$item['code']`, `$item['plan']`, `$PLAN` (raw `echo $item`), `$PLAN2`, `$providerNAME` in the PDF branch.
  - `display_draw_image()`: `echo '<td>'.$note->get_note().'<br /><br /></td>';` is unescaped.
  - Reflected: `$pid` is placed unescaped in `img src='...patient_id=$pid...'`. Since `$pid` comes from `ptid`, a crafted value with a quote (for example `1'onerror=alert(1)//`) can break out of the attribute. The photo query is parameterized, but MySQL's numeric comparison of `'1'...'` to `foreign_id` can still match patient 1, which lets the injected output reach the page.
  - `$display_Add` is used unescaped in a `class` attribute.
- **Severity:** High. Clinician- and patient-entered text is stored and rendered to every viewer of the report.
- **Fix:** Wrap every value in `text()` (or `attr()` inside attributes). Escape note content. Cast `$pid` to int before building URLs.

### 5. Command injection in `custom_report.php`
- **Location:** `custom_report.php`, the document conversion branch: `exec("convert -density 200 \"$from_file\" -append -resize 850 \"$to_file\"");`
- **OWASP:** A03 Injection
- **Problem:** `$from_file` is built from `documents.url`. Inside double quotes the shell still expands `` ` ``, `$(...)`, and `$`. A filename containing those characters would execute commands. Whether this is exploitable depends on how uploaded filenames are sanitized, which is not shown here.
- **Severity:** High (exploitable if filenames are not strictly sanitized; otherwise medium).
- **Fix:** Use `escapeshellarg()` on both paths, or use `proc_open` with an argument array.

### 6. Unsafe variable handling: `$$LOCATION` and `@extract()`
- **Location:**
  - `report.php`, top level: `$LOCATION = $prefs['LOCATION']; $$LOCATION = text($prefs['GOVALUE']);`
  - `report.php`, `eye_mag_report()` and `narrative()`: `@extract($objQuery)` and `@extract($encounter_data)`.
  - `left_overs()`: `$$key=$value;`
- **OWASP:** A08 Software and Data Integrity Failures; A03 Injection
- **Problem:** Variable names come from database columns (`LOCATION`) that users can influence through preferences. Any name can be assigned, including `pid`, `encounter`, `form_id`, `web_root`, `fileroot`, `webserver_root`, and `choice`. `extract()` of query results does the same for every column in `form_encounter.*` and `form_eye_mag.*`, including `pid`. `@` suppresses the warnings that would otherwise reveal this.
- **Severity:** Medium-High.
- **Fix:** Replace `$$LOCATION` with an explicit whitelist array. Replace `extract()` with explicit column reads. Remove the `@` operators.

## Medium severity

### 7. Dynamic function call driven by request keys
- **Location:** `custom_report.php`: `call_user_func($res[1] . "_report", $pid, $form_encounter, $N, $form_id);`
- **OWASP:** A03 / A08
- **Problem:** `$res[1]` is taken from a POST/GET key name matched by `^(.*)_(\d+)$`, so an attacker can choose which `*_report` function runs. Only functions ending in `_report` are reachable, which limits the impact, but any such function will be called with attacker-chosen `$pid`, which bypasses the form-level authorization.
- **Fix:** Validate `$res[1]` against the set of form directories returned by the `forms` table query, and check that the directory is active.

### 8. Session `$pid` overwritten by the request, then used unparameterized
- **Location:** `custom_report.php`: `immunizations` and `batchcom` queries use `'$pid'` directly. `report.php` has already overwritten `$pid` from `ptid` during the `include_once` loop.
- **OWASP:** A03 Injection
- **Problem:** Because of item 2, `$pid` is attacker-controlled when these queries run, and they concatenate it into SQL.
- **Fix:** Parameterize these queries and remove the request-driven `$pid` assignment.

### 9. Outdated jQuery
- **Location:** `custom_report.php`: `<script src=".../jquery-min-1-5/index.js">`
- **OWASP:** A06 Vulnerable and Outdated Components
- **Problem:** jQuery 1.5 (2011) has multiple published XSS CVEs.
- **Fix:** Upgrade to a supported jQuery release and verify that `$j` usage still works.

### 10. Unescaped output in `custom_report.php`
- **Location:** `custom_report.php`: `echo $row{'batchcom_data'}` ... `$row{'msg_txt'}` (curly-brace syntax is a parse error in PHP 8, and the key is misspelled); issue output (`$irow['title']`, `$irow['comments']`, `$dcode`); billing output (`$b['code']`, `$b['code_text']`); printable header (`$facility['name']`, `$titleres['DOB_TS']`).
- **OWASP:** A03 XSS
- **Fix:** Wrap in `text()`.

### 11. Missing audit logging of PHI access
- **Location:** `report.php` and `custom_report.php`, all data reads.
- **OWASP:** A09 Security Logging and Monitoring Failures
- **Problem:** Viewing and printing a patient's clinical report, including PDF export and transmission to the patient portal, is not logged to the audit trail.
- **Fix:** Use the existing event-audit facility on report view, print, and portal send.

### 12. State change without CSRF protection
- **Location:** `custom_report.php`: `$PDF_OUTPUT == 2` sends a patient report to the CMS portal on a POST that carries no token.
- **OWASP:** A01 (CSRF)
- **Fix:** Require a CSRF token on that path.

## Low severity

### 13. Unvalidated local/remote file reference in PDF output
- **Location:** `report.php`, PDF branches: `echo "<img src='". $from_file."' ...>"` where `$from_file` is built from `documents.url`. html2pdf fetches `img src` values, so a tampered DB value could point to local files or internal URLs.
- **OWASP:** A10 SSRF / A01
- **Fix:** Resolve to a canonical path and confirm it is under the site documents directory before using it. Or embed the image bytes directly.

### 14. Code and maintenance issues that affect security
- `$choice` is read from `$_REQUEST['choice']` but tested with `$_REQUEST['CHOICE']`, so the DRAW/TEXT modes can never be selected from the request. Not a vulnerability, but it means the intended access paths are not what they appear to be.
- `full_report()` and `left_overs()` reference undefined variables. They are dead code, but `left_overs` would fail badly if called.
- `$fake_register_globals` and `$sanitize_all_escapes` are set at file scope but do nothing here. They give a false impression that input sanitization is in place.
