# Security Review: `Controller.class.php` routing refactor

I found no SQL injection or stored XSS in this diff. The concerns are mainly broken access control and insecure routing design, plus one reflected-input issue. Several of the access control findings depend on code outside this diff, which I flag where relevant.

---

### 1. Broken access control: ACL check covers only two controllers
- **Location:** `VALID_CONTROLLERS`, `CONTROLLER_ACL_MAP`, `dispatch()` (`checkControllerAcl` call)
- **OWASP:** A01:2021 Broken Access Control
- **Problem:** `CONTROLLER_ACL_MAP` has entries only for `practice_settings` and `prescription`. Every other whitelisted controller (`document`, `document_category`, `hl7`, `insurance_company`, `insurance_numbers`, `pharmacy`, `x12_partner`, `patient_finder`) is dispatched with no ACL check at the router.
  - `pharmacy` is the most concerning. The comment on `act()` describes `practice_settings -> pharmacy -> list` as a sub-controller delegation pattern, which implies pharmacy administration sits under the `admin/practice` permission. Because `pharmacy` is now directly routable via `controller=pharmacy`, that permission can be bypassed.
  - This gap existed before the diff, but the refactor makes it more visible because the whitelist now exposes these controllers by name.
- **Severity:** High (pending verification that each controller enforces its own ACL; the diff does not show this).
- **Fix:** Add an ACL entry for every whitelisted controller, or require each controller to enforce ACL in a common base method invoked by `dispatch()`. Deny by default when no entry exists.

### 2. Process branch bypasses the method-existence guard; action name is user-controlled
- **Location:** `dispatch()`, `$isProcessing && is_callable(...)` followed by `$callMethod($actionMethod)`
- **OWASP:** A03:2021 Injection (method-name injection), A04:2021 Insecure Design, A05:2021 Security Misconfiguration
- **Problem:** `$action` comes from the request and is used to build `{$action}_action`. When `process=true`, the code calls `$callMethod($actionMethod)` without checking `is_callable` or `method_exists`:
  ```php
  if ($isProcessing || is_callable([$controllerObj, $actionMethod])) {
      $output .= $callMethod($actionMethod);
  ```
  The old code guarded this path. The comment in the original code notes that `is_callable()` is unreliable under Smarty 4 because of `__call`, so an undefined name can reach `__call` or raise an uncaught `Error`. This can expose stack traces or internal class details in production. The `$callMethod` closure is also defined in `Controller` scope, so it can invoke any accessible `*_action` method on the controller object, which widens the reachable surface.
- **Severity:** Medium
- **Fix:** Always require `is_callable` (or `method_exists` plus a visibility check via `ReflectionMethod`) before invoking either action or process method. Restrict the action name to a strict pattern such as `/^[A-Za-z][A-Za-z0-9_]*$/`, and return a 404 when the method is absent.

### 3. Positional argument binding contradicts the "order-independent" routing claim
- **Location:** `dispatch()` argument build (`$args[$key] = ...`, `$controllerObj->$method(...array_values($args))`); docblock of `dispatch()`
- **OWASP:** A04:2021 Insecure Design
- **Problem:** The docblock says routing is order-independent, but arguments are passed as `array_values($args)`, so they bind by URL order, not by name. For example, `controller=document&action=view&patient_id=1&doc_id=2` and `controller=document&action=view&doc_id=2&patient_id=1` invoke the action with swapped arguments. If the target action treats its first parameter as an authorization-scoped ID, a caller can cause it to act on a different record than the one they were checked against. The same mismatch can silently break legitimate callers.
- **Severity:** Medium
- **Fix:** Bind arguments by name, for example with reflection on parameter names, or pass a single params array. Do not rely on `$_GET` key order.

### 4. State-changing actions reachable via GET; no CSRF protection at the router
- **Location:** `dispatch()`, `if (isset($params['process'])) { ... $_POST['process'] = "true"; }`
- **OWASP:** A01:2021 Broken Access Control, A04:2021 Insecure Design
- **Problem:** `process` is read from `$params`, which is typically `$_GET`. Any GET request containing `process=` sets `$_POST['process']='true'` and runs the `*_action_process` method, which is the state-changing path. This makes processing reachable through a plain link or image tag, bypassing the POST-only intent. No CSRF token is checked at the dispatch layer either, so a cross-site request can trigger process actions for an authenticated user. The CSRF gap may be pre-existing in individual controllers, but this change makes the GET-to-process path explicit.
- **Severity:** Medium
- **Fix:** Honour `process` only when `$_SERVER['REQUEST_METHOD'] === 'POST'`. Verify a CSRF token (`CsrfUtils`) before running any `*_process` method.

### 5. Reflected user input in exception messages
- **Location:** `dispatch()`: `throw new NotFoundHttpException("Action '$action' does not exist on controller: $className");`
- **OWASP:** A03:2021 Injection (reflected XSS)
- **Problem:** `$action` is raw request input. If the framework's exception renderer outputs the message as HTML without escaping, this is reflected XSS. The original code had the same issue by echoing `$c_action`, so this is not new, but it has been moved into an exception path whose rendering is not visible in this diff. The unknown-controller message is static, so it is safe. Note that `$action` also reaches `_current_action`.
- **Severity:** Low to Medium (depends on the exception handler's output encoding)
- **Fix:** Do not echo request-derived values in error messages, or HTML-encode them with `text()` or `htmlspecialchars` before output. Keep messages generic.

### 6. Type confusion from array-valued request parameters
- **Location:** `dispatch()`: `$args[$key] = $value === '' ? null : $value;`
- **OWASP:** A03:2021 Injection / A04:2021 Insecure Design
- **Problem:** Values are passed through unchecked. A request such as `foo[]=x` yields an array, which is forwarded to action methods expecting scalars. Depending on those signatures this causes `TypeError`s, or, if the methods use loose comparisons or string concatenation, unexpected behaviour. Arrays also bypass any `(string)` coercion a controller might assume.
- **Severity:** Low
- **Fix:** Reject or normalise non-scalar values at the router boundary (`is_scalar` check), or enforce types through reflection.

### 7. Insufficient logging of routing decisions and denials
- **Location:** `dispatch()` (exceptions and ACL path); `checkControllerAcl()`
- **OWASP:** A09:2021 Security Logging and Monitoring Failures
- **Problem:** The router emits no log entries for unknown controllers, missing actions, or process invocations. ACL denials go through `AccessDeniedHelper`, whose logging behaviour is not shown here. Probing of the whitelist and method names therefore leaves no trace in the router.
- **Severity:** Low
- **Fix:** Log invalid controller/action requests and process invocations with user ID and IP, consistent with the rest of the application's audit logging.

---

### Notes
- `act()` remains reachable as a deprecated entry point and still derives routing from key position. It inherits findings 1 through 3. Its `sub_action` rename also silently drops a sub-action when the second key is `action`, which should be checked.
- The whitelist `VALID_CONTROLLERS` is a sound mitigation for arbitrary class instantiation and include injection. `$className` is never built from raw input, so no LFI/RFI or arbitrary class instantiation is possible through `dispatch()`.
